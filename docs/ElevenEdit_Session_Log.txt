ELEVEN EDIT — SESSION LOG (append-only scratchpad)
===================================================================
Purpose: the ONE place provisional, unconfirmed, or in-progress findings
live during a work session. Newest entry on top. Safe to be messy and even
contradictory — nothing here is treated as truth until it is promoted.

TRUTH LIVES ELSEWHERE:
  ElevenEdit_Technical_Reference.txt — confirmed protocol/hardware facts
  ElevenEdit_Primer.txt              — project orientation & app state
Confirmed facts are EDITED IN PLACE in those two docs. This log is never a
substitute for them and is never superseded by a dated copy.

HOW AN ENTRY GRADUATES:
  1. Add findings here as you work (any state: idea, tried-X-got-Y, confirmed).
  2. When a finding is CONFIRMED, promote it: edit the value directly into the
     Technical Reference (or Primer), then mark the log entry [FOLDED IN].
  3. [FOLDED IN] entries can be deleted once the merge is verified. The log
     should trend back toward empty.

A FACT IS EITHER:
  - confirmed  -> lives in a main doc, edited in place, not here; or
  - provisional -> lives here.
Never both. Never a third dated file.

             endpoint/linearity error shows up ~4x bigger in ms on screen —

             Sync behaviour is correct regardless (confirmed by Charlie);

DATE:        2026-08-27
STATUS:      confirmed — TESTED LIVE (Charlie, 2026-08-27): min/max/midpoint
             (0.0 at centre) all correct on both To Amp 1 and To Amp 2.
AREA:        To Amp 1/2 Volume / CMD 0x36 / sendToAmpVolume (transport.js)
FINDING:     Charlie's report: both To Amp knobs rotate correctly from mute
             to +12 but hardware never actually reads past +11.8 at the top
             end (min/mute end is fine). Root cause: sendToAmpVolume never
             got the endpoint-sentinel fix that sendParamWrite (CMD 0x11)
             got on 7/23/2026 for the same "9.9 bug" class of symptom. Tech
             Ref Sec 7 already documents CMD 0x36 as part of the same
             single-byte-offset-binary family as 0x11/0x07, sentinels
             included (min 0x40 00 00 00, max 0x3F 7F 7F 7F) - the fix was
             simply never applied to this specific send function. The old
             code always sent v0 + a flat "00 00 00 00" tail, which for the
             true top value (v0=0x3F) asks for the BOTTOM of that step, not
             the top - landing about one 24dB/127-step (~0.19 dB) short of
             +12.0, consistent with the reported 11.8. Min was unaffected by
             coincidence: 0x40 00 00 00 already IS the true minimum's exact
             encoding, so there's no "bottom of the step" gap to fall into
             at that end. FIXED: sendToAmpVolume (transport.js) now special-
             cases v127>=127 with tail "7F 7F 7F 7F" (true max) and
             v127<=0 with "00 00 00 00" (unchanged, already correct),
             matching sendParamWrite's approach but WITHOUT copying CMD
             0x11's extra final-byte 0x10-broadcast-offset quirk (0x0F in
             its own max sentinel) - that quirk is specific to CMD 0x11's
             message framing per Sec 7's TRAILING BYTES note and has no
             documented equivalent for CMD 0x36.
EVIDENCE:    Charlie's live-hardware report (11.8 max, never 12.0); Tech Ref
             Sec 7 CONTINUOUS KNOBS entry naming 0x36 in the same family as
             0x11/0x07 with the same sentinel scheme; sendParamWrite's
             existing 7/23/2026 fix as the confirmed working pattern for
             this exact symptom shape.
CONFLICTS:   none — pure bug fix, no documented value changes.
NEXT:        None — closed. CONFIRMED LIVE 2026-08-27. Master (Main) Volume
             was flagged as a same-family risk but Charlie clarifies it is
             NOT a knob (it's the chain-strip stepper/value-box control,
             valToMasterVol) and is already spot-on at every value he's
             checked — the endpoint-sentinel gap is specific to the two
             CANVAS KNOB controls (To Amp 1/2) using sendToAmpVolume; no
             action needed on Master Volume.

STATUS:      [FOLDED IN: Primer WORKING/Tech Ref Sec 15 cross-check]
AREA:        RigRollerPlus auto-advance / CMD 0x03
FINDING:     Roller self-paused 4x in an 11:26-12:01 session with no real
             hardware save. Root cause: handleSaveRigResponse (sysex-
             handler.js) treated CMD 0x03 data[7]===0x01 as "a save just
             happened" and called togglePause(). But per Tech Ref Sec 4/15,
             data[7] is a per-SLOT DIRTY flag (unsaved edits present on
             that slot), not a save event, and CMD 0x03 also fires as a
             side effect of ordinary CMD 0x02 slot navigation (Sec 6) —
             including the roller's own auto-advance. Landing on an
             already-dirty slot (leftover from earlier manual editing)
             falsely read as a hardware save. Confirmed against the
             uploaded log: all 4 pause events line up exactly with "PROBE
             resp CMD 0x03 ... 01" broadcasts following ordinary nav, not
             any front-panel save action.
EVIDENCE:    RigRollerPlus session-2026-08-11-112642.log lines 8327,
             15255, 16975, 21485 — each pause immediately follows an
             unsolicited CMD 0x03 broadcast (data[6]=slot, data[7]=0x01)
             with no preceding save action; cross-checked against the full
             set of CMD 0x03 variants in the same log (data[7] is 0x01 for
             specific slots throughout an ordinary bank walk at
             11:28-11:31, long before any save).
CONFLICTS:   none — clarifies Tech Ref Sec 4's existing "CMD 0x03 dirty
             flag" note, does not contradict it.
NEXT:        FIXED, 1st pass (WRONG SCOPE): deleted the CMD 0x03 dirty-
             flag pause trigger outright and routed roller-pause only
             through handleBulkTfxData's isSave (real-save) branch. Broke
             an existing, working feature — Charlie confirmed the dirty-
             flag trigger is what correctly pauses the roll when a user
             touches ANY control (bass, vol, etc.) mid-roll; that behavior
             is intentional and was not part of the reported bug.
             FIXED, 2nd pass (CORRECT SCOPE): restored the dirty-flag
             pause-on-edit trigger, but gated it with a settle-window
             guard — ROLLER_NAV_SETTLE_GUARD (2000ms, transport.js) —
             using a new lastNavTime timestamp set in goToSlot
             (patch-nav.js). A CMD 0x03 dirty broadcast arriving within
             2000ms of the last recall is treated as settle/query noise
             from the recall itself (matches worst-case NAV_RECALL_SETTLE
             + NAV_CHAIN_TIMEOUT + NAV_AMP_TIMEOUT + query gaps); one
             arriving after that window pauses the roll same as before.
             Real hardware-save pause (isSave branch) is untouched and
             coexists with this. NOT YET TESTED LIVE — needs (a) a full
             roll session with no false pauses on dirty slots, (b) a knob
             touch mid-roll (after settle) still pausing it, and (c) a
             real front-panel save during a roll still pausing it.

             UPDATE 2026-08-11 (later) — Charlie's live test confirmed the
             first-edit pause works and confirmed (via testing on main)
             that this gap predates today's changes. Diagnosed by Charlie:
             once dirty flag is 1, a second edit after Resume produces no
             new CMD 0x03 broadcast (nothing to announce — flag already
             set, and only a save clears it), so the roller never
             re-paused on the second+ edit within a dirty session.
             FIXED: added maybePauseRollerOnEdit(), shared by CMD 0x03
             (first edit, dirty-flag transition) and CMD 0x11 (every
             discrete param-change broadcast, unconditional — catches
             every subsequent edit the dirty flag alone would swallow).
             Both share the same ROLLER_NAV_SETTLE_GUARD gate. NOT YET
             TESTED LIVE — needs confirmation that a second/third control
             touch after Resume now pauses the roll again.

             UPDATE 2026-08-11 (later still) — Charlie's report of a missed
             touch confirmed against session-2026-08-11-124328.log: a real
             drag on tone Middle (paramLo 0x0b, 60->69->71) at ~2s after a
             nav did NOT pause, because it landed inside the CMD 0x11
             trigger's own 2000ms settle guard — the same guard meant to
             stop false pauses ended up eating a real one. Confirmed from
             the same log that the hardware's settle process re-broadcasts
             every tone/amp paramLo TWICE with the identical value right
             after "Nav pull complete" — so a time window can't cleanly
             separate settle noise from a fast genuine touch, since both
             can land in the same few seconds.
             FIXED: CMD 0x11's trigger no longer uses a time guard at all.

             cleared in goToSlot, records the last value seen for each
             param since the current nav. First sighting of a paramLo this
             nav = settle baseline, not a pause. Any LATER value that
             differs from that baseline = the knob actually moved = pause,
             regardless of elapsed time. CMD 0x03's dirty-flag trigger is
             unchanged (still time-guarded) — its settle-noise broadcasts
             were confirmed to arrive within milliseconds of the recall
             every time, so a time guard is sufficient there specifically.
