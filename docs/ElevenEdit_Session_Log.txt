ELEVEN EDIT — SESSION LOG (append-only scratchpad)
===================================================================
Purpose: the ONE place provisional, unconfirmed, or in-progress findings
live during a work session. Newest entry on top. Safe to be messy and even
contradictory — nothing here is treated as truth until it is promoted.

TRUTH LIVES ELSEWHERE:
  ElevenEdit_Technical_Reference.txt — confirmed protocol/hardware facts
  ElevenEdit_Primer.txt              — project orientation & app state
Confirmed facts are EDITED IN PLACE in those two docs. This log is never a
substitute for them and is never superseded by a dated copy.

HOW AN ENTRY GRADUATES:
  1. Add findings here as you work (any state: idea, tried-X-got-Y, confirmed).
  2. When a finding is CONFIRMED, promote it: edit the value directly into the
     Technical Reference (or Primer), then mark the log entry [FOLDED IN].
  3. [FOLDED IN] entries can be deleted once the merge is verified. The log
     should trend back toward empty.

A FACT IS EITHER:
  - confirmed  -> lives in a main doc, edited in place, not here; or
  - provisional -> lives here.
Never both. Never a third dated file.

STATUS:      provisional — NOT YET TESTED LIVE
AREA:        Manual step nav (PCH>/PCH<, arrow keys) wrongly clamped to the
              Roll from/to range — patch-nav.js stepNav()
FINDING:     Live-tested follow-up to Stage 1 (factory patch nav): Charlie
              reported PCH> from Z4 landed on A1 (not a1), and PCH> from a4
              (reached via BNK>, confirmed correct — bank-step deliberately
              preserves slot-within-bank position across a bank change,
              not a bug) also landed on A1 instead of b1. ROOT CAUSE:
              stepNav (used by both the manual Prev/Next buttons/arrow
              keys AND shared, pre-dating today, by autoStep's timed
              auto-advance loop) wraps within getRangeFrom()/getRangeTo()
              — the Roll from/to pickers, which default to 0-103 (user
              only). That range exists to bound the TIMED auto-advance
              loop; manual single-stepping had no business sharing it, but
              did. So PCH> would silently snap back to A1 the instant you
              were anywhere the roll range didn't cover — including a4,
              reached validly via BNK>, which is outside the default
              range entirely.
FIX:          stepNav decoupled from the Roll from/to pickers — now wraps
              across the full 0-MAX_NAV_SLOT (207) range unconditionally,
              independent of whatever the roller's range is set to.
              autoStep/startAuto (the actual timed loop) are UNCHANGED and
              still respect the Roll from/to pickers exactly as before —
              that was always their correct job, just wrongly shared with
              manual stepping.
EVIDENCE:     JS-only diff, patch-nav.js stepNav(). Passes `node --check`.
              Version bumped 1.3.46 -> 1.3.47 (package.json). Diagnosis
              derived from Charlie's two reported cases (Z4->A1, a4->A1)
              both matching the shared-range-clamp math exactly; not yet
              re-tested live after the fix.
CONFLICTS:    none
NEXT:         NOT YET TESTED LIVE. Charlie to confirm PCH>/PCH< now cross
              Z4<->a1 and wrap z4<->A1 at the true ends, with auto-advance
              still respecting the Roll from/to range unchanged.

DATE:        2026-08-27
STATUS:      confirmed — TESTED LIVE
AREA:        Knob rendering — value-arc round-cap blob at tiny values
             (drawKnob, src/js/ui.js) — applies to EVERY knob, reported on
             FX LOOP Mix
FINDING:     Charlie reported a round dot sitting outside the knob's ring
             at very low values (e.g. FX Loop Mix at 1%), and that the dot
             disappears once the value hits exactly 0 (knob turns red at
             that point too, but the two are coincidental, not related).
             ROOT CAUSE: the value arc is stroked with lineWidth 5 and
             lineCap 'round'. At a small enough value, the swept angle is
             shorter than the cap's own width, so the two end-caps overlap
             almost entirely into a solid round blob instead of reading as
             a short line segment — and because a round cap bulges
             tangentially past its stroke's own endpoints, that blob can
             sit partly outside the ring's normal silhouette. At value127
             === 0 no arc is drawn at all (existing `if (value127 > 0)`
             guard), which is why the dot vanishes there — not because red
             fixes anything, just because nothing is drawn.
FIX:         drawKnob (ui.js ~line 67) now computes minSweepForRoundCap =
             5/(r-4) (the arc's own lineWidth as an angular width at this
             radius) and uses lineCap 'butt' instead of 'round' only when
             the swept angle is below that threshold; normal-sized arcs
             are unaffected and still get the polished rounded-cap look.
             Threshold is geometric (radius-relative), not a magic value
             count, so it should hold for any knob canvas size, not just
             FX Loop's.
EVIDENCE:    JS-only diff, src/js/ui.js drawKnob(). Not yet visually
             confirmed against a real drag to a low value on hardware.
             Version bumped 1.3.43 -> 1.3.44 (package.json).
