A FACT IS EITHER:
  - confirmed  -> lives in a main doc, edited in place, not here; or
  - provisional -> lives here.

DATE:        2026-07-20 (late)
STATUS:      [FOLDED IN: Technical Reference Sec 3, C11, Sec 24; code shipped]
AREA:        Bypass — Format B false positive when a block handle is 0x04
FINDING:     MOD bypass state was never stored — "state unknown yet" on every
             click. Bypass routing detected Format B by testing
             data[6] === 0x04, but a block's runtime handle CAN be 0x04 (MOD,
             in certain chain orders). A Format A message from that block was
             read as Format B, every field parsed one byte off, paramLo 0x01
             never matched, state never stored.
FIX:         Before treating data[6] === 0x04 as a Format B marker, check
             whether 0x04 is a live handle in currentChain. If it is, data[6]
             IS the handle and the message is Format A. Covers every block,
             not just MOD — WAH, DIST or any other would have failed the same
             way once its handle landed on 0x04.
TESTED:      Build confirmed 2026-07-20 — "Bypass: MOD -> ACTIVE" now appears
             in the log and the click toggles correctly.
LESSON:      Same failure mode as C1: treating a byte whose VALUE is 0x04 as a
             structural marker when 0x04 is also a legal datum. Third time this
             family of bug has cost us a day. When a constant doubles as data,
             the discriminator must come from context, never from the value.

STATUS:      [FOLDED IN: Technical Reference Sec 4, 24; code shipped]
AREA:        CMD 0x21 handler rewritten; amp handle was wrong on most patches
FINDING:     The old handler searched the chain map for a first byte of 0x07
             and took that triplet's handle as the amp, on the (documented,
             wrong) belief that field 1 was a type tag. Field 1 is a BACK-LINK
             carrying the PREVIOUS block's slot ID, and 0x07 is DIST's slot ID
             — so it actually found "the block after DIST". That coincides
             with the amp only when the amp immediately follows the
             distortion. Checked against 14 real patches: WRONG on 11.
             On those it addressed FX2, LOOP or REVERB instead, so every amp
             write (tone, gate, amp out, cab, mic, amp select) went to the
             wrong block, and incoming amp broadcasts were discarded by the
             instId guard as "not ours".
             Survived because the test patch set all had AMP after DIST.
FIX:         Handler now decodes back-links to recover slot IDs and stores the
             whole chain (position, slotId, name, modelId, handle) in
             currentChain. currentParamHi is derived from the block whose slot
             ID is 0x00. No call sites changed — currentParamHi keeps its name
             and meaning, it simply gets the right value now.
VERIFIED:    Decoder logic replayed over all 42 unique chain maps in the
             session logs: amp handle correct 42/42, all slots recognised.
AUDIT:       Other TFX decoders checked for the same fixed-position hazard.
             decodeAmpKey / tone / gate / ampOut anchor off a searched 6dls
             marker; decodeCabMicValues and decodeMonoStereo search by key —
             all safe. decodeToAmpVolumes uses fixed body offsets 52/60, which
             appear to be in the fixed global header rather than the variable
             keyed region, but this was NOT fully verifiable (decoded bulk body
             is not byte-identical to a saved TFX). Confirm when To Amp work
             resumes — note To Amp is already on the known-broken list.
TESTED:      Build test 2026-07-19 PASSED. session-2026-07-19-091431.log —
             8 chain maps, amp handle correct 8/8, all slots recognised, amp

DATE:        2026-07-19
STATUS:      provisional — deferred, not started
AREA:        Chain drag — live reorder preview (Avid's feel)
FINDING:     Our drag shows a thin insertion marker and only reorders on drop.
             Avid instead previews LIVE: as you drag, the blocks physically
             shift to make room, so the row continuously shows the result. That
             is the whole difference in feel Charlie noticed — it is deliberate
             and obvious rather than requiring attention to a small marker.
             THE FX LOOP HAS ITS OWN RULE. Observed: with the loop at position
             7, dragging it left made ALL SIX blocks before it move right in
             one step — i.e. the loop JUMPS to its next legal stop and the
             blocks in between shift as a group. It does not inch through
             illegal positions and get rejected. This matches the front-panel
             behaviour (scrolling steps the loop between its four stops,
             skipping everything between).
APPROACH:    Reorder the actual divs on dragover using a speculative order —
             the same move operation renderChainRow already performs, driven by
             a provisional order instead of the hardware's. Send that order on
             drop; redraw from currentChain on cancel. Remove the edge marker,
             since moving blocks are the indicator and both would be noise.
             Two rules needed: ordinary blocks shift one position at a time;
             FX Loop jumps between its four legal stops.
             BONUS: makes the loop's snap visible DURING the drag rather than
             surprising the user on release — it teaches the rule.
WATCH FOR:   During a drag we are showing a speculative order, so a broadcast
             arriving mid-drag (a move made in Avid, or a patch change) must
             not fight the preview.
OPEN:        Does AMP-CAB have a special rule too? Avid drags an adjacent loop
             along with the amp (Tech Ref Sec 4). And what triggers the loop's
             jump — cursor crossing a threshold, or distance dragged? The
             latter decides whether the preview feels responsive or twitchy.
NEXT:        Deferred by agreement 7/19. Current drag behaviour is correct and
             working; this is feel, not function. Revisit after the effect
             panel work.
