SESSION START — DO THIS BEFORE ANY WORK
--------------------------------------------------
(Rewritten 7/28/2026 — this project moved from upload-a-file-into-chat
sessions to Claude Code, which reads this git repo directly. Most of what
used to live here was about surviving that upload/paste-back cycle — a
chat only knew whatever copy it had been handed, and could silently hand
back something OLDER under the same filename. That whole class of risk is
gone: there is one working tree, every session reads it fresh, and every
edit is visible immediately via `git diff` and the commit history — not a
line count guessed after the fact. See the Archive for the old version of
this section and the incidents that shaped it; the lessons are still true
history, just no longer the operating procedure.)

  1. The repo IS the current state. No re-upload, no "which copy is this
     thread holding" — just read the files that are actually there.
  2. The one thing that DOES need checking at the start of a work session is
     git/branch state, per the repo's own branch instructions: is the
     previous work branch still unmerged (keep building on it) or already
     merged into main (restart it fresh from main, keep any unmerged work by
     rebasing it on top)? `git fetch origin main` +
     `git merge-base --is-ancestor <branch> origin/main` answers this in one
     step — do it before the first commit of a session, not after.
  3. REVIEW SESSIONS — ASK FOR CODE WHEN THE DOCS ALONE CANNOT SETTLE IT.
     A review compares documents against each other and cannot see the code
     unless it is actually read; being "in the repo" does not make a claim
     verified on its own. So doc-vs-code drift — a session that documents a
     fix but ships something slightly different — is invisible unless you go
     read the file. REQUEST/READ the specific file when:
       - a retraction lands and the withdrawn behaviour may still be in code
       - a named constant or formula is documented (settle times, dB anchors,
         zone arithmetic) and can be checked against the source in seconds
       - a symptom recurs after a documented fix — doc and binary disagree,
         and only the code decides
       - two docs describe one function differently, or a doc describes a
         behaviour without naming the mechanism
     WHERE TO LOOK: transport.js and protocol.js carry most protocol-critical
     claims (send builders, constants, lookup tables, decoders);
     sysex-handler.js for routing and format detection; ui.js for display
     formulas. Read one or two files, never the whole set reflexively.
     DO NOT read routinely just because you can. A well-scoped additive
     session does not need it, and reading files that don't inform the task
     costs context for no return. Expect to catch "the doc says 0.6 and the
     code says 0.61", not architectural problems.

HOW UPDATES WORK (read before adding any findings)
--------------------------------------------------
Three files, one direction of flow. Do NOT create new dated copies of any
reference doc to hold updates.

  ElevenEdit_Technical_Reference.txt  TRUTH — confirmed protocol/hardware facts
  ElevenEdit_Primer.txt (this file)   TRUTH — orientation & current app state
  ElevenEdit_Session_Log.txt          SCRATCH — provisional/in-progress findings
  ElevenEdit_Archive.txt              DRAIN — superseded history, never read
                                      during normal work

A fact is either confirmed (lives in a main doc, EDITED IN PLACE) or
provisional (lives in the session log). Never both, never a third dated file.
During a session, findings go to the SESSION LOG only — that is the whole
point of the log. Do NOT rewrite or regenerate the Technical Reference or the
Primer on every turn; the masters are the ledger, not the scratchpad, and each
full rewrite is a chance to drop a section or reorder something. Fold the log's
confirmed findings into the masters ONCE, at wrap (see FINALIZATION), editing
in place and marking each entry [FOLDED IN]. The log trends back toward empty;
the masters stay current without being touched mid-session. This is what
prevents the six-overlapping-documents problem.
  WHY THIS STILL MATTERS UNDER CLAUDE CODE (7/28/2026): the original reason
  for this split was that a chat session could only rewrite a master doc by
  having the whole thing pasted back, and a full rewrite risked silently
  dropping a section. Git removes that specific risk — every edit shows up
  in `git diff` before it's committed. But the split is worth keeping anyway,
  for a different reason: the Primer and Technical Reference are what a
  fresh session reads FIRST to get oriented, every single time. Folding a
  day's worth of provisional, still-shifting findings straight into them
  would make that orientation read longer and noisier for no benefit —
  better to let the log carry the day's mess and fold in only what turned
  out to matter, once, at wrap.
  ONE EXCEPTION — fold immediately, mid-session, only when a finding changes
  what the next step does: a retraction the next task would otherwise build on,
  or a hardware-safety item. Everything else waits for wrap.

THE ARCHIVE (added 7/21). Promoted log entries and superseded narrative move
to ElevenEdit_Archive.txt, one direction only — things go in, nothing comes
back out. You do not need it to work; the Primer and Technical Reference are
complete without it. Each block that moved left a one-line pointer behind.
  DO NOT ARCHIVE anything that stops a future session repeating work, however
  historical it reads: Section 20's dead ends, the retraction notes in Sec 6
  and Sec 23, any WITHDRAWN block quoted in place, and unresolved conflicts.
  Test: does it change what I would DO next? If it only explains WHY, it can
  be archived. If it would stop someone repeating a mistake, it stays.


FINALIZATION — HOW TO WRAP A SESSION (the method that has been working)
----------------------------------------------------------------------
This runs ONCE, when Charlie says to finalize/wrap — NOT every turn. During the
session the masters are left alone and findings accumulate in the log (see HOW
UPDATES WORK). Producing full Technical Reference / Primer files on every pass
is wasted effort and adds risk; wait for the wrap signal, then do this in order:
  1. FOLD IN. For each confirmed finding in the session log, edit the value
     directly into the Technical Reference (or this Primer) IN PLACE — new
     protocol facts into the relevant numbered section, plus a one-line entry
     in Tech Ref Sec 24 (Change Log). Never create a dated copy.
  2. MARK THE LOG. Change each folded entry's STATUS to
     "[FOLDED IN: <doc + section>]". Leave the entry in place (do not delete);
     the log trends toward empty over time, not in one wipe. Anything still
     provisional or unverified stays as-is with a clear NEXT.
  3. UPDATE PRIMER STATE. Bump the Status line and CURRENT APP STATE phase,
     move the shipped feature into WORKING, trim it from NOT YET IMPLEMENTED,
     and add its functions to the CODE FILE MAP.
  4. REVIEW THE DIFF. Run `git diff` (or check each Edit result) on every
     doc touched this session before committing. This is the current version
     of the old "line-count tell" — git shows exactly what changed, including
     an accidental deletion, instead of inferring one from a line count after
     the fact (see the 7/20 and 7/23 incidents in the Archive for why that
     check existed).
  5. COMMIT AND PUSH. Code and docs land in the SAME commit (or the same
     small batch of commits) on the session's working branch, then pushed —
     see the repo's own branch/git-workflow instructions for the exact
     commands and the merge-base check. Charlie tests the real build off
     that branch; once confirmed on real hardware, he merges it into main
     himself (or asks Claude Code to). There is no separate zip/fold-back
     step — the branch IS the consistent set, and it stays that way until
     Charlie says to merge.


WHAT THIS PROJECT IS
--------------------
Eleven Edit is a full patch editor and bank manager for the Avid Eleven Rack
guitar processor. It replaces the Avid editor entirely — no iLok, no Avid
software needed. Built on the confirmed Java-bridge architecture below.


HOW TO WORK WITH CHARLIE
------------------------
Non-developer, Pascal/Delphi background; no JavaScript, Electron, or Java.
He defines requirements, reviews mockups, tests builds, and reports what he
sees; he cannot write or debug code himself and won't fill in gaps.
  - Agree on the approach before writing any code. All decisions need his
    confirmation before implementation.
  - Be concise. Keep explanations outcome-focused, not technical.
  - Conclude internally; present the solution or finding, not the reasoning.
  - Always build the EXE for testing — npm start has never worked here.
  - THE TEST STEP, EXACTLY (Charlie's own words, 7/29/2026): after code is
    handed over, he runs `npm run build` (electron-builder --win --x64),
    executes the resulting EXE, and tests it live against the real hardware.
    There is no other test step and no way to shortcut it — "there is nothing
    to test when ElevenEdit can't communicate with hardware." Don't propose
    unit tests, mocked bridges, or "verify without hardware" steps as a
    substitute; they are not part of how this project gets verified.
  - CHARLIE ONLY TESTS ON REAL HARDWARE, ALWAYS (confirmed 7/28/2026). He
    builds this repo's code into an EXE and runs it against the real Eleven
    Rack over the Java bridge — there is no "dry run" step in his workflow.
    Without the bridge actually connected to hardware, essentially nothing
    is testable beyond the about box, the settings panel, and the window's
    close button; every other feature (chain row, effect panels, knobs,
    bypass, patch load/save, tuner, etc.) requires a live connection to
    produce any real signal to observe. So: a claim like "this needs testing
    without hardware to isolate X" doesn't fit how testing happens here —
    Charlie's confirmation IS the real-hardware test, not a step before it.
    Two specific mistakes to not repeat (both made 7/28/2026, same session):
    (1) treating in-conversation feedback ("good," "off," "almost there")
    as provisional/pending a future hardware test — it is NOT provisional,
    each round of feedback IS a fresh real-hardware test result, given live
    while he has the rebuilt EXE running against the rack. Don't sign off
    with "let me know how it feels once you test" after he has already just
    told you the result. (2) the app does not run ON the hardware — it runs
    on Charlie's PC/VM and REMOTE-CONTROLS the Eleven Rack over MIDI via the
    Java bridge. Get this distinction right when describing the setup.
  - Old eyes: amber-on-dark, readable fonts, generous sizing.
  - THE REPO IS CANONICAL, FULL STOP (updated 7/28/2026 — under Claude Code,
    not the old chat workflow). There is no separate "outputs" snapshot to
    fall out of sync with: every file read is the actual working tree, every
    edit lands in it directly, and `git status`/`git diff` show the true
    current state at any point mid-session. No re-copy risk to guard against.
  - TWO FAILED FIXES = STOP AND RE-DERIVE. If two consecutive changes produce
    no change in observed behaviour, the problem is a wrong assumption, not a
    wrong value. Go back to the raw evidence and re-derive from scratch rather
    than adjusting bytes. On 7/18 this rule would have saved roughly a dozen
    build cycles: every "fix" was a guess downstream of one unexamined
    assumption (that USB CIN framing bytes were payload data).
  - Update the session log in the SAME turn you present files, not later.
  - TEST READBACK WITH THE AVID EDITOR CLOSED. Our app adopts any broadcast on
    the wire, including ones triggered by the editor's own queries. With both
    running, features that never query anything can appear to work perfectly.
    This caused a false pass on 7/19 (per-block bypass). If a feature reads
    state from the hardware, it is not proven until it has run solo.
  - KNOB "JUMP TO CENTRE" — recurs every time a new knob type is added. When a
    knob sitting at value 0 is grabbed, it leaps to the middle on the first
    drag. Cause: reading the start value as `parseInt(dataset.value) || 64`,
    where a legitimate 0 is falsy and becomes 64. FIX (copy from the tone-knob
    drag, the known-good one): guard explicitly —
    `(dataset.value !== undefined && dataset.value !== '') ? parseInt(...) : 64`.
    Was present in DIST and REVERB panels; both fixed 7/22. Check for this
    pattern in any new knob before building.
  - A DISPLAY THAT CANNOT REACH A ROUND NUMBER IS A SCALE BUG, NOT DRIFT. Two
    readouts were quietly wrong for weeks because a 0-127 integer was stretched
    across a symmetric dB range, putting 0.0 dB between two integers where it
    could never be shown. One was even written off as "log-pot nonlinearity".
    Anchor any scale on its zero point. Same family: a write that asks for the
    bottom of a step, which is why Speed would not reach 10.0.
  - AN EDIT ANCHORED ON A LOOSE MARKER CAN SILENTLY DELETE A SECTION. Folding
    in on 7/23, "cut from C11 to the next C12" removed Sections 23 and 24 of
    the Technical Reference, because the FLAGGED CONFLICTS entries are not in
    numeric order and C12's header sits ABOVE C11's. Nothing looked wrong;
    only a manual line-count check caught it (this was before Claude Code —
    under it, `git diff` shows a deletion like this immediately, without
    having to think to check). Anchor on unique text and check the section
    headers survive either way.


CONFIRMED ARCHITECTURE (brief)
------------------------------
  ElevenRackBridge.jar (Java, javax.sound.midi) <-> ws://localhost:57121
  <-> Electron UI.
  IN  port: "Eleven Rack No details available" (Vendor Specific interface)
  OUT port: "Eleven Rack External MIDI Port"
  Java sees the Vendor Specific port that node-midi / Web MIDI cannot.
  App-visible SysEx is clean: F0 13 0B 0F [dir] [cmd] ... F7 (no 0x04 framing).
  Do NOT suggest Zadig, node-usb, node-midi, or Web MIDI — all confirmed dead
  ends (Technical Reference, Section 20). Full wire details: Technical
  Reference, Sections 1–2.

HARDWARE SAFETY
---------------
  Always back up patches before any SW-send testing session.
  CMD 0x37 (To Amp Source) is the project's most dangerous command. EVERY
    assert on it has BRICKED the rack and forced a full factory reset — three
    times across two non-consecutive days, all from 0x37 selects, never from
    0x36 volume. Patches survive only from backup. A CMD 0x3A query-first
    sequence avoided the assert in limited testing, but the feature never
    worked and why SW sends don't move the HW source is unknown, so the
    dropdowns stay removed. DO NOT send 0x37 until an observation-only capture
    explains the difference (see the To Amp Source investigation brief). This
    brick-on-assert behaviour is SPECIFIC to 0x37: asserts elsewhere
    (bad-patch-format while learning TFX, front-panel oddities) recovered with
    a nav-away-and-back and never needed a reset. See Tech Ref Sec 18.
  NEVER run the Avid Editor on Windows 11 — BSOD. It may be installed there
    for its graphics, but never launched (see GRAPHICS below).
  Never drive the Avid Editor and Eleven Edit at the same time. Several BSODs
    early in development; roughly the last week has been clean with both open
    but use ALTERNATING, never overlapping. The rule stands regardless.
  Factory reset (loses all patches): hold FX Loop + Mod + Reverb at power on,
    wait for the logo with no scroll bar, power off, then power on normally.
  After a firmware assert (MAudioFW...): power-cycle the hardware.

GRAPHICS — DESIGN DECISIONS (7/19, agreed but not yet implemented)
-------------------------------------------------------------------
  WHERE THE GRAPHICS LIVE (confirmed 7/21/2026). The pedal/amp/cab images are
  files in one folder:
      C:\Program Files\Avid\Eleven Rack Editor\System Plug-Ins
  They ship with the Avid Editor, but the Editor never has to RUN to use them —
  which is what makes graphics viable on Windows 11, where the Editor BSODs. It
  does not even need to stay installed once that folder is in hand. The app
  only reads the folder; it launches nothing. (This is the "skin" idea: dress
  the panels in the Avid pedal art. See the note under GRAPHICS below.)

  NEVER BUNDLE AVID'S ARTWORK. The app reads images from the user's existing
  Avid editor installation. The repo contains our mapping table and loader and
  none of Avid's assets — this keeps the project clean to open-source and
  avoids the question entirely rather than arguing it. Consequences:
    - path discovery, with a manual "point at your install" fallback
    - graphics are an ENHANCEMENT; the text-only UI stays the baseline and
      must look deliberate, not broken, for users without the editor installed
    - the loader fails quietly if Avid's file layout differs by version

  CHAIN ROW: pedal thumbnail ABOVE our existing text label — not instead of
  it. Avid's row has a tiny image with a tiny label and is hard to scan, which
  is the whole reason this app exists. Thumbnail plus our larger label beats
  either app alone. Keep the hover text too: it costs nothing and covers users
  without the graphics. Row grows from 62px to roughly 110px (BUILT 7/28, see
  WORKING: CHAIN ROW GRAPHICS-READY LAYOUT — currently dummy placeholders,
  real images are the next step below).

  7/28 UPDATES (folder handling + real data, ahead of actually loading images):
    SETTING RENAMED "Avid Editor Folder" -> "Avid Graphics Folder" (index.html,
    main.js) — reflects that this no longer needs to be a live Editor install.
    FOLDER DEPTH: do NOT require the user to pick an exact folder depth (not
    the Editor root specifically, not System Plug-Ins specifically). The
    loader (not yet built) should search recursively for the plugin image
    structure wherever it sits inside whatever folder is chosen. This is what
    makes "copy the folder off before uninstalling Avid on a Win11 box"
    actually work — a fixed-depth picker breaks the moment that copy gets
    reorganized even slightly, and Win11 users are exactly the ones most
    likely to only ever have a one-time copied-out folder, never a live
    install on that machine.
    REAL FOLDER LISTING obtained (Charlie, full recursive dir listing off a
    real install, 3934 lines / 3623 PNGs across 11 plugin folders: AmpsCabs,
    Delay, Distortion, Dynamics, EQ, FX Loop, Modulation, Reverb, Tuner,
    Volume, WAH). CONFIRMED FACTS from it:
      - Pedal thumbnails live at <Plugin>.aaxplugin\Contents\Resources\Images\
        <ModelName>.png (+ a same-named _sel.png — a plain generic amber
        rounded-rect outline, NOT a per-pedal custom asset, so it can likely
        just be a CSS border instead of another image dependency).
      - The Resources ROOT (sibling to Images\) holds only per-model GUI
        layout XML (<ModelName>GUI.xml) — not images. Easy to grab the wrong
        level if not checked; confirmed by directly inspecting the Distortion
        and Reverb folders.
      - Avid spells it "GreenJVCOD", not "GreenJRCOD" — a real naming quirk,
        consistent with the "MultiChorus spelled two ways" one already noted
        above.
      - AMP IMAGES ARE MANY-TO-ONE: only 17 amp_*.png files exist for 33
        documented amp models — several modeled amps share one thumbnail
        (same physical chassis, different channel/mode). The mapping table
        must account for this; it is not one row per amp model.
    MAPPING TABLE ARCHITECTURE (decided, not yet built): the MID->filename
    table itself is CODE DATA, not documentation — it belongs in its own
    dedicated JS file (like fx-transport.js/fx-panels.js), not pasted into
    any doc. The docs get a short pointer paragraph (this one) plus gotchas,
    never the raw table.

  EFFECT PANELS: pedal image in the panel HEADER only, for recognition, with
  real sliders and labelled values below — the way our amp panel already
  works. Do NOT make the pedal image the interactive surface: that is what
  forces Avid's small unlabelled knobs, and it would need a hand-positioned
  hitbox map for ~26 panels.

  Scope if built: ~27 distinct effect graphics (note the firmware spells
  MultiChorus two ways), ~34 amps, one cab. Key the lookup by MID, not by
  name — names contain slashes and inconsistent spellings that make bad
  filenames. Bypassed blocks dim via a CSS filter, no second image set.

QUERY BUDGET — READ THIS BEFORE ADDING BLOCK PANELS
-------------------------------------------------------------------
  Measured from Avid (7/23/2026), per patch recall: 11 bypass flags, one per
  block, PLUS 25 parameters for the AMP BLOCK ONLY. Avid queries NO parameters
  for MOD, DELAY or any other block on recall — only their bypass flags. It
  pulls the amp in full because the amp is the panel it shows.
  So our ~20 queries should NOT grow toward Avid's 47 as blocks are added.
  Fetch a block's parameters WHEN ITS PANEL OPENS, not on every nav — the
  distPanelOpen / reverbPanelOpen flags already point this way. Querying every
  block on every patch change adds permanent cost for values nobody is looking
  at, and would make us slower than Avid rather than faster.
