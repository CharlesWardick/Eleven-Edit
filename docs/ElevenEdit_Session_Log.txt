  - confirmed  -> lives in a main doc, edited in place, not here; or

DATE:        2026-08-29 (seventh round, same day)
STATUS:      provisional (code fix written, NOT YET TESTED LIVE)
AREA:        Post-save chain-map refresh missing a settle delay
             (sysex-handler.js isSave branch) + a real regression in the
             1.3.64 pacing fix (requestAllBypass/requestFxHostParams
             interleaving, transport.js/fx-transport.js)
FINDING:     Charlie ran his own controlled test: Save to Rack targeting a
             DIFFERENT slot (Z1) than the currently-loaded one, then FX1
             model changes — NO corruption, clean throughout. This isolates
             it precisely: only a SAME-slot save sets up the failure.
             Root cause found: handleSlotConfirm (CMD 0x02 handler) only
             runs its full, battle-tested resync (clearStaleReadoutsOnNav +
             requestPatchStateAfterNav, which always waits NAV_RECALL_SETTLE
             before querying anything) when the confirmed slot DIFFERS from
             currentSlot. A different-slot save trips that guard (real slot
             change) and gets the full, settled resync for free. A
             same-slot save never trips it — confirmed===currentSlot,
             guard skipped — leaving ONLY the isSave branch's own narrower
             "Post-save: re-reading chain map" REQU_CHAIN_MAP resend, which
             had NO settle delay before it at all, unlike every other
             post-commit/post-nav re-read in the app. If hardware hasn't
             finished reassigning handles yet when that resend goes out,
             the chain-map reply (and therefore currentChain) can be
             stale — and a subsequent FX-host model change builds its
             10-block chain-array write from that stale currentChain,
             embedding wrong handles for the other 9 blocks. Matches every
             observation: same-slot only, right after save only, breaks
             specifically at the model-change write.
             SEPARATELY: while re-reading this code, found the 1.3.64
             pacing fix has its own real bug — requestAllBypass and
             requestFxHostParams are both now async/paced, but nothing
             stops two from running AT THE SAME TIME if triggered around
             the same event; their individual awaited sends round-robin on
             the event loop and interleave on the wire (confirmed in
             Charlie's f5c82674 log, lines ~2447-2472 — a bypass query and
             an FX-host param query shuffled together mid-burst). Before
             1.3.64 each burst was atomic/synchronous, so this never
             happened; the pacing fix traded one hazard for a smaller,
             different one.
EVIDENCE:    be90309a-session20260829092822.log (different-slot save, Z1,
             clean) vs. the prior several same-slot-save logs (all showed
             the corruption or its precursor). f5c82674 log for the
             interleaving.
CONFLICTS:   none.
FIX APPLIED: (1) sysex-handler.js isSave branch — added
             `await sleep(NAV_RECALL_SETTLE)` before the post-save
             REQU_CHAIN_MAP resend, matching what requestPatchStateAfterNav
             already does for every other post-nav/post-recall re-read.
             (2) transport.js — added a small shared serialization queue
             (runPacedBurst/pacedBurstQueue) so paced bursts run one at a
             time instead of interleaving; requestAllBypass and
             requestFxHostParams (fx-transport.js) both now route through
             it (renamed to *Impl internally, public name unchanged, no
             call-site changes needed). Version bumped 1.3.64 -> 1.3.65.

             shorter than the cap's own width, so the two end-caps overlap
             almost entirely into a solid round blob instead of reading as
             a short line segment — and because a round cap bulges
             tangentially past its stroke's own endpoints, that blob can
             sit partly outside the ring's normal silhouette. At value127
             === 0 no arc is drawn at all (existing `if (value127 > 0)`
             guard), which is why the dot vanishes there — not because red
             fixes anything, just because nothing is drawn.
FIX:         drawKnob (ui.js ~line 67) now computes minSweepForRoundCap =
             5/(r-4) (the arc's own lineWidth as an angular width at this
             radius) and uses lineCap 'butt' instead of 'round' only when
             the swept angle is below that threshold; normal-sized arcs
             are unaffected and still get the polished rounded-cap look.
             Threshold is geometric (radius-relative), not a magic value
             count, so it should hold for any knob canvas size, not just
             FX Loop's.
