ELEVEN EDIT — SESSION LOG (append-only scratchpad)
===================================================================
Purpose: the ONE place provisional, unconfirmed, or in-progress findings
live during a work session. Newest entry on top. Safe to be messy and even
contradictory — nothing here is treated as truth until it is promoted.

TRUTH LIVES ELSEWHERE:
  ElevenEdit_Technical_Reference.txt — confirmed protocol/hardware facts
  ElevenEdit_Primer.txt              — project orientation & app state
Confirmed facts are EDITED IN PLACE in those two docs. This log is never a
substitute for them and is never superseded by a dated copy.

HOW AN ENTRY GRADUATES:
  1. Add findings here as you work (any state: idea, tried-X-got-Y, confirmed).
  2. When a finding is CONFIRMED, promote it: edit the value directly into the
     Technical Reference (or Primer), then mark the log entry [FOLDED IN].
  3. [FOLDED IN] entries can be deleted once the merge is verified. The log
     should trend back toward empty.

A FACT IS EITHER:
  - confirmed  -> lives in a main doc, edited in place, not here; or
  - provisional -> lives here.
Never both. Never a third dated file.

AREA:        Startup — chain row graphics sometimes blank on load
FINDING:     Long-standing intermittent bug (predates the 2026-08-02 startup
  gate; a 2026-07-31 pass added retry+logging but Charlie confirmed the
  symptom still recurs). ROOT CAUSE FOUND: the Avid-graphics auto-scan (and
  the retry loop around it) lived inside index.html's big INLINE <script>
  block (starts ~line 1574), which executes at HTML PARSE TIME — i.e.
  BEFORE the <script src="js/chain-graphics.js"> / js/ui.js tags further
  down the same file have even loaded. The scan is an async IPC round-trip
  (main.js walks the folder, replies); its .then() callback is a genuine
  RACE against those later <script> tags finishing load. If the scan
  resolved first, setAvidGraphicsManifest/renderChainRow didn't exist yet,
  the existing typeof guards silently no-op'd, and the manifest was simply
  never applied that session — timing-dependent, so it took many runs to
  reproduce, and the 2026-07-31 retry logic couldn't help because every
  retry re-runs the exact same race, not a different failure mode.
  FIX: the scan trigger is now exposed as window.startAvidGraphicsAutoScan
  (defined in the same inline-script closure, so runAvidGraphicsScan/
  safeAppLog are still reachable) but no longer auto-invoked there. Instead
  app-init.js's init() calls it — init() only ever runs after EVERY script
  has fully loaded (it's wired via a setTimeout(init, 150) at the bottom of
  app-init.js, the last file loaded), so the race is structurally gone, not
  just less likely. This lines up with Charlie's own suggestion ("scan
  right at the transition point of the loading screen going away") — init()
  IS that checkpoint; the manual Settings-panel Scan button is untouched
  (its handler already only runs after a user click, long after load, so it
  was never exposed to this race).
EVIDENCE:    root-caused directly from script tag order in index.html + the
  promise-based scan flow (unambiguous once traced to which script block
  the auto-scan actually lived in). node --check clean. NOT yet re-tested
  live — this is exactly the kind of intermittent bug that needs several
  cold-start runs to confirm gone, per the Primer's own "intermittent bugs
  need more than one clean pass" rule, not just one green run.
CONFLICTS:   none — additive/relocation only, no protocol or manifest-format
  change.
NEXT:        Charlie: several cold-start launches (not just one) with a
  graphics folder already configured, confirming the chain row shows real
  Avid art every time, before this is treated as fixed rather than just
  "less likely."

AREA:        Startup — second launch kills the running instance's bridge
FINDING:     Charlie noticed (may have existed before, only surfaced/noticed
  since the startup gate splash landed 2026-08-02): launching the EXE while
  it's already running shows a brief, barely-visible splash flash, then
  the ALREADY-RUNNING instance's Java bridge connection dies (Restart JB
  in the running instance fixes it, but shouldn't be needed — the second
  launch should just no-op / focus the existing window).
  ROOT CAUSE (main.js): the single-instance lock
  (app.requestSingleInstanceLock()) already existed, but the `if (!gotLock)`
  branch only called app.quit() — which merely SCHEDULES a quit, it does not
  stop the rest of the script executing synchronously. So a second launch
  still reached app.whenReady() -> launchBridge() ->
  killOrphanedBridgeProcesses() (a PowerShell sweep that force-kills any
  ElevenRackBridge.jar process — by design, to clean up a stale one left
  over from a crashed prior session) before the second instance's own
  app.quit() actually took effect — killing the FIRST, legitimately running
  instance's bridge in the process.
  FIX: added `return;` right after app.quit() in that branch, so a second
  launch bails out of the rest of main.js entirely — never reaches
  whenReady/launchBridge/window creation at all.
EVIDENCE:    code read and root-caused directly (killOrphanedBridgeProcesses'
  blanket kill-by-jar-name behavior is unambiguous); one-line fix, node
  --check clean. NOT yet re-tested live by Charlie (double-launch scenario).
CONFLICTS:   none — killOrphanedBridgeProcesses itself is intentional/correct
  behavior for its actual purpose (cleaning up a truly orphaned bridge from
  a crashed session); the bug was only that a second instance could reach it
  at all.
NEXT:        Charlie's live test: launch the EXE, then launch it again while
  the first is running and connected — confirm the second launch does

AREA:        Amp Controls — tone-knob drag/drop reorder + remember (UI)
FINDING:     New feature, agreed with Charlie before coding: the tone-stack
  knobs (up to 8 per amp, AMP_TONE_PARAMS) can be dragged into a user-
  preferred order, per amp, persisted across restarts. Design:
    - Drag handle is the knob's LABEL only (not the knob itself), reusing
      the chain row's mousedown/mousemove/mouseup + FLIP-slide technique
      (wireChainDrag) as the agreed reference implementation — adapted, not
      copied verbatim (see MECHANISM below for why).
    - Locked by default every launch (toneRowLocked, state.js — NOT
      persisted, a deliberate extra guard Charlie asked for on top of the
      label-only handle) — a small lock icon must be clicked to arm
      dragging. A reset icon clears just the current amp's saved order.
      Both docked to the right of the tone-knob row behind a divider
      (Charlie's call, after seeing a mock), no grip glyph on the labels
      (Charlie's call — undocumented detail, shifted label text off-center).
    - Order is loaded from settings.json (toneKnobOrder, keyed by ampKey ->
      array of paramLo) at app-init, BEFORE the first tone knob ever paints
      this session (same timing slot as the existing bank-cache load) — so
      a saved custom order is what's drawn on the very first render, never
      a default-order paint that then jumps to the preferred one. This was
      Charlie's explicit ask ("don't want to see them jump around").
  MECHANISM (why this isn't a literal chain-row copy): the chain row
  physically relocates real DOM nodes on reorder. The tone row's 8 slots
  (tone-k0..tone-k7) are fixed DOM elements that every OTHER tone-knob code
  path (drag/dblclick/wheel handlers, the live CMD 0x11 readback router in
  sysex-handler.js, updateToneReadouts) already addresses by fixed slot id,
  derived from a single new ordering function, getOrderedToneKnobs(ampKey)
  (protocol.js) — physically moving those divs would break every one of
  those id-based lookups. So a reorder here swaps CONTENT between fixed
  slots (paintToneSlots / repaintToneRowPreview, ui.js) instead of moving
  nodes, and the smooth "slide into place" feel is recreated on top of that
  with a FLIP animation keyed by paramLo (content identity) rather than by
  which DOM node moved (repaintToneRowAnimated) — same First/Last/Invert/
  Play idea as the chain row's applyChainOrderAnimated, different unit of
  identity. All existing tone-knob consumers were updated to route through
  getOrderedToneKnobs/toneSlotIndexForLo instead of the raw table filter,
  so drag/dblclick/wheel/live-readback/TFX-initial-readback can never
  disagree with each other or with what's painted on screen about which
  slot is which control.
  Files touched: state.js (toneKnobOrderPrefs, toneRowLocked), protocol.js
  (getOrderedToneKnobs, toneSlotIndexForLo, setToneKnobOrder,
  resetToneKnobOrder), ui.js (updateToneKnobs rewritten + ~340 new lines:
  paintToneSlots/repaintToneRowPreview/repaintToneRowAnimated/
  wireToneKnobDrag/lock+reset button wiring; updateToneReadouts and the
  tone knob drag/dblclick/wheel handlers updated to route by slot), sysex-
  handler.js (live CMD 0x11 tone router updated to route by slot, and
  skips repainting while a reorder drag preview is on screen — same
  "don't fight the live preview" guard the chain row uses), app-init.js
  (loads toneKnobOrder before initMIDI), main.js + preload.js (get/save-
  tone-knob-order IPC, same storeGet/storeSet pattern as bank cache/zoom).
EVIDENCE:    code written and read back this session; node --check clean on
  every touched .js file. NOT run against real hardware — per project rule,
  nothing here is "working" until Charlie builds the EXE and drags real
  knobs on a connected rack.
CONFLICTS:   none — additive. Does not touch AMP_TONE_PARAMS itself, the
  wire protocol, or any send/query mechanism.
NEXT:        Charlie's live test: drag-reorder several amps (incl. one with
  a toggle like Bright, one with Tremolo/Sync, one 3-knob and one 8-knob
  amp to exercise the flex-wrap case), confirm the saved order survives an
  app restart and a patch nav, confirm lock/reset behave, confirm no value
  flash/jump on amp change. If confirmed clean, fold into Primer
  WORKING/NOT YET IMPLEMENTED and Tech Ref Change Log at wrap.
  [UPDATE 2026-08-03, same day, after first live test] Charlie found a real
  bug: during a reorder drag, knobs that slid into a new slot (not the
  dragged one) turned red and their value/readout dropped toward 64/"--",
  even though no send happened and the watchdog never tripped (correctly
  read by Charlie as "display-only, not a HW issue"). ROOT CAUSE, two
  compounding bugs in repaintToneRowPreview (ui.js):
    (1) knobColor/drawKnob decide red-vs-amber by comparing live value
    against wrap.dataset.orig (baseline) — a property of the FIXED slot
    DOM node, not of the knob's content. The preview repaint moved VALUES
    between slots on reorder but left each slot's dataset.orig behind, so
    a knob landing in a new slot got compared against the PREVIOUS
    occupant's baseline (false red almost every time).
    (2) The dragged knob's own slot content was deliberately skipped each
    preview step (excludeLo) so its position could be driven by a separate
    continuous cursor-follow transform — but that left stale leftover
    value/text in that slot, and since the next step's snapshot trusted
    lo-bookkeeping over what was actually painted, that staleness could get
    attributed to the wrong knob and compound over a multi-slot drag,
    eventually surfacing as a knob showing 64/"--" though nothing was ever
    reset. FIX: repaintToneRowPreview now snapshots+carries dataset.orig
    alongside value/text on every slot swap, and no longer skips the
    dragged knob's own content (safe — its value isn't changing while its
    LABEL is what's being dragged; only repaintToneRowAnimated's FLIP
    transform still skips it, for position only, not content).
  STATUS: fix written, NOT yet re-tested live — needs Charlie's next build.
