ELEVEN EDIT — SESSION LOG (append-only scratchpad)
===================================================================
Purpose: the ONE place provisional, unconfirmed, or in-progress findings
live during a work session. Newest entry on top. Safe to be messy and even
contradictory — nothing here is treated as truth until it is promoted.

TRUTH LIVES ELSEWHERE:
  ElevenEdit_Technical_Reference.txt — confirmed protocol/hardware facts
  ElevenEdit_Primer.txt              — project orientation & app state
Confirmed facts are EDITED IN PLACE in those two docs. This log is never a
substitute for them and is never superseded by a dated copy.

HOW AN ENTRY GRADUATES:
  1. Add findings here as you work (any state: idea, tried-X-got-Y, confirmed).
  2. When a finding is CONFIRMED, promote it: edit the value directly into the
     Technical Reference (or Primer), then mark the log entry [FOLDED IN].
  3. [FOLDED IN] entries can be deleted once the merge is verified. The log
     should trend back toward empty.

A FACT IS EITHER:
  - confirmed  -> lives in a main doc, edited in place, not here; or
  - provisional -> lives here.
Never both. Never a third dated file.

BUILD 3 —
INTERLOCK
SOLVED:      Avid_Shark_Sync_Test.pcapng (Avid alone, Wireshark) settles the
             Sync/Speed interlock that has been open since 7/23 morning.
             1. THE OLD DIAGNOSIS WAS WRONG. Speed writes did not fail because
                sendParamWrite's trailing bytes were malformed. They failed
                because the rack IGNORES any Speed write while Sync is on a
                division. Avid sent ~40 Speed writes between t=95s and t=116s
                with v0 ranging 0x16-0x2D; the hardware echoed the SAME
                unchanged value (1F 7F 7F 7F 1F) back every single time. Avid
                never clears Sync first, so its own Speed knob is equally
                inert in that state — user confirmed visually before the
                capture was analysed.
             2. SYNC WRITE FORMAT CONFIRMED, and it is what we already emit.
                Avid picking OFF from its dropdown sends
                  00 11 <handle> 12 40 00 00 00 00
                and the rack echoes
                  02 11 <handle> 12 40 00 00 00 10
                That outgoing message is byte identical to
                sendParamWrite(0x12, 0).
             3. THE 0x10 IS A BROADCAST ARTEFACT. The final byte of every
                hardware broadcast is 0x10 higher than the corresponding
                write. Seen on both Sync and Speed. It is added by the rack on
                the way out and must NOT be included in writes. This retires
                the "trailing bytes are not understood" caveat in Sec 7 for
                these two controls.
             4. Speed's v1-v4 in broadcasts are genuine low-order bits of the
                same quantity, not a fixed signature: v0=0x00 appeared with
                both 00 00 00 10 and 7F 7F 7F 1F within one sweep, either side
                of centre. Display continues to use the single-byte decode,
                which is correct to the tenth (Finding 3).

BUILD 4 —
PRECISION
FIXES:       1. SPEED WOULD NOT REACH 10.0, settling back to 9.9. Cause: a CMD
                0x11 value is FIVE 7-bit bytes and v1..v4 are the LOW-ORDER
                bits, not padding. sendParamWrite always sent v0 + 00 00 00 00,
                i.e. the very BOTTOM of the requested step. Most controls are
                quantised to the byte and cannot tell; Speed carries real
                sub-step precision (v0=0x00 was seen with both 00 00 00 10 and
                7F 7F 7F 1F within one sweep) and reported exactly what it was
                asked for. Depth and Presence were checked and are clean,
                confirming this is a precision issue and not Speed-specific.
                FIX: endpoint sentinels, already documented in Sec 7 —
                  v127 >= 127  ->  3F 7F 7F 7F 0F
                  v127 <= 0    ->  40 00 00 00 00
                  otherwise    ->  v0 00 00 00 00  (unchanged)
                Writes carry 0F in the final byte where broadcasts carry 1F.
                Applied to ALL knobs by agreement: for controls already
                reaching 10.0 this asks for a value strictly closer to true
                maximum, so nothing visible changes.
             2. TO AMP 1/2 COULD NEVER DISPLAY 0.0 dB. The old scale,
                db = -12 + (v127/127)*24, puts zero at v127 = 63.5, which
                cannot exist — it showed +0.1 at 64 and -0.1 at 63.
                EVIDENCE, from existing logs, no new capture needed: with the
                rack reading 0.0 dB our log recorded
                  CMD 0x36 ToAmp1 volume: v0=0x00 (+0.1 dB)
                and v0=0x00 decodes to 64. So 64 is the hardware's 0 dB point.
                FIX: anchor at 64, with 64 steps below centre and 63 above, so
                all three anchors land exactly: 0 -> -12.0, 64 -> 0.0,
                127 -> +12.0. Also drops the '+' from a bare 0.0.
                LIKELY CLOSES the "Amp Out 0.2-0.4 dB midrange nonlinearity"
                in Sec 21: an offset scale is worst mid-range and vanishes at
                the ends, which is exactly the reported shape. It was never
                nonlinearity.
             3. AMP OUT — SAME DEFECT, NOW FIXED AND CONFIRMED.
                From session-2026-07-23-155947.log:
                  rack set to 0.0 dB  -> v127 = 98,  we showed +0.2
                  rack reading 4.8 dB -> v127 = 106, we showed +5.1
                106 is 8 steps above 98 and 4.8 / 8 = 0.6 exactly, so the step
                is 0.6 dB and the 0 dB anchor is v127 = 98.
                NEW: db = (v127 - 98) * 0.6.
                The old -60..+18 span implies 0.6142 per step, which would show
                4.9 where the rack shows 4.8 — so the documented range was
                rounded. Implied endpoints are now -58.8 dB at v127=0 and
                +17.4 dB at v127=127. WORTH A SPOT CHECK at both extremes; if
                either disagrees, the step is not exactly 0.6 and both anchors
                need re-deriving rather than nudging (see Primer, two-failed-
                fixes rule).
                Rig Vol (-24..0) and Gate Threshold (-90..-20) have no zero
                crossing and are unaffected.
                CONFIRMS the Sec 21 entry "Amp Out display has ~0.2-0.4 dB
                nonlinearity at midrange — likely log-pot response" was a
                MISDIAGNOSIS. There is no log-pot behaviour: the scale was
                linear all along, just anchored wrongly and with a step 2%
                too large. That entry should be deleted, not amended.
             4. FOCUS RING — TRIED AND REVERTED AT USER REQUEST. The ring left
                on dropdowns and buttons after a click is the browser's default
                focus indicator, not a deliberate "recently used" marker. It
                was briefly limited to keyboard focus (:focus-visible) with a
                blur() on the Sync dropdown. User asked for it back, so both
                the CSS and the blur calls were removed and the default
                behaviour restored. Recorded here only so the idea is not
                re-proposed as new: it was considered and declined, not missed.

FINDING 1 —
TREMOLO
ON/OFF:      paramLo 0x13 on the amp handle. This control exists ONLY on the
             hardware front panel: Avid's editor has no such toggle and the
             per-amp XML does not describe it. Encoding is identical to
             Bright — 127 = ON, 0 = OFF, seen on the wire as
               ON   3F 7F 7F 7F 1F
               OFF  40 00 00 00 10
             The tremolo set is therefore a contiguous paramLo block:
               0x10 Depth   0x11 Speed   0x12 Sync   0x13 On/Off
EVIDENCE:    session-2026-07-23-131306.log. Eight 0x13 events 13:13:35 to
             13:14:35 = the four on/off presses reported; four 0x0E events
             13:15:29 to 13:15:40 = the two Bright presses. Distinct
             parameters, correct counts, correct order.
FINDING 2 —
SYNC MAP:    Sync (0x12) is a continuous 0-127 value quantised into 14 zones:
             OFF plus 13 note divisions. Zone width 10; first and last zones
             truncated to 4 so the total is exactly 128.
               0-3 OFF | 4-13 div 1 | ... | 114-123 div 12 | 124-127 div 13
             Division order: whole note, then dotted / plain / triplet for
             half, quarter, eighth and sixteenth.
EVIDENCE:    Two front-panel sweeps at different tempos, which agree:
             at 120 BPM the Speed broadcast changed at decoded 64, 74, 84, 94,
             104, 114, 124 (zones 7-13); at 32.1 BPM only at 114 and 124
             (zones 12-13). Slower divisions fall below the Speed floor and
             read 0 — hardware behaviour, not a decode fault.
             ORDER CONFIRMED INDEPENDENTLY: a dotted note is slower than the
             triplet before it, so displayed Speed must dip at zones 8 and 11.
             It does — 1.3, 0.8, 2.5, 5.0, 4.2, 7.5 at 120 BPM.
FINDING 3 —
SPEED
DECODE:      Speed's displayed value is the STANDARD single-byte offset decode
             of v0. Verified on nine messages against the rack's own display:
             0x50 -> 1.3, 0x4A -> 0.8, 0x60 -> 2.5, 0x1F -> 7.5, all to the
             tenth. The 35-bit multi-byte formula in Tech Ref Sec 7 returns
             6.28, 5.87, 7.52 and 2.56 for those same messages and is WRONG
             for this control. The trailing bytes carry precision below the
             displayed step, not a different encoding.
CONFLICTS:   Tech Ref Sec 7 — the 35-bit formula must be scoped or corrected.
             Sec 11 — Sync is no longer an unimplemented 'selector'.
             Sec 21 / Primer — "Sync dropdown needs a valid-value capture" is
             now satisfied.
FINDING 4 —
C11 SETTLED: FORMAT B does not exist on this connection. Across ~20 replies in
             one session, byte 6 is always the block handle (0x04-0x0D,
             0x12-0x1B), never a fixed 0x04 marker, and every reply is 14
             bytes — handle, paramLo and five value bytes, with no room for an
             extra marker. Recommend deleting FORMAT B from Sec 3 and closing
             C11. The handler accepts both shapes, so nothing breaks either
             way.
FINDING 5 —
RIG TEMPO:   CMD 0x50, four payload bytes, broadcast on tempo change.
             INVERSELY related to BPM — the value traced a V while the tempo
             traced a peak, twice, matching two sweeps. NOT decoded: the value
             range spans a ratio of about 98 where 10-500 BPM spans 50, so it
             is not a simple reciprocal. A tempo change also triggered 753
             rebroadcasts of paramLo 0x02 on handle 0x17 and 0x04 on handle
             0x1A — tempo-synced parameters in other chain blocks.
             The startup reply F0 13 0B 0F 12 50 01 3A 04 20 F7 is byte
             identical across sessions at different tempos, so it is NOT the
             tempo value.
             NEXT: a two-minute calibration capture — set tempo to exactly
             60.0, 120.0, 240.0 and 32.1 with a pause at each. Four known

STATUS:      provisional — deferred, not started
AREA:        Chain drag — live reorder preview (Avid's feel)
FINDING:     Our drag shows a thin insertion marker and only reorders on drop.
             Avid instead previews LIVE: as you drag, the blocks physically
             shift to make room, so the row continuously shows the result. That
             is the whole difference in feel Charlie noticed — it is deliberate
             and obvious rather than requiring attention to a small marker.
             THE FX LOOP HAS ITS OWN RULE. Observed: with the loop at position
             7, dragging it left made ALL SIX blocks before it move right in
             one step — i.e. the loop JUMPS to its next legal stop and the
             blocks in between shift as a group. It does not inch through
             illegal positions and get rejected. This matches the front-panel
             behaviour (scrolling steps the loop between its four stops,
             skipping everything between).
APPROACH:    Reorder the actual divs on dragover using a speculative order —
             the same move operation renderChainRow already performs, driven by
             a provisional order instead of the hardware's. Send that order on
             drop; redraw from currentChain on cancel. Remove the edge marker,
             since moving blocks are the indicator and both would be noise.
             Two rules needed: ordinary blocks shift one position at a time;
             FX Loop jumps between its four legal stops.
             BONUS: makes the loop's snap visible DURING the drag rather than
             surprising the user on release — it teaches the rule.
WATCH FOR:   During a drag we are showing a speculative order, so a broadcast
             arriving mid-drag (a move made in Avid, or a patch change) must
             not fight the preview.
OPEN:        Does AMP-CAB have a special rule too? Avid drags an adjacent loop
             along with the amp (Tech Ref Sec 4). And what triggers the loop's
             jump — cursor crossing a threshold, or distance dragged? The
             latter decides whether the preview feels responsive or twitchy.
NEXT:        Deferred by agreement 7/19. Current drag behaviour is correct and
