  - confirmed  -> lives in a main doc, edited in place, not here; or
  - provisional -> lives here.

AREA:        Rig tempo — CMD 0x50 decode; chain-strip right-hand group
FINDING:     CMD 0x50 carries MICROSECONDS PER BEAT as a 24-bit number in four
             SIX-bit digits, most significant first:
               us = (d1<<18)|(d2<<12)|(d3<<6)|d4,  BPM = 60000000/us
             The 7/23 reading of this as a mysterious non-reciprocal inverse
             with a ~98:1 span was an artifact of assuming 7-bit bytes, which
             is what every other multi-byte value in this protocol uses. Every
             payload byte in the capture is below 0x40.
EVIDENCE:    Tempo_Settings.pcapng, six values keyed directly on the Avid
             editor. Decode is exact on all six with no rounding slack, and
             the encoder reproduces all six captured messages byte for byte:
               500.0 00 1D 13 00   60.0 03 34 09 00   120.0 01 3A 04 20
               240.0 00 3D 02 10   32.1 07 08 15 27    10.0 16 38 36 00

AREA:        Amp model change — tone stack values / per-slot parameter storage
FINDING:     Changing amp model in an open patch blanked every tone knob to
             "--" while the Avid editor kept showing values. True even
             between two models with an identical layout (92 Treadplate
             Vintage -> Modern).
             CAUSE: amp params are stored PER CHAIN SLOT and shared across
             models; the model only selects which paramLos are exposed and
             what they are called. The rack never cleared anything. Our
             setCurrentAmp -> updateToneKnobs blanked the knobs to 64/"--"
             and no code path ever re-read the block. Avid was not
             remembering values; it was re-reading.
EVIDENCE:    Four user tests against the Avid editor, no capture needed:
             (a) same-layout Vintage -> Modern still blanked in our app,
                 not in Avid;
             (b) Vintage -> Tweed -> Vintage returned all eight original
                 values intact, so the rack retains hidden values;
             (c) editing Tweed's "Tone" to 2.2 then returning to Vintage
                 showed Treble = 2.2, not the original 7.4 — proving one
                 stored value under two model-specific names;
             (d) Sync survived 65 AC Boost -> DC family;
             (e) cab type changes already preserved mic/axis/breakup — the
                 tell that one path in the app re-read and the other did not.
FIX:         On the 0x0F echo, when the amp key actually changes, wait
             AMP_CHANGE_SETTLE ms and re-query the amp block's paramLo set
             against the EXISTING handle. No chain map re-read: 0x0F is a
             parameter inside the block, not a CMD 0x21 model change, so the
             handle does not move. No mapping table, no knob-count
             reconciliation — the hardware is authoritative.
             transport.js: ampBlockParamLos() (Phase 3's list builder,
             extracted so the nav path and this path cannot drift),
             ampParamQuery(), requestAmpBlockParamsAfterAmpChange() with a
             sequence guard that cancels on a further amp change or a patch
             change mid-refresh.
             sysex-handler.js: 0x0F handler calls it. Fires for our dropdown,
             the rack's front panel and the Avid editor alike.
BUILD 1
DEFECT:      "PROMISE: paramQuery is not defined" on load. paramQuery() is a
             PRIVATE helper declared inside requestPatchStateAfterNav and was
             called from module scope. Fixed with a standalone ampParamQuery()
             rather than hoisting the original, because the nav version also
             increments the Dev timings query counter — reusing it would have
             polluted the nav timing figures with queries the nav pull never
             made. LESSON: check the SCOPE of a helper before reusing it, and
             check whether it has side effects beyond returning its value.
             This one had both problems.
TESTED:      Build 2 passed on hardware. Settle time 150 ms, then lowered to
             100 ms, both good.
CONFLICTS:   none. Nothing in the Technical Reference contradicted any of it;
             this is new ground, not a correction.
NEXT:        (1) AMP_CHANGE_SETTLE is a fixed guess about other machines —

AREA:        Chain drag — live reorder preview (Avid's feel)
FINDING:     Our drag shows a thin insertion marker and only reorders on drop.
             Avid instead previews LIVE: as you drag, the blocks physically
             shift to make room, so the row continuously shows the result. That
             is the whole difference in feel Charlie noticed — it is deliberate
             and obvious rather than requiring attention to a small marker.
             THE FX LOOP HAS ITS OWN RULE. Observed: with the loop at position
             7, dragging it left made ALL SIX blocks before it move right in
             one step — i.e. the loop JUMPS to its next legal stop and the
             blocks in between shift as a group. It does not inch through
             illegal positions and get rejected. This matches the front-panel
             behaviour (scrolling steps the loop between its four stops,
             skipping everything between).
APPROACH:    Reorder the actual divs on dragover using a speculative order —
             the same move operation renderChainRow already performs, driven by
             a provisional order instead of the hardware's. Send that order on
             drop; redraw from currentChain on cancel. Remove the edge marker,
             since moving blocks are the indicator and both would be noise.
             Two rules needed: ordinary blocks shift one position at a time;
             FX Loop jumps between its four legal stops.
             BONUS: makes the loop's snap visible DURING the drag rather than
             surprising the user on release — it teaches the rule.
WATCH FOR:   During a drag we are showing a speculative order, so a broadcast
             arriving mid-drag (a move made in Avid, or a patch change) must
             not fight the preview.
OPEN:        Does AMP-CAB have a special rule too? Avid drags an adjacent loop

  STATIC LEGALITY RULE — CONFIRMED, NO CODE CHANGE NEEDED. Charlie supplied a
  full 10x10 table of every legal AMP-CAB x LOOP position pair. Checked by
  hand against ui.js's existing legalLoopIndices()/enforceLoopPlacement()
  (computeReorder's insertion-index math: legal = {0, ampIndex, ampIndex+1,
  length}) for AMP-CAB at 1, 3, 5, 8, 9 and 10 — every row matched. Plain-
  English version of the invariant: LOOP is legal ONLY at position 1,
  position 10, or immediately adjacent to AMP-CAB (either side). That is
  already what the code enforces today. This was the part of the OPEN
  question below that turned out to already be correct.

  LIVE-DRAG "LINKED BLOCK" RULE — newly derived from Charlie's direct testing,
  NOT yet re-checked a second time, treat as strong-but-unconfirmed until
  implementation testing backs it up:
    1. Dragging AMP-CAB while LOOP sits immediately adjacent to it (either
       side, NOT already parked at position 1 or 10): LOOP moves WITH it,
       same direction, same distance, staying stuck on the same side — i.e.
       they behave as one linked "super block" while this holds.
    2. That linked pair stops when LOOP would be pushed past position 1 or
       10 — LOOP hits the physical end of the chain and the whole drag halts
       there (AMP-CAB ends up one-in from the end, LOOP AT the end).
    3. Once LOOP is parked at an end this way, grabbing AMP-CAB again lets it
       roam completely freely through every other slot — LOOP sitting at an
       end is legal regardless of AMP-CAB's position, so they un-link.
    4. Grabbing LOOP directly (AMP-CAB now fixed somewhere) only lets LOOP
       hop between whatever few slots are legal for that AMP-CAB position —
       this part is the EXISTING jump-between-legal-stops behaviour (see
       FINDING above), unchanged.
    5. Confirmed symmetric: works the same whichever side of AMP-CAB LOOP
       starts on (mirrors left/right), and the same whichever direction is
       dragged.
  So of the two things this entry originally flagged as open, only #1-3 above
  are actually new work — the jump-between-stops behaviour (#4) was already
  built. The net new piece is small: "when AMP-CAB moves and LOOP is touching
  it, move LOOP the same amount until LOOP hits an end."

  WHY THIS MATTERS ENOUGH TO FIX (Charlie's words, paraphrased): with the
  current drop-only reorder, you can't see what's about to move while
  dragging, and the missing linked-block behaviour makes some legal
  arrangements very hard or effectively impossible to land deliberately.

STATUS:      TWO REAL BUGS FOUND AND FIXED, verified live via simulated drag

AREA:        Chain drag — linked AMP-CAB+LOOP pair misbehaving under the new
             continuous-follow drag (previous entry)
FINDING:     Charlie, after confirming the plain continuous-follow drag was
             "pretty dang good": dragging the linked AMP-CAB+LOOP pair showed
             two distinct problems. (1) LOOP trailing "at least one block
             behind" AMP-CAB instead of staying close. (2) Dragging AMP
             toward the far end, LOOP would "shoot to slot 10 then back" —
             a real ricochet, repeated multiple times over a 4-position drag
             — though the pair always landed correctly by mouseup either way.
             Precise enough to diagnose directly from the description alone.
ROOT CAUSE 1 (the ricochet): computeLinkedAmpLoopReorder (ui.js) filters
             BOTH AMP and LOOP out of `rest` before searching for the hit-
             tested target's index. If elementFromPoint ever returned LOOP
             itself as the target — likely with continuous-follow, since
             LOOP (unlike the dragged AMP-CAB block) had no pointer-events:
             none and could genuinely be found under the cursor as AMP-CAB
             passed near/over it — `rest.findIndex` for SLOT_LOOP always
             returned -1 (LOOP isn't IN rest), and the old fallback
             (`idx = rest.length`) parked the whole pair at the very end.
             That IS the "shoot to slot 10" — a real logic bug, not a timing/
             animation artifact.
ROOT CAUSE 2 (the lag): LOOP had no special handling at all in the new
             continuous-follow code (previous entry) — it was just another
             "other block" getting applyChainOrderAnimated's FLIP slide-in,
             now running at Charlie's own CHAIN_SLIDE_MS=1000. Since a real
             drag re-triggers a reorder far more often than once per second,
             LOOP's slide could never fully catch up before the next one
             restarted it, so it visually lagged behind AMP-CAB instead of
             looking glued to it.
FIX 1:       computeLinkedAmpLoopReorder: idx < 0 (target not found in rest,
             meaning the hit-test landed on AMP or LOOP itself) now returns
             `src` unchanged — a no-op, matching how the plain single-block
             path already handles targeting yourself — instead of jumping to
             the end.
FIX 2:       New state var chainDragLinkedCont, set at drag-start alongside
             chainDragCont whenever linkedAmpLoopInfo confirms this is a
             linked drag. It gets the SAME pointer-events:none + transition:
             none treatment as the dragged block, is excluded from
             applyChainOrderAnimated's mover list (which now takes an array
             of exclusions, not just one), and — critically — receives the
             EXACT SAME translateX delta as chainDragCont every frame,
             rather than computing its own. Since LOOP's natural DOM position
             is always kept immediately adjacent to AMP-CAB's by
             computeLinkedAmpLoopReorder, applying an identical shift to both
             preserves their gap exactly, giving true lockstep movement.
VERIFIED:    Live CDP drag simulation across all four combinations (LOOP
             before/after AMP-CAB, dragging left/right), 8-10 steps each,
             measuring the gap between the two blocks' rendered rects at
             EVERY step: the gap was PERFECTLY CONSTANT (86px or 111px

             tests, with the reorder sequence progressing cleanly block-by-
             block and no ricochet observed at any point. Also caught and

             bug — turned out to be a pure test artifact (60 mousemoves fired
             with zero real elapsed time between them, so FX1's 1000ms
             slide-out animation never got a chance to render a frame).
             Redone with real ~50ms delays between steps confirmed clean,
             non-overlapping layout once actual time is allowed to pass —
             worth remembering for any future drag verification: a tight
             synchronous event-firing loop does not represent real drag
             timing for anything that depends on CSS transitions.

1a — CC DIRTY CATEGORIZATION (SAVE-green-on-startup fix). DONE.
  Root cause (found 7/26, confirmed in current code): sendCC routes through
  sendPatchWrite, so EVERY CC marked the patch dirty. The startup "forced Guitar
  input" (sendCC(65,0), app-init.js ~1200 ms after launch) therefore lit SAVE
  green after the nav's dirty-clear.
  Fix: sendCC now marks dirty only for PER_PATCH_CCS = [17] (Rig Volume). Input
  (CC 65/66/67) and Tuner (CC 69) use plain sendHex → never dirty. Also fixes the
  latent "changing input or tuner lights SAVE" issue.
  CONFIRMED (Charlie): input select is a GLOBAL hardware setting, not per-patch —
  it never changes with patch and only when the user changes input. So it does
  not belong to the patch and must not dirty it.

1b — RETIRE FORCED A1 ON FIRST CONNECT (reflect current patch, Avid-like). DONE.
  Was: first connect forced goToSlot(0) (recall to A1) "for a predictable state"
  — legacy from the pre-Java-bridge era. Reconnect already reflected the current
  patch. Now first connect does too: it sets currentSlot = -1 then calls
  requestFullState(); the REQU_CURR_RIG reply (CMD 0x02 handler) sets the real
  slot and runs clearStaleReadoutsOnNav + requestPatchStateAfterNav for us.
  DETOUR/why currentSlot=-1: currentSlot inits to 0 (state.js), and the CMD 0x02
  handler only pulls when the confirmed slot DIFFERS from currentSlot — so if the
  rack sat on A1 (slot 0) it would not have pulled. Forcing -1 guarantees the
  confirmation registers as a change and the pull fires, wherever the rack is.
  No recall is sent, so the rack is left where the user had it.

2 — PHANTOM RED ON SAVE (the 3 order-dependent red knobs). DONE.
  Root cause (found 7/26): the TFX body stores knobs as high-res int32; the live
  CMD 0x11 protocol carries them as coarse 0-127. On save/capture the body was
  re-decoded (gateRawToV127) and REPAINTED over the already-live knobs; for knobs
  whose stored value straddles a rounding boundary the body value lands one unit
  off the live one. Values are NOT wrong (inaudible ~0.08 diff) — our
  pixel-perfect red just flags the variance. Save-to-Rack re-anchored the
  baseline (flash then amber); Save-to-Disk did not (stayed red). Different amps
  show a different set of knobs (Tweed Bass: Amp Out/Treble/Vol Bright;
  82 Lead 800: Gate Thresh/Presence/Treble) — same single cause.
  Fix: in BOTH save/capture branches (sysex-handler.js), keep amp-ID + discrete
  controls (cab/mic, mono) but do NOT repaint the continuous red-tracked knobs
  (gate, amp out, tone, To-Amp vols) from the body — they already show the live
  value. Gated behind REQUEST_BULK_ON_NAV so the legacy bulk-on-nav mode, where
  nothing live-populated them, still repaints. Baseline and display now both come
  from the live 0-127, so the rounding gap cannot surface. Keeps pixel-perfect
  red intact (no tolerance introduced).

1c — REFLECT LAST INPUT / STOP FORCING GUITAR. DEFERRED (Charlie's call).
  Not needed to fix startup-green (1a already does) and independent of 1b/2.
  Left as-is: app still forces Guitar on connect. Because input is GLOBAL, the
  right future design is NOT "read input from patch body" (a stale snapshot) but
  "stop forcing, reflect the live global input" — belongs in a future global-HW-
  settings area. There is no REQU to poll input; the CMD 0x3D broadcast handler
  (sysex-handler ~469) already sets the buttons when the rack volunteers input,
  but the rack does not announce it on patch recall. Revisit with item B / a
  global-settings panel.
