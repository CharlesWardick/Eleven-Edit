WHAT THIS PROJECT IS
--------------------
Eleven Edit is a full patch editor and bank manager for the Avid Eleven Rack
guitar processor. It replaces the Avid editor entirely — no iLok, no Avid
software needed. Built on the confirmed Java-bridge architecture below.


HOW TO WORK WITH CHARLIE
------------------------
Non-developer, Pascal/Delphi background; no JavaScript, Electron, or Java.
He defines requirements, reviews mockups, tests builds, and reports what he
sees; he cannot write or debug code himself and won't fill in gaps.
  - Agree on the approach before writing any code. All decisions need his
    confirmation before implementation.
  - Be concise. Keep explanations outcome-focused, not technical.
  - Conclude internally; present the solution or finding, not the reasoning.
  - Always build the EXE for testing — npm start has never worked here.
  - Old eyes: amber-on-dark, readable fonts, generous sizing.
  - THE OUTPUTS FOLDER IS CANONICAL DURING A SESSION. Project files are read
    ONCE at the start; after that, always base edits on the files you last
    presented, never re-copy from the project mid-session or you will silently
    revert earlier fixes. Charlie folds the final outputs back into the project
    at end of day.
  - TWO FAILED FIXES = STOP AND RE-DERIVE. If two consecutive changes produce
    no change in observed behaviour, the problem is a wrong assumption, not a
    wrong value. Go back to the raw evidence and re-derive from scratch rather
    than adjusting bytes. On 7/18 this rule would have saved roughly a dozen
    build cycles: every "fix" was a guess downstream of one unexamined
    assumption (that USB CIN framing bytes were payload data).
  - Update the session log in the SAME turn you present files, not later.
  - TEST READBACK WITH THE AVID EDITOR CLOSED. Our app adopts any broadcast on
    the wire, including ones triggered by the editor's own queries. With both
    running, features that never query anything can appear to work perfectly.
    This caused a false pass on 7/19 (per-block bypass). If a feature reads
    state from the hardware, it is not proven until it has run solo.
  - KNOB "JUMP TO CENTRE" — recurs every time a new knob type is added. When a
    knob sitting at value 0 is grabbed, it leaps to the middle on the first
    drag. Cause: reading the start value as `parseInt(dataset.value) || 64`,
    where a legitimate 0 is falsy and becomes 64. FIX (copy from the tone-knob
    drag, the known-good one): guard explicitly —
    `(dataset.value !== undefined && dataset.value !== '') ? parseInt(...) : 64`.
    Was present in DIST and REVERB panels; both fixed 7/22. Check for this
    pattern in any new knob before building.
  - A DISPLAY THAT CANNOT REACH A ROUND NUMBER IS A SCALE BUG, NOT DRIFT. Two
    readouts were quietly wrong for weeks because a 0-127 integer was stretched
    across a symmetric dB range, putting 0.0 dB between two integers where it
    could never be shown. One was even written off as "log-pot nonlinearity".
    Anchor any scale on its zero point. Same family: a write that asks for the
    bottom of a step, which is why Speed would not reach 10.0.
  - AN EDIT ANCHORED ON A LOOSE MARKER CAN SILENTLY DELETE A SECTION. Folding
    in on 7/23, "cut from C11 to the next C12" removed Sections 23 and 24 of
    the Technical Reference, because the FLAGGED CONFLICTS entries are not in
    numeric order and C12's header sits ABOVE C11's. Nothing looked wrong; the
    line-count tell caught it. Anchor on unique text and check the section
    headers survive.


CONFIRMED ARCHITECTURE (brief)
------------------------------
  ElevenRackBridge.jar (Java, javax.sound.midi) <-> ws://localhost:57121
  <-> Electron UI.
  IN  port: "Eleven Rack No details available" (Vendor Specific interface)
  OUT port: "Eleven Rack External MIDI Port"
  Java sees the Vendor Specific port that node-midi / Web MIDI cannot.
  App-visible SysEx is clean: F0 13 0B 0F [dir] [cmd] ... F7 (no 0x04 framing).
  Do NOT suggest Zadig, node-usb, node-midi, or Web MIDI — all confirmed dead
  ends (Technical Reference, Section 20). Full wire details: Technical
  Reference, Sections 1–2.

HARDWARE SAFETY
---------------
  Always back up patches before any SW-send testing session.
  CMD 0x37 (To Amp Source) must ALWAYS be preceded by a CMD 0x3A query for
    that slot. Sent unqueried it caused a firmware hang and factory reset
    (all patches lost) on 7/14. With the query first the sequence is safe and
    asserts no longer occur — but the GUI dropdowns stay removed because SW
    sends still do not move the HW source. See Tech Ref Sec 18.
  NEVER run the Avid Editor on Windows 11 — BSOD. It may be installed there
    for its graphics, but never launched (see GRAPHICS below).
  Never drive the Avid Editor and Eleven Edit at the same time. Several BSODs
    early in development; roughly the last week has been clean with both open
    but use ALTERNATING, never overlapping. The rule stands regardless.
  Factory reset (loses all patches): hold FX Loop + Mod + Reverb at power on,
    wait for the logo with no scroll bar, power off, then power on normally.
  After a firmware assert (MAudioFW...): power-cycle the hardware.

GRAPHICS — DESIGN DECISIONS (7/19, agreed but not yet implemented)
-------------------------------------------------------------------
  WHERE THE GRAPHICS LIVE (confirmed 7/21/2026). The pedal/amp/cab images are
  files in one folder:
      C:\Program Files\Avid\Eleven Rack Editor\System Plug-Ins
  They ship with the Avid Editor, but the Editor never has to RUN to use them —
  which is what makes graphics viable on Windows 11, where the Editor BSODs. It
  does not even need to stay installed once that folder is in hand. The app
  only reads the folder; it launches nothing. (This is the "skin" idea: dress
  the panels in the Avid pedal art. See the note under GRAPHICS below.)

  NEVER BUNDLE AVID'S ARTWORK. The app reads images from the user's existing
  Avid editor installation. The repo contains our mapping table and loader and
  none of Avid's assets — this keeps the project clean to open-source and
  avoids the question entirely rather than arguing it. Consequences:
    - path discovery, with a manual "point at your install" fallback
    - graphics are an ENHANCEMENT; the text-only UI stays the baseline and
      must look deliberate, not broken, for users without the editor installed
    - the loader fails quietly if Avid's file layout differs by version

  CHAIN ROW: pedal thumbnail ABOVE our existing text label — not instead of
  it. Avid's row has a tiny image with a tiny label and is hard to scan, which
  is the whole reason this app exists. Thumbnail plus our larger label beats
  either app alone. Keep the hover text too: it costs nothing and covers users
  without the graphics. Row grows from 62px to roughly 110px.

  EFFECT PANELS: pedal image in the panel HEADER only, for recognition, with
  real sliders and labelled values below — the way our amp panel already
  works. Do NOT make the pedal image the interactive surface: that is what
  forces Avid's small unlabelled knobs, and it would need a hand-positioned
  hitbox map for ~26 panels.

  Scope if built: ~27 distinct effect graphics (note the firmware spells
  MultiChorus two ways), ~34 amps, one cab. Key the lookup by MID, not by
  name — names contain slashes and inconsistent spellings that make bad
  filenames. Bypassed blocks dim via a CSS filter, no second image set.


NEXT SESSION — RIG TEMPO CONTROL
-------------------------------------------------------------------
  Identified 7/23 as CMD 0x50, four payload bytes, broadcast on every tempo
  change and INVERSELY related to BPM. Not finished: the value range spans a
  ratio of about 98 where 10-500 BPM spans 50, so it is not a plain reciprocal.
  ONE SHORT CAPTURE FINISHES IT: with our app running, set the rack tempo to
  exactly 60.0, 120.0, 240.0 and 32.1, pausing at each. Four known points
  against four broadcast values pin the formula.
  UI: a clock-style spinner near the STEREO badge — arrows to step, click the
  decimal to edit it, accepts typed entry. Rig level, not the amp panel.
  Motivation: reaching tempo on the rack's front panel is tedious.
  Full detail: Technical Reference Sec 21.

QUERY BUDGET — READ THIS BEFORE ADDING BLOCK PANELS
-------------------------------------------------------------------
  Measured from Avid (7/23/2026), per patch recall: 11 bypass flags, one per
  block, PLUS 25 parameters for the AMP BLOCK ONLY. Avid queries NO parameters
  for MOD, DELAY or any other block on recall — only their bypass flags. It
  pulls the amp in full because the amp is the panel it shows.
  So our ~20 queries should NOT grow toward Avid's 47 as blocks are added.
  Fetch a block's parameters WHEN ITS PANEL OPENS, not on every nav — the
  distPanelOpen / reverbPanelOpen flags already point this way. Querying every
  block on every patch change adds permanent cost for values nobody is looking
  at, and would make us slower than Avid rather than faster.

  RECOMMENDED ORDER (by capture simplicity):
