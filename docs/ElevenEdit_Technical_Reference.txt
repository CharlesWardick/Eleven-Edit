1. ARCHITECTURE & TRANSPORT
===================================================================

CONFIRMED WORKING ARCHITECTURE (supersedes all earlier transport designs):

  ElevenRackBridge.jar  <->  ws://localhost:57121  <->  Electron UI
         |
   javax.sound.midi
         |
   Eleven Rack USB
     IN:  "Eleven Rack No details available"  (Vendor Specific interface)
     OUT: "Eleven Rack External MIDI Port"    (standard MIDI interface)

WHY JAVA: The Eleven Rack's "Vendor Specific" USB interface carries all
SysEx traffic. Java's javax.sound.midi sees ALL Windows MIDI ports,
including the "No details available" Vendor Specific port. node-midi,
Web MIDI, and MIDI-OX see only 3 standard ports and miss it. Confirmed by
direct testing. ElevenHack (2013) uses this same javax.sound.midi approach.

PORT AUTO-DETECT (case-insensitive):
  IN  = name contains "Eleven" AND "No detail"
  OUT = name contains "Eleven" AND "External"
Typical Windows enumeration: IN=port 7, OUT=port 5 (do not hardcode indices;
match by name).

BRIDGE PROTOCOL (JSON over WebSocket):
  CLIENT -> BRIDGE: {"cmd":"connect","inPort":7,"outPort":5}
                    {"cmd":"send","hex":"F0 13 0B 0F 01 01 F7"}
  BRIDGE -> CLIENT: {"type":"midi_in","hex":"F0 13...","bytes":[...]}
  First byte auto-detects SysEx (0xF0) vs short message (CC/PC).
  Shutdown: write "SHUTDOWN\n" to bridge stdin. A forceful kill
  (taskkill /F) skips JVM shutdown hooks on Windows and can leave orphan
  processes.

FRAMING — IMPORTANT: On this MIDI-layer path the app sees clean SysEx:
  F0 13 0B 0F [dir] [cmd] ... F7  — pure 7-bit, NO 0x04 framing.
  The 0x04 device-address byte and the "0x04 per 3 bytes" framing described
  in old raw-USB (node-usb / Wireshark) research apply ONLY to the raw
  Vendor Specific endpoint. javax.sound.midi handles that layer for us.
  Never insert or strip 0x04 framing in application code. (See Section 22
  conflict C1 for how this reconciles the two research eras.)

ENVIRONMENT:
  Electron ^25.0.0, build with electron-builder --win --x64.
  No node-midi, no electron-rebuild, no node-usb dependency.
  npm start has never worked in this environment — always build the EXE.
  Java: bridge source is Java 8 compatible (compile --release 8).
  Compiled under JDK 25; JDK 21 was used earlier and the --release 8 target
  makes the compiler version largely immaterial. Runtimes verified: 21, 25, 26.

PLATFORM MATRIX (consolidated 7/21/2026 — supersedes all earlier scattered
Windows notes). Avid USB driver v1.1.12 throughout.

===================================================================
2. SYSEX WIRE FORMAT
===================================================================

All messages:  F0 13 0B 0F [dir] [cmd] [data...] F7
  Manufacturer ID: 0x13 0x0B (Avid/Digidesign)
  Device ID:       0x0F  (0x0E occasionally noted in ElevenHack source)

DIRECTION BYTE:
  0x00 = SNDSET  — we write/command to hardware
  0x01 = REQU    — we request data from hardware
  0x02 = ASYNC   — hardware sends an unsolicited state update
  0x12 = RESPOND — hardware responds to one of our REQU queries

REQU LENGTH (confirmed 7/9, 18 commands in real Avid traffic):
  Every bare REQU is exactly 7 bytes: F0 13 0B 0F 01 [cmd] F7. No trailing
  bytes. (CMD 0x11 REQU is the exception: it carries paramLo — see Sec 3.)

RESP vs ASYNC PAYLOAD OFFSET (confirmed 7/9):
  RESP to our own REQU (dir=0x12) has NO slot byte; payload starts at
  byte 6. An ASYNC broadcast (dir=0x02, e.g. hardware save) has a slot byte
  at position 6; payload starts at position 7. This offset difference is
  handled by the SEND_PATCH decode path.

*** USB-MIDI FRAMING — READ BEFORE DERIVING ANY FORMAT FROM A CAPTURE ***
  (confirmed 7/18, after a full day lost to this)
  A raw USB capture of the Avid editor is NOT the message. USB-MIDI packs
  SysEx into 4-byte groups, each led by a Code Index Number (CIN) framing
  byte. Those framing bytes are transport, not data, and our Java bridge
  strips them. Regroup every capture in fours before reading it:

    f0 13 0b 04 0f 00 0d 06 00 f7
      -> [04] f0 13 0b | [04] 0f 00 0d | [06] 00 f7
      -> actual message: F0 13 0B 0F 00 0D 00 F7   (8 bytes, not 10)

  Common CINs: 0x04 = SysEx starts/continues (3 data bytes follow),
  0x05/0x06/0x07 = SysEx ends with 1/2/3 data bytes. The SAME framing byte
  appears at different offsets in different captures depending on payload
  length, which makes it look like a meaningful per-command value. It is not.

  SANITY CHECK: a send and its matching broadcast should be the same shape.
  If your derived send format is longer than the hardware's own broadcast of
  the same command, you have almost certainly kept a framing byte.


===================================================================
3. CMD 0x11 — LIVE PARAMETER READ/WRITE
===================================================================

The single most important command. Reads/writes any parameter on the amp
block in real time. TWO receive formats + one send format (resolved 7/16).

FORMAT A — ASYNC broadcast (hardware -> us, spontaneous):
  F0 13 0B 0F [dir] 11 [currentParamHi] [paramLo] [v0] 00 00 00 00 F7
    data[6]=currentParamHi, data[7]=paramLo, data[8]=v0
  Fires when: any parameter changes from any source (HW knob turned, or the
  hardware echoing a value we just sent). Used for tone knobs, gate, amp out,
  amp select, cab/mic/axis/breakup live updates, bypass changes.

FORMAT B — RESP to our explicit REQU:
  F0 13 0B 0F 12 11 04 [currentParamHi] [paramLo] [v0] 00 00 00 00 F7
    data[6]=0x04 (fixed), data[7]=currentParamHi, data[8]=paramLo, data[9]=v0
  Fires when: we send a REQU query for a specific parameter.
  NOTE: This 0x04 at data[6] is REAL SysEx content, not USB framing. Earlier
  research confused it with the USB 0x04 framing byte (see C1).
  See C11 — not every REQU response arrives in this shape.

  *** FORMAT A / FORMAT B DISAMBIGUATION — CONFIRMED BUG, FIXED 2026-07-20 ***
  data[6]===0x04 is NOT a reliable Format B marker. A block's runtime handle
  can itself BE 0x04 (observed on MOD in certain chain orders), and a Format A
  message from that block also has data[6]=0x04. The two are indistinguishable
  from that byte alone.
    DETECTION RULE: before treating data[6]===0x04 as a Format B marker, check
    whether 0x04 exists as a live handle in currentChain. If it does, data[6]
    IS the handle and the message is FORMAT A. Only if no block in the current
    chain holds handle 0x04 may it be read as Format B.
    SYMPTOM IF WRONG: bytes parse one position off, paramLo never matches, and
    any block whose handle lands on 0x04 reports "state unknown yet" forever.
    First hit MOD; would equally have hit WAH, DIST or any other block.
    Fix lives in the sysex-handler.js bypass routing block.
  This is a second instance of the same failure mode as C1: treating a byte
  whose VALUE is 0x04 as a structural marker, when 0x04 is also a legal datum.

SEND (our app -> hardware):
  F0 13 0B 0F 00 11 [currentParamHi] [paramLo] [v0] 00 00 00 00 F7
  Hardware accepts Format A (no 0x04) for ALL params including cab/mic, then
  echoes back as Format A ASYNC. v1–v4 = 0x00 confirmed for all writes.

REQU (query one parameter):
  F0 13 0B 0F 01 11 [handle] [paramLo] F7
  *** [handle] IS THE BLOCK HANDLE FROM THE CHAIN MAP, NOT A LITERAL 0x07. ***
  Earlier revisions of this doc showed 0x07 hardcoded — a stale artifact from
  early captures where the amp happened to be allocated handle 0x07. Querying
  with a fixed 0x07 silently fails on any patch where the amp sits elsewhere.
  This single wrong byte is what blocked amp/cab bypass from Phase 7 until
  7/18. Confirmed against Avid traffic: it queries every block this way.
  The 0x07 here is a broadcast/wildcard instance the firmware resolves to
  the current block; hardware replies as Format B with the real
  currentParamHi filled in.

UNIVERSAL paramLo VALUES (identical for all 33 amps, all sessions):
  0x03 = Amp Out Level
  0x04 = Gate Threshold
  0x05 = Gate Release
  0x01 = Block Bypass      (EVERY non-amp chain block, on its own handle;
                            v0: 0x40=active, 0x3F=bypassed. Confirmed 7/18.)
  0x06 = Amp Bypass        (v0: 0x40=active, 0x3F=bypassed)
  0x0E = Bright toggle     (live: v0=127=ON, v0=0=OFF)
  0x0F = Amp Select        (raw v0 — NOT run through the (v+64)%128 formula)
  0x14 = Cab Bypass        (v0: 0x40=active, 0x3F=bypassed)
  0x15 = Cab Type          (non-standard v0 — lookup table, Section 8)
  0x16 = Mic Type          (non-standard v0 — lookup table, Section 8)
  0x17 = Mic Axis          (v0: 0x3F=On-Axis, 0x40=Off-Axis — see C4)
  0x18 = Speaker Breakup   (standard continuous 0–127)

Tone knob paramLo values are PER-AMP — see Section 11.

CRITICAL — paramLo is NOT derived from the Avid XML sldX key name above
0x09. sldF -> paramLo 0x10, sldG -> paramLo 0x11 (NOT 0x0F/0x10 as the
letter positions would imply). Wireshark is the source of truth for
paramLo; XML is the source of truth for knob labels and tfxKey names only.
(This corrects the June research; see C3.)

DO NOT send CMD 0x11 before currentParamHi is set (<=0): causes a HW assert.


===================================================================
4. currentParamHi — RUNTIME HANDLE
===================================================================

currentParamHi is a runtime handle the firmware assigns to the amp block on
each patch load. It IS the instance byte in every CMD 0x11 message for that
patch. It changes every firmware session and varies by slot position. It
CANNOT be predicted, hardcoded, or read from the TFX body.

SOURCE: data[i+2] — the third byte of the typeA=0x07 triplet in the CMD 0x21
chain map. Triplet structure at data[6+]: [typeA][mid][third]. typeA=0x07 =
amp block; its third byte = currentParamHi. DO NOT change the data[i+2]
offset — confirmed correct across many captures.

Confirmed via round-robin capture (single session):
  A2: typeA=0x07 third=0x10 -> CMD 0x11 instance=0x10
  A1: typeA=0x07 third=0x1E -> CMD 0x11 instance=0x1E
  J2: typeA=0x07 third=0x2C -> CMD 0x11 instance=0x2C
Same patch across different sessions: 0x03, 0x74, 0x21, 0x2B — varies each time.

IMPLEMENTATION:
  Read from CMD 0x21 on EVERY patch navigation; store as currentParamHi.
  Use as the instance byte in all CMD 0x11 sends.
  Filter incoming CMD 0x11 by instance === currentParamHi.
  Reset to -1 on disconnect.

*** CHAIN-REORDER HAZARD — RESOLVED 7/18-7/19, kept for context ***
  currentParamHi is POSITION-DEPENDENT: moving a block makes the firmware
  assign it a new handle on next load, and a send using a stale handle hits
  whatever block now sits at that position (this corrupted gate parameters
  when the amp was moved). That hazard is REAL but is no longer a limitation:
  the chain map was solved 7/18 and every block's handle is now read from it
  on each patch nav, so sends are correct at any chain position. Bypass
  shipped 7/19 on that basis and is verified at six different amp handles
  including the amp last in the chain.
  THE RULE THAT REMAINS: never cache a handle across a chain map. Re-read
  currentChain after every CMD 0x21, and after every CMD 0x0D (below).

*** STEREO/MONO ALSO REASSIGNS HANDLES *** (confirmed 7/18)
  Every accepted CMD 0x0D rebuilds the post-amp half of the chain and fires
  a fresh CMD 0x21 with NEW handles for those blocks. The amp handle and all
  pre-amp handles are unaffected.

    Same patch, consecutive toggles:
      Stereo: amp 0x30, post-amp blocks 0x31–0x36
      Mono:   amp 0x30, post-amp blocks 0x3A–0x3F
      Stereo: amp 0x30, post-amp blocks 0x43–0x48

  No consequence today — every wired control (amp, tone, gate, cab, mic) sits
  at or before the amp. But any future post-amp block control MUST re-read the
  chain map after a 0x0D send. The Avid editor does exactly this: after each
  toggle it re-queries every parameter it displays.

  [DONE 7/18-7/19] The former "future fix" described here — identify every
  block in the chain map and store each block's handle per patch nav — is
  implemented. Blocks are identified by SLOT ID (not by the field once called
  typeA, which is a back-link), and the full chain is stored in currentChain
  on every map. See the chain map structure below.

  *** FX LOOP PLACEMENT RULE (confirmed 7/18 by Charlie, definitive) ***
  The FX Loop block has only FOUR legal chain positions:
    1. First in chain
    2. Immediately left of AMP-CAB
    3. Immediately right of AMP-CAB
    4. Last in chain
  No other placement is possible. Every other block may go anywhere.
  NOTE: both sample patches captured 7/18 have LOOP immediately RIGHT of
  AMP-CAB — the same case twice. The other three positions are unsampled,
  so reorder captures must exercise all four deliberately.

  THE FOUR POSITIONS BEHAVE AS AN ORDERED LIST (observed 7/18, both UIs):
      START  <->  left-of-AMP  <->  right-of-AMP  <->  END
  On the hardware front panel, highlighting the loop and scrolling moves it
  one step along this list, skipping every illegal position in between. In
  the Avid editor, dragging the loop and releasing snaps it to the nearest
  legal position rather than refusing the drop. Neither UI ever presents an
  illegal placement to the protocol.
  IMPLICATIONS:
   - The rule is almost certainly enforced in firmware, not just in the
     editor. Mirror it; do not invent our own policy.
   - We cannot learn the hardware's tolerance for an illegal placement
     through either UI, and deliberately sending one to a working unit is
     not worth the risk. Assume it is rejected.
   - Our chain row must treat the loop differently from other blocks:
     four discrete stops, not free placement. Design this in from the start.
   - AVID DRAGS THE LOOP ALONG WITH THE AMP when the two are adjacent, which
     is why the amp cannot be pushed past position 9 in the Avid editor while
     the loop sits to its right — you must park the loop elsewhere first.
     OUR APP DELIBERATELY DOES NOT DO THIS (agreed 7/19): dragging the amp
     leaves the loop where it is and, if that strands it, snaps the loop to
     its nearest legal position. Charlie prefers the freer behaviour. This is
     an intentional divergence from the Avid editor, not a defect.
   - Because both UIs resolve legality before sending, the reorder command
     most likely carries a resolved destination rather than a raw drop
     position. Expect a clean capture.

  CHAIN MAP STRUCTURE — SOLVED 7/18 (8 patches + TFX cross-check)

  MESSAGE:  F0 13 0B 0F [dir] 21 [11 triplets] [trailing] F7   (41 bytes)
  Triplet = [backLink][mid][handle]

  IT IS A LINKED LIST. [backLink] is the SLOT ID OF THE PREVIOUS BLOCK, not
  a type and not an allocation index. The trailing byte is the LAST block's
  own slot ID. Triplet 1 (the input block) back-links to itself as the head
  marker. Read it as:

    slotID(triplet N) = backLink(triplet N+1)     for N = 1..10
    slotID(triplet 11) = trailing byte

  *** SLOT IDs ARE FIXED PER BLOCK TYPE, IN EVERY PATCH *** (8/8, and
  independently confirmed against TFX Wst keys — see below)

    0x00  AMP-CAB        0x05  REVERB
    0x01  FX LOOP        0x06  DELAY
    0x02  VOLUME         0x07  DIST
    0x03  WAH            0x08  FX 1
    0x04  MOD            0x09  FX 2
                         0x0B  INPUT  (triplet 1; 0x0A unused)

  This is the correct and only reliable way to identify a block. Do NOT
  identify blocks by mid ranges — mid is the effect MODEL (Sec 23), and the
  generic FX slots host models from other categories, so ranges overlap.
  Slot ID says WHICH BLOCK; mid says WHICH MODEL is loaded in it.
  In particular FX 1 and FX 2 are distinguishable ONLY by slot ID: they can
  hold the same model (B2 has Parametric EQ 0x12 in both) and their chain
  order is not fixed (A3 has FX1 first, A4 has FX2 first).

  MAP ORDER = CHAIN ORDER (left to right as shown in the Avid editor).
  Triplet 1 is the INPUT block (mid 0x37 "Guitar In"; other input models
  0x38-0x40). Skip it — that leaves 10 triplets for the 10 chain blocks.

  AMP-CAB IS ONE BLOCK in the protocol, with two independent bypass flags.

  *** HANDLES ARE SEQUENTIAL IN CHAIN ORDER *** (8/8 patches)
    handle(position N) = handle(position 1) + N - 1        [N = 1..10]
    input block handle = handle(position 1) + 10
  Examples: A1 blocks 0x0E-0x17, input 0x18.  B1 blocks 0x46-0x4F, input 0x50.
  The base shifts on every reload and after every stereo/mono toggle, so the
  map must still be re-read — but triplets need no individual parsing.

  TFX CROSS-CHECK (this is what settled the field-1 question):
    Keys WorB..WorL / WstB..WstL, 11 slots, 8 bytes each from offset 208.
    Wst[letter] = SLOT ID — matches the chain map exactly.
    Letters run B..L in CHAIN ORDER: B = input, C..L = the 10 blocks.
    Per-block parameters follow the bypa[letter] keys later in the body;
    the amp block uses sld* keys instead of a bypa* key.

  BYPASS MUST BE QUERIED — NOTHING PUSHES IT TO US.
  After every chain map, query all ten blocks:
      F0 13 0B 0F 01 11 [handle] 01 F7     the nine ordinary blocks
      F0 13 0B 0F 01 11 [ampHandle] 06 F7  amp
      F0 13 0B 0F 01 11 [ampHandle] 14 F7  cab
  11 queries in total, which is what the Avid editor itself does at each load.
  *** DO NOT TEST BYPASS READBACK WITH THE AVID EDITOR OPEN. *** Our app adopts
  broadcasts regardless of who asked for them, so with the editor running
  alongside, ITS queries make our state look populated when we never asked for
  anything. This produced a false pass on 7/19: only amp and cab were being
  queried, yet all ten slots appeared to work. Verified afterwards — that day's
  log contains zero paramLo 0x01 queries from us. Any readback feature must be
  tested with the editor CLOSED before it is called working.

  BYPASS IS NOT IN THE CHAIN MAP. Patches B2/B3/B4 (same rig, same order,
  different on/off states) produce byte-identical maps apart from handles.
  Bypass is CMD 0x11 on the block's handle — see Section 3.

  *** CHAIN REORDER — SOLVED 7/19 ***
  THERE IS NO SEPARATE REORDER COMMAND. To reorder, send a COMPLETE CHAIN MAP
  back with dir=0x00, in the same 41-byte format the hardware broadcasts:

      F0 13 0B 0F 00 21 [11 triplets] [trailing] F7

  Build it by taking the current map and re-linking it into the desired order:
  keep each block's existing [mid] and [handle], and rewrite the back-links so
  they describe the new sequence (backLink of triplet N+1 = slotID of triplet
  N; trailing byte = last block's slotID). Triplet 1 remains the input block.
  Confirmed over four consecutive moves in one capture, every one decoding to
  exactly the move performed.

  HARDWARE RESPONSE: a dir=0x02 broadcast of the resulting map, then a
  CMD 0x03 dirty flag (F0 13 0B 0F 02 03 [slot] 01 F7).
  *** THE BROADCAST IS AUTHORITATIVE — ADOPT IT, DO NOT ASSUME OUR SEND STUCK.
  The hardware may return different [mid] and [handle] values than we sent.

  *** FX LOOP MODE IS GLOBAL, NOT PER-PATCH *** (confirmed 7/19)
  CMD 0x3C (Sec 6) selects Mono (L) / Mono-Stereo / Stereo. It lives in the
  editor's USER OPTIONS panel, alongside other global settings.
   - The mode is NOT stored in the TFX. Saving the same rig under all three
     modes changes only the checksum and three model ids (the loop and the two
     blocks after it) — there is no mode field anywhere in the file.
   - THE GLOBAL SETTING OVERRIDES THE PATCH. Uploading a TFX that was saved
     under Mono (L) while the unit is set to Stereo yields a Stereo loop. All
     three uploads in the test produced the same loop model.
   - The loop's model id is therefore a CONSEQUENCE of the mode, not a store
     of it. Observed: Mono(L) -> 0x2D (key LMMM), Mono-Stereo -> 0x30 (LYMS),
     Stereo -> 0x32 (LSMS). The first key character tracks the mode (M/Y/S).
     Three of the seven loop variants sampled; the rest are unexplained.
   - PRACTICAL: our app can infer the current mode from the loop block's mid
     in any chain map. No REQU for CMD 0x3C was observed — the editor never
     queries it — so whether one exists is untested.

  *** CHANNEL CONFIGURATION — WHAT THE MODEL VARIANTS MEAN *** (7/19)
  The variant index within a model family selects a CHANNEL CONFIGURATION —
  but the set of configurations a model supports is PER MODEL and CANNOT be
  inferred from how many variants it has.

  THE RULE (7/19, holds across all 30 direct observations, no exceptions):
      the LOWEST variant in a model family outputs MONO;
      every other variant in that family outputs STEREO.
  It follows directly from there being no stereo-in/mono-out variant anywhere:
  once a block must produce mono it must also accept mono, so only the bottom
  variant of a family can be mono-out.

  *** RETRACTED — a "correction" recorded earlier the same day *** An earlier
  revision of this section claimed C1 Chorus/Vibrato broke the pattern by being
  stereo-out in BOTH variants, and concluded that capability cannot be inferred
  from variant position. That conclusion was itself the product of incomplete
  data: C1 Chorus/Vibrato has THREE variants (mid 0x01/0x02/0x03) and only the
  upper two had ever been seen. With 0x01 included it is an ordinary
  three-variant family and the rule above holds. The lesson repeats the one
  from the chain-map defect — a pattern inferred from a partial family looks
  exactly like a broken pattern.

  EXCEPTION — FX LOOP. Its send and return are independent, so variant order
  carries no information about its output (0x31 is mono-out despite not being
  the lowest). Loop variants must each be observed.

  *** THERE IS NO STEREO-IN / MONO-OUT VARIANT. *** This single fact drives
  the whole propagation behaviour: the moment a block must produce mono it
  must also accept mono, which forces the block feeding it to produce mono,
  and so on BACKWARDS to the stereo source.
  CONSEQUENCE: placing a mono-only block (wah, distortion, volume...) anywhere
  in the post-amp section collapses EVERYTHING UPSTREAM of it to mono.
  Verified: moving WAH to the very end of the chain took LOOP 0x11->0x0F,
  ParamEQ 0x4F->0x4E, MultiChorus 0x5A->0x58, DynDelay 0x52->0x50 and
  Eleven SR 0x35->0x33 — the entire post-amp chain, in one move.
  Downstream is unaffected, because mono-in/stereo-out DOES exist: inserting
  mono DIST between MOD and DELAY left REVERB stereo (DELAY simply became
  mono-in/stereo-out 0x22->0x21).

  Pre-amp blocks are always mono because the amp is a mono device; stereo can
  only originate at or after the amp/cab (or at a stereo FX Loop return).

  UI IMPLICATION: dragging a mono-only block into the post-amp section is an
  audible change the user did not explicitly request. Warn, or at minimum
  reflect the resulting mono state in the chain row immediately.

  CHAIN ROW RENDERING SPEC (from Avid editor reference screenshots, 7/19):
   - Block ORDER comes from the chain map, not a fixed layout. Our current row
     uses the default order with FX1/FX2 hardcoded, which is wrong for most
     patches — this is the visible symptom of the old "assume default chain"
     limitation.
   - STEREO IS SHOWN PER CONNECTION: Avid draws a DOUBLE connector line
     between blocks where the signal is stereo and a SINGLE line where it is
     mono. The connector after block N is stereo exactly when block N's OUTPUT
     is stereo.
     Use the OUTPUT CHANNEL TABLE in Section 23 — 30 models resolved. It
     cannot be derived from variant rank (two models with the same variant
     count can differ), so anything not in that table gets a single line plus
     a logged warning naming the mid, rather than a guess.
   - AMP and CAB render as ONE block with two stacked labels, matching the
     protocol (one handle, two independent bypass flags at paramLo 0x06/0x14).
   - Bypassed blocks are drawn dimmed; active blocks lit.
   - ACCEPTANCE TEST: load a patch with a stereo post-amp section, then drag a
     mono-only block (e.g. WAH) to the very end. Every connector in the row
     must collapse to single-line. If it does, the variant decoding is right.

  WHY IT MAY DIFFER — CHANNEL RECONFIGURATION:
  The firmware recomputes mono/stereo propagation through the chain on every
  reorder and RE-INSTANTIATES any block whose input/output configuration
  changed, giving it a different model variant and a new handle. Observed:
  moving mono-only DIST in between MOD and DELAY changed MOD 0x05->0x04 and
  DELAY 0x22->0x21, both with new handles. The other three moves in the same
  capture changed nothing at all.
  So handles are NOT reassigned wholesale on reorder (unlike a stereo/mono
  toggle, which reassigns the whole post-amp group) — only affected blocks
  move. Re-read the broadcast either way.

  LEGALITY IS RESOLVED BEFORE SENDING. The editor never transmits an illegal
  arrangement: dropping VOL between AMP-CAB and LOOP resulted in a map with
  VOL placed on the FAR SIDE of LOOP. Our UI must do the same resolution
  before building the map (see the FX Loop placement rule above).

  CAPTURES NO LONGER NEED MOVE NOTES: consecutive maps fully describe what
  moved, since slot IDs name the blocks. Verified by reconstructing four
  documented moves from the data alone.

===================================================================
6. FULL COMMAND REFERENCE (0x00–0x50)
===================================================================

Legend: [SEND]=we can send it, [RECV]=hardware broadcasts it,
[DEAD]=receive-only, no send path exists on any known interface.

CMD 0x00 — Bulk TFX (patch body). Hardware broadcasts full 7-bit-encoded
  patch body on hardware-initiated save. Auto-captured to disk. [RECV]
CMD 0x01 — SEND_PATCH / bulk write. Send = load body to HW memory
  (Section 16). REQU (dir=0x01) = pull current slot's body back. [SEND/RECV]
CMD 0x02 — Current Rig Number. Send selects a slot; broadcast/RESP reports
  current slot. Used in save + navigation. [SEND/RECV]
CMD 0x03 — Save Rig (commit to slot). Part of save sequence (Section 15). [SEND]
CMD 0x04 — Rig Get/Set Name (address-based). Used in save; also a cheap
  names-only bank scan path. [SEND/RECV]
CMD 0x05 — Patch Name. Broadcast = null-terminated ASCII name; send = set
  current rig name (plain ASCII, no 7-bit encoding, no framing, max 16
  chars). [SEND/RECV]
CMD 0x07 — Rig Volume knob broadcast. F0 13 0B 0F 02 07 [v0] 00 00 00 00 F7.
  v0 decoded as CMD 0x11. Range val=0 -> -24.0 dB, val=127 -> 0.0 dB.
  REQU form reads current value. [SEND via CC17 / RECV via 0x07]
CMD 0x3C — FX Loop mode. GLOBAL setting, not per-patch.
  Send:      F0 13 0B 0F 00 3C [mode] F7
  Broadcast: F0 13 0B 0F 02 3C [mode] F7   (echo carries the real value,
             unlike CMD 0x0D — decode it normally)
  mode: 0x01 = Mono-Stereo, 0x02 = Stereo, 0x00 = Mono (L) (INFERRED — the
        capture only ever moved up from Mono, so 0x00 was never observed).
        The editor's label "Mono (L)" implies a "Mono (R)" exists; not seen.
  See Section 4 for what it does to the chain. [SEND/RECV]

CMD 0x0D — Stereo/Mono. Send: F0 13 0B 0F 00 0D [val] F7. Broadcast:
  F0 13 0B 0F 02 0D [val] F7. val 0x01=Mono, 0x00=Stereo (both directions).
  Echo after our own send is always 0x01 — acknowledgement only, do not
  decode. Global, not per-patch. See Section 10. [SEND/RECV]
CMD 0x11 — Live parameter read/write. See Section 3. [SEND/RECV]
CMD 0x20 — Effect Description (per-effect query). Effect string ID at byte 7,
  name at byte 25. [SEND/RECV]
CMD 0x21 — Chain Map / Rig Description. F0 13 0B 0F 01 21 F7 -> 11 triplets
  + trailing byte (41 bytes). Triplet = [backLink][mid][handle], where
  backLink = the PREVIOUS block's SLOT ID (a linked list, NOT a type tag),
  mid = the effect MODEL, handle = that block's CMD 0x11 instance byte.
  Identify a block by its SLOT ID, never by mid range. Full structure,
  slot-ID table and handle arithmetic: Section 4.
  *** The old reading "[typeA][mid][third], typeA=0x07=amp" is WRONG and
  caused a live defect — 0x07 is DIST's slot ID, so it found the block
  AFTER dist. See Sec 24 (7/19). Do not reintroduce it. ***
  Send with dir=0x00 to REORDER the chain (Section 4). Fires on every patch
  load and on chain changes. [SEND/RECV]
CMD 0x22 — Effect Count. [SEND/RECV]
CMD 0x34 — True Z impedance broadcast. Global, front-panel only. Auto-
  broadcasts on amp/cab model change (val=0x7E=Auto in that context). [DEAD-send]
CMD 0x36 — Output Volume. F0 13 0B 0F [dir] 36 [outSel]... See Section 18.
  outSel 0x00=Main, 0x02=To Amp1, 0x03=To Amp2, 0x04=Unit Vol, 0x06=query.
CMD 0x37 — To Amp Source. F0 13 0B 0F 00 37 07 [slot] [val] F7.
  *** MUST be preceded by a CMD 0x3A query for that slot — sending without it
  causes a firmware assert. *** The 7/14 factory-reset incident was this
  command sent unqueried. With the query first the sequence is safe, but SW
  sends still do not move the HW source (cause unknown). See Section 18.
CMD 0x3A — To Amp Source query. REQU: F0 13 0B 0F 01 3A [slot] F7.
  RESP: F0 13 0B 0F 12 3A 07 [slot] [currentVal] F7. Required before any
  CMD 0x37 write. See Section 18. [SEND/RECV]
CMD 0x38 — Global Cabinet Bypass. Global override. Front-panel only. [DEAD-send]
CMD 0x3B — Global Mute. F0 13 0B 0F 02 3B 01 [val] F7. Front-panel only. [DEAD-send]
CMD 0x3D — Input Selector broadcast. F0 13 0B 0F 02 3D [val] F7 (value at
  data[6], NOT data[7]=F7). Values: 0x00=Guitar, 0x02=Mic, 0x03=Line L,
  0x04=Line R, 0x05=Line L+R, 0x06=Dig L, 0x07=Dig R, 0x08=Dig L+R,
  0x12=Re-Amp. Broadcast on input change only (not startup/patch change).
CMD 0x40 — Tuner. See Section 9. [SEND/RECV]
CMD 0x41 — Tuner companion broadcast. Safe to ignore.
CMD 0x50 — Version/capabilities query. Request data=0x05; response
  04 03 14 29 (likely firmware version). [SEND/RECV]

Startup commands seen only in Avid editor USB capture (purpose unknown,
not required by Eleven Edit): 0x08, 0x0A, 0x35, 0x39.
  (0x3A and 0x3C were formerly on this list; both are now identified —
  0x3A = To Amp Source query, 0x3C = FX Loop mode. See above.)


===================================================================
7. VALUE ENCODINGS
===================================================================

CONTINUOUS KNOBS (CMD 0x11, 0x07, 0x36) — single-byte offset binary:
  DECODE: if v0 >= 0x40 -> val = v0 - 0x40   (range 0–63)
          if v0 <  0x40 -> val = v0 + 64     (range 64–127)
  ENCODE: v0 = (targetV127 + 64) % 128
  val 0–127 maps to 0.0–10.0 on display.
  Sentinels: min = 0x40 00 00 00 (val 0); max = 0x3F 7F 7F 7F (val 127).

TOGGLES (Bright, live) — do NOT use the continuous decode:
  Live CMD 0x11: v0=127=ON, v0=0=OFF.
  In TFX body: raw 0=OFF, 1=ON (see Section 13 toggle note).

BYPASS (amp & cab, live) — check v0 DIRECTLY, do not decode:
  v0=0x40 = active,  v0=0x3F = bypassed.

MIC AXIS (live) — check v0 directly:
  v0=0x3F = On-Axis,  v0=0x40 = Off-Axis.   (Corrected 7/16 — see C4.)

AMP SELECT (paramLo 0x0F): raw v0 used directly (NOT the (v+64)%128 formula).
  Full v0->amp table is AMP_SELECT_LIST in protocol.js (Section 12 scheme B).

CAB TYPE / MIC TYPE: non-standard, require lookup tables. See Section 8.

32-BIT VALUES in TFX body (amp model, cab type raw): signed int32,
  little-endian in the body's 8-byte key/value pairs. Amp model also appears
  as a 32-bit selector in some CMD 0x11 contexts assembled big-endian
  (v0<<24|v1<<16|v2<<8|v3). Use the integer maps in Section 12.

9. TUNER
===================================================================

SOFTWARE SEND: CC 69 (0x45).  ON = B0 45 7F   OFF = B0 45 00.

HARDWARE READBACK: the hardware does NOT echo CC 69. It responds with a
SysEx CMD 0x40 broadcast (corrected 7/15):
  F0 13 0B 0F 02 40 [state] F7      state: 0x01=ON, 0x00=OFF
CMD 0x41 fires as a companion broadcast — safe to ignore.
Handler lives in sysex-handler.js. (Reconciles with C6.)

(Raw-USB research also documented a tuner-data polling path — REQU 0x41/0x42
returning note/cents — used by the Avid editor's tuner graphic. Not used by
Eleven Edit; retained here for completeness. Tuner reading: RESP
F0 13 0B 04 0F 12 42 07 [note] [tune] F7; note low-nibble=note 0=C..11=B,
high-nibble=octave; tune 0=in tune.)


===================================================================
10. STEREO / MONO
===================================================================

Global setting, not per-patch. FULLY BIDIRECTIONAL (confirmed 7/18/2026).
Earlier docs called this receive-only; that was wrong — the send path exists,
it is just not exposed on the Eleven Rack front panel in an obvious way. The
Avid editor drives it from a small button on its chain graphic.

SOFTWARE SEND (confirmed 7/18 from Avid USB capture + working build):
  F0 13 0B 0F 00 0D [val] F7
  val: 0x01 = Mono,  0x00 = Stereo
  8 bytes. No query-first, no preamble, no length byte.

  *** Do NOT insert a 0x06 (or 0x04, or 0x07) before [val]. *** Those bytes
  appear in USB captures as CIN framing and are stripped by our bridge. A
  literal 0x06 in the payload is read by the hardware AS the value, so every
  send resolves to the same state (Mono) and Stereo becomes unreachable.
  See the USB-MIDI FRAMING block in Section 2.

HARDWARE BROADCAST (front-panel or Avid-editor change):
  F0 13 0B 0F 02 0D [val] F7
  val: 0x01 = Mono,  0x00 = Stereo   (same sense as send; message is the
  same shape as the send with only the direction byte differing)

ECHO AFTER OUR OWN SEND — UNRELIABLE, DO NOT DECODE:
  The hardware answers our send with F0 13 0B 0F 02 0D 01 F7 regardless of
  the value sent or the resulting state. It is an acknowledgement, not a
  state report. Decoding it drives the UI to the wrong state.
  Handling: transport.js sets suppressMonoEcho before each send;
  sysex-handler.js drops exactly one incoming CMD 0x0D and clears the flag.
  Unsolicited broadcasts (front panel) are never suppressed and decode
  normally. Our own display is set optimistically at click time.

TFX: key RMno (global section), body byte 124. 0=Stereo, 1=Mono.
  Matches the wire value sense. Read on patch load.

CHAIN-MAP SIDE EFFECT: every accepted 0x0D reassigns the runtime handles of
  all post-amp chain blocks and fires a fresh CMD 0x21. See Section 4.

UI: clickable badge on the chain row; dim when Stereo, lit amber when Mono.
  300 ms click lockout to prevent accidental double-fires (the hardware
  itself has no minimum interval — it accepted machine-gun toggling from the
  Avid editor without complaint).

===================================================================
13. TFX BINARY FORMAT
===================================================================

A .tfx file = [56-byte header] + [body]. Body == decode7bit(SEND_PATCH
payload). A 968-byte body -> 1024-byte file. All sources (Avid Editor,
ElevenHack, Eleven Edit, HW save) produce SHA-256 identical files for the
same patch content.

56-BYTE HEADER:
  bytes 0–3   total file size, big-endian uint32 (e.g. 0x00000400 = 1024)
  bytes 4–7   zeros
  bytes 8–23  magic "DigiElvRELVhRig " (16 bytes, space-padded)
  bytes 24–55 zeros
  Load compatibility check: magic begins "DigiElv" at offset 8.

BODY LAYOUT:
  bytes 0–3   version quadlet
  bytes 4–7   signature/headerCode (changes when content changes)
  bytes 8–35  rig name, 7 quadlets (reversed byte order per quadlet)
  byte 36+    TOC / global params, then per-effect sections

KEY ENCODING ("quadToKey"): read 4 raw bytes, reverse to get the key name.
  e.g. raw 0x36 0x64 0x6C 0x73 reversed = "6dls" (amp model marker);
       raw 0x37 0x64 0x6C 0x73 reversed = "sld7".
  Every key is immediately followed by its 4-byte little-endian value
  (8-byte pairs). Key search scans the whole body, so it is position-
  independent and works regardless of chain order.

VALUE ENCODING (continuous knobs — gate, amp out, rig vol, tone, breakup):
  Signed 32-bit int, linear across the full int32 range.
  INT32_MIN (0x80000000) = 0% ; INT32_MAX (0x7FFFFFFF) = 100%.
  To 0–127: Math.round((signed - (-2147483648)) / 4294967295 * 127).
  Helper gateRawToV127(signed) does this.

TOGGLES in TFX body (e.g. Bright): raw 0=OFF, 1=ON. Do NOT run through
gateRawToV127 (which would map 0 to the midpoint 64). Use: signed !== 0 ? 127 : 0.

7-BIT DECODE (protocol.js — the trusted version):
  function decode7bit(enc){
    const res=[]; let begin=0,shift=1,i=0,len=enc.length;
    while(begin+i<len-1){
      let v=(((enc[begin+i]&0xFF)<<shift)&0xFF)+(((enc[begin+i+1]&0xFF)>>(7-shift))&0xFF);
      res.push(v&0xFF); shift++;
      if(shift===8){shift=1;begin++;} i++;
    }
    res.push(((enc[len-1]&0xFF)<<shift)&0xFF);
    return res;
  }
7-BIT ENCODE: use ONLY the encode7bit in protocol.js. encode7bit(968-byte
body) must produce exactly 1107 bytes. ElevenHack's encode7bit does NOT
correctly invert this decode — do not use it (causes "Bad Patch Data").

15. SAVE PROTOCOL (software-initiated commit to slot)
===================================================================

STATUS: implemented. Rename-on-save implemented (Phase 4a). Each step
uses a DIFFERENT addressing format:
  Step  Cmd     Format                          Example (slot 4 = B1)
  1     0x05    name (plain ASCII)              F0 13 0B 0F 00 05 [name] 00 F7
  2     0x03    [raw_slot] [0x00]               F0 13 0B 0F 00 03 04 00 F7
  3     0x04    [bank] [num] [name] [00]        F0 13 0B 0F 00 04 01 00 [name] 00 F7
  4     0x02    [0x00] [raw_slot]               F0 13 0B 0F 00 02 00 04 F7
  raw_slot = 0–103, bank = floor(slot/4), num = slot%4.
  Name: plain ASCII, max 16 chars, null-terminated in Steps 1 and 3.

RENAME: Step 1 (CMD 0x05) IS the rename. Passing any name string renames
the patch in hardware memory before committing. saveCurrentPatchToSlot()
in capture-scan.js accepts an optional nameOverride param; if supplied it
updates currentPatchName and the display element before sending. Rename
without a subsequent commit (Steps 2–4) changes the working name only —
not persisted to the slot until Step 4 fires.

SAVE TO RACK + AUTO TFX (Phase 4a, via SAVE ▾ → Save to Rack…):
saveToRackAndDisk(name) calls saveCurrentPatchToSlot(name) then waits
500 ms for the commit to settle before calling captureCurrentPatchNow().
The TFX file is written with the new name since currentPatchName is
updated before the capture request fires.

Hardware responds with dirty-flag clear, slot confirm, full bulk broadcast.
SAFETY NOTE: software save does NOT trigger the hardware-save auto-export
(the CMD 0x04 echo arrives AFTER the bulk broadcast in software save, but
auto-export detection needs it BEFORE).
NOT YET: save-to-different-slot (slot picker UI). Protocol is identical to
current save — only the target slot number changes. When built, Load TFX
→ Save to Different Slot serves as "copy file into any slot".


===================================================================
16. LOAD TFX PROTOCOL (file -> hardware memory)
===================================================================

STATUS: implemented ("Load TFX"), round-trip verified.
  Step 1 — bulk write (memory only, does NOT commit to a slot):
    F0 13 0B 0F 00 01 [encode7bit(body)] F7
    body = TFX file minus the 56-byte header. encode7bit(968) -> 1107 bytes.
  Step 2 — name write:
    F0 13 0B 0F 00 05 [ASCII name] 00 F7
Hardware echoes bulk data back as ASYNC (dir=0x02, cmd=0x01); the SEND_PATCH
handler decodes it (payload at position 6). Load accepts any file with
"DigiElv" magic at offset 8. Round-trip: capture -> save -> load -> capture
-> SHA-256 matches.


===================================================================
17. BANK BACKUP / RESTORE (EHB format)
===================================================================

Not yet implemented; protocol fully known. EHB = a standard ZIP of 104 TFX
files, one per slot. No proprietary format, no encryption.
  Filename inside ZIP: [Letter][Number]-[PatchName].tfx (e.g. A1-DC Vintage
  Crunc.tfx). Unused slots: "-unused-.tfx" (default empty patch).
BANK SAVE (HW -> file): for each slot: CURR_RIG to slot -> REQU SEND_PATCH ->
  hardware streams body back -> strip, decode7bit, prepend 56-byte header ->
  write .tfx. (RIG_GETNAME via CMD 0x04 is a cheaper names-only scan.)
BANK RESTORE (file -> HW): per slot, run the Load (Section 16) + Save
  (Section 15) sequence. ~104 cycles; several minutes with per-slot verify.

TO AMP 1 / 2 VOLUME (CMD 0x36):

    To Amp 2 volume: body[60–63] — signed LE32, standard gateRawToV127.
    MUTE = INT32_MIN (0x80000000) -> v=0; MAX = INT32_MAX (0x7FFFFFFF) -> v=127.
  Global setting — not per-patch. Persists across patch navigation.
  STATUS: SW send + HW readback + TFX initial readback all working (7/17).
  HW knob -> SW display tracking confirmed working.

TO AMP SOURCE (CMD 0x37):
  Confirmed wire format 7/17/2026 from Avid editor USB capture:
    F0 13 0B 0F 00 37 07 [slot] [val] F7
  slot: 0x00=ToAmp1, 0x01=ToAmp2.
  val:  0x00=Rig Input, 0x01=Amp Input, 0x02=Amp Output, 0x03=Rig Output.
  HW also has additional options beyond Avid's 4 (Rig Out No Cab, RESO toggle)
  with unknown val bytes — not yet captured.

  Global setting — not per-patch, not stored in TFX body.
  REQUIRED: Send CMD 0x3A query for the slot FIRST, wait for response, then
  send CMD 0x37. Skipping the query causes firmware assert (7/17/2026 x2).
  CMD 0x3A REQU: F0 13 0B 0F 01 3A [slot] F7
  CMD 0x3A RESP: F0 13 0B 0F 12 3A 07 [slot] [currentVal] F7  (10 bytes)

  STATUS: Query+write sequence confirmed — no assert. HW source does not

  Factory reset recovery: hold FX Loop + Mod + Reverb at power on.

22. FLAGGED CONFLICTS
===================================================================

C1 — 0x04 FRAMING (RESOLVED). Old raw-USB research (node-usb / Wireshark)
  shows a 0x04 device byte in the header (F0 13 0B 04 0F) and a 0x04 marker
  before every 3 payload bytes. The Java-bridge MIDI path does NOT: the app
  sees clean F0 13 0B 0F with no framing. Both are correct for their own
  layer. Application code must never add/strip 0x04. Separately, the 0x04 at
  data[6] of CMD 0x11 FORMAT B is real SysEx, unrelated to USB framing.

C2 — REQUIRED DRIVER VERSION (RESOLVED). v1.1.12 is confirmed as the working
  driver for the Java-bridge build. The v1.0.11 requirement came from the 
  abandoned node-usb path, which claimed the raw USB interface; the Java-bridge
  path goes through the OS MIDI layer and works on the newer, fully featured
  v1.1.12. Use v1.1.12.

C3 — paramLo VALUES ABOVE 0x0F (RESOLVED, newer wins). The June research
  derived paramIds from Avid XML sldX letters (sldF=0x0F, sldG=0x10), which is
  WRONG above sld9. Wireshark (7/15) confirms sldF=0x10 and sldG=0x11. Several
  per-amp assignments in the June table were also wrong (e.g. Lead 800 and DC
  family Master/Gain/PreAmp swaps). Section 11 (Wireshark-confirmed) is
  authoritative; the June per-amp paramId table is superseded in full.

C4 — MIC AXIS v0 DIRECTION (RESOLVED). On-Axis=0x3F, Off-Axis=0x40 — confirmed
  from the Avid editor walk capture AND working in the current build. The 7/14
  value (On-Axis=0x40) was inferred before a real capture existed and was wrong.
  Document and code agree. (TFX key sldM is separately 0=Off-Axis, 1=On-Axis.)

C5 — AMP BYPASS paramLo (RESOLVED). June research: 0x01 (from the wrong XML
  derivation). Confirmed: amp bypass = 0x06, cab bypass = 0x14, and paramLo
  0x01 is PER-BLOCK bypass for the nine non-amp blocks — so the June value was
  a real paramLo, just not the amp's. The old note "REQU returns nothing" is
  WITHDRAWN (7/18): the hardware answers correctly; our query had the handle
  hardcoded to 0x07. Query every block after each chain map (Sec 4).

C6 — AMP TYPE / AMP SELECT paramLo. June research: 0x03 = amp/cab type
  selector. Confirmed: 0x03 = Amp Out Level; Amp Select = 0x0F (raw v0). Use
  0x0F for selecting the amp, 0x03 for Amp Out.

C7 — TUNER READBACK. Reference 07-14 implied a CC-based tuner confirm
  (0x40/0x3F). 7/15 confirmed the hardware does NOT echo CC 69; it broadcasts
  CMD 0x40 SysEx (01=ON/00=OFF). Send is still CC 69. Use CMD 0x40 for readback.

C8 — SLOT/BANK ARITHMETIC. Most docs: bank=floor(slot/4), num=slot%4 (4 slots
  per bank, 26 banks). Primer note gives bank=floor(slot/24), rig=slot%24.
  The /4 grouping matches the A1–Z4 labeling used everywhere else and the save
  protocol; treat /4 as authoritative unless a specific feature proves otherwise.

C9 — TRUE Z "AUTO" VALUE. Live CMD 0x34 broadcast uses 0x00 (older) / 0x7E
  (raw-USB capture) for Auto; the TFX PIGI field uses 125. These are different
  representations on different paths, not a single value. True Z is receive-
  only and non-core; note but no action needed.

C10 — STEREO/MONO SEND PATH (RESOLVED 7/18). Every doc prior to this one
  said CMD 0x0D was receive-only / front-panel-only / [DEAD-send]. Wrong. A
  send path exists and is now working in the build. The claim survived
  because the Avid editor's control for it is an easily-missed button on its
  chain graphic, so no capture of a software-initiated change existed until
  7/18. Section 10 is authoritative. Related: the 0x06 seen in old captures
  was USB CIN framing, not a payload byte — see Section 2.

C12 — ENVIRONMENT: WINDOWS 11 AND JDK VERSIONS (RESOLVED 7/21/2026).
  Both parts were apparent conflicts between statements about DIFFERENT
  things, not disagreements about the same thing.
  (a) WINDOWS 11. "Windows 11 confirmed compatible" referred to ELEVEN EDIT;
      "Avid Editor on Win11 — BSOD" referred to the AVID EDITOR. Both are
      true. Eleven Edit works on 22H2 and 26H1; the Avid Editor BSODs on
      22H2 and is assumed to do the same on 26H1. Full matrix in Section 1.
  (b) JDK. The toolchain moved and the older line was simply not updated.

C11 — CMD 0x11 "FORMAT B" PROVENANCE. *** STILL UNRESOLVED, narrowed 7/20 ***
  UPDATE 7/20: a real bug confirmed that data[6]===0x04 cannot by itself mean
  "Format B", because a block handle can legitimately equal 0x04 (Sec 3
  disambiguation rule). That fixes the DETECTION problem but does not settle
  the ORIGINAL question below — whether a genuine 0x04-prefixed Format B
  exists on the MIDI layer at all, or whether every real RESP is Format A
  shaped and Format B is a USB-framing artifact. Both remain possible. The
  handler accepting both shapes is still the safe position.

  Section 3 documents a FORMAT B for RESP messages, with a fixed 0x04 at

  REQU this app ever sent (7/19) came back FORMAT A shaped instead:

      IN  F0 13 0B 0F 12 11 51 06 40 00 00 00 00 F7
  i.e. data[6]=handle, no 0x04. FORMAT B may be another USB-CIN-framing
  misread of the same kind that cost a day on CMD 0x0D (see C1 / Sec 2).
  CURRENT PRACTICE: the bypass router accepts BOTH shapes, which is safe.
  ACTION: before relying on FORMAT B anywhere new, capture a RESP on the MIDI
  layer and confirm whether the 0x04 is ever really present. If it is not,
  delete FORMAT B from Section 3 rather than leaving both documented.

23. EFFECT MODEL TABLE (CMD 0x20) — COMPLETE
===================================================================

Captured 7/18 from Avid editor startup enumeration. The editor queries
CMD 0x20 for every model index at launch; CMD 0x22 returns the count.

  MODEL COUNT:  F0 13 0B 0F 01 22 F7  ->  ... 12 22 41 F7   (0x41 = 65)
  MODEL INFO:   F0 13 0B 0F 01 20 [idx] F7
    Response:   12 20 [idx] "Digi" [4-char type][3-char variant]
                [3 bytes] [category?] [display name, NUL-terminated]

These indices ARE the chain map "mid" field. NOTE: mid identifies the MODEL
loaded in a block, NOT which block it is. To identify the block itself use
the slot ID (Section 4). Use this table for display names only.

RECORD LAYOUT (after "Digi" + 4-char type + 4-char variant):
  6 bytes, two little-endian 3-byte fields, then NUL-terminated display name.
    field 1 = category  (0x010000 = input source, 0x020000 = internal)
    field 2 = SLOT LEGALITY BITMASK — which chain slots may host this model

  BITMASK -> SLOT.  bit = (slotID - 4) mod 12, i.e.
    bit0  MOD      bit3  DIST     bit8   AMP      bit10  VOL
    bit1  REVERB   bit4  FX 1     bit9   LOOP     bit11  WAH
    bit2  DELAY    bit5  FX 2
  Common values: 0x031 = MOD+FX1+FX2   0x030 = FX1+FX2 only
                 0x008 = DIST   0x004 = DELAY   0x002 = REVERB
                 0x800 = WAH    0x400 = VOL     0x200 = LOOP   0x100 = AMP
  This is the authoritative source for populating a model dropdown per slot.
  Confirmed against the editor's own dropdown contents.

TFX BLOCK PARAMETER SETS  (from 9 patch files, 7/18)
-------------------------------------------------------------------
A TFX carries all 10 blocks, so each saved patch yields up to 10 model
parameter sets for free. No capture needed.

TFX LAYOUT: 4-byte key stored REVERSED, followed by its 4-byte value.
  Slot table at offset 208: 11 x 16 bytes = Wor[letter]+value, Wst[letter]+value.
    Wst value = SLOT ID (see Sec 4).   Wor value = MODEL ID (TFX numbering).
  Block parameters follow the bypa[letter] marker for that slot. The bypa key
  is 5 chars, which breaks the 8-byte stride — re-anchor after it.
  The AMP block has NO bypa marker; it uses sld* keys and sits in chain order.

*** TFX MODEL ID IS A DIFFERENT NUMBERING FROM THE CMD 0x20 MODEL INDEX. ***
  They are not offset by a constant. Do not convert between them by arithmetic;
  correlate by parameter set / block type. (MultiChorus: CMD 0x20 0x04-0x06,
  TFX 0x58-0x5A. Parametric EQ: CMD 0x20 0x12-0x13, TFX 0x4E-0x4F.)

*** MODEL ID ENCODES MONO vs STEREO INSTANTIATION *** (confirmed 7/18)
  The same patch saved in mono and again in stereo keeps identical model IDs
  for every PRE-amp block and changes the ID of every POST-amp block:
    800 EchoScream  post-amp  0F 26 4E 50 33  ->  11 48 4F 52 35
    Big Blue        post-amp  0F 58 1B 55 4E 33 -> 11 5A 30 56 4F 35
  Pre-amp blocks unchanged in both. Confirmed on two independent file pairs.
  Known mono/stereo pairs: 0F/11 (FX Loop), 26/48 (Volume), 4E/4F (Param EQ),
  50/52 (Dyn Delay), 33/35 (Eleven SR), 58/5A (MultiChorus), 1B/30 (BBD Delay).
  THIS EXPLAINS two earlier observations: the duplicate display names in the
  CMD 0x20 table (Sec 23) are mono/stereo variants, and a stereo/mono toggle
  reassigns exactly the post-amp handles (Sec 4) because those blocks are
  genuinely re-instantiated as different models.

*** EXTEND THIS TABLE ONLY BY THE LOWEST-VARIANT RULE, NEVER BY GUESSWORK. ***
The rule (Sec 4): within a model family the LOWEST variant is mono-out and
every other variant is stereo-out. It follows from there being no
stereo-in/mono-out variant anywhere.
  NOTE — an earlier revision of this header claimed the rule was broken by
  C1 Chorus/Vibrato being stereo-out in both variants, and concluded the table
  could not be extended by inference at all. That was itself a partial-data
  error: C1 has THREE variants (mid 0x01/0x02/0x03) and only the upper two had

  EXCEPTION: FX Loop — send and return are independent, so variant order says
  nothing about its output. Loop variants must each be observed.

  Do this in TFX-model-id space, then translate to mid via the bridge — the

  pre-amp is mono" anchor is unsafe there (a stereo FX Loop can sit pre-amp).
