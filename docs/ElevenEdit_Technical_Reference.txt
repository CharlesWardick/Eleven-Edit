1. ARCHITECTURE & TRANSPORT
===================================================================

CONFIRMED WORKING ARCHITECTURE (supersedes all earlier transport designs):

  ElevenRackBridge.jar  <->  ws://localhost:57121  <->  Electron UI
         |
   javax.sound.midi
         |
   Eleven Rack USB
     IN:  "Eleven Rack No details available"  (Vendor Specific interface)
     OUT: "Eleven Rack External MIDI Port"    (standard MIDI interface)

WHY JAVA: The Eleven Rack's "Vendor Specific" USB interface carries all
SysEx traffic. Java's javax.sound.midi sees ALL Windows MIDI ports,
including the "No details available" Vendor Specific port. node-midi,
Web MIDI, and MIDI-OX see only 3 standard ports and miss it. Confirmed by
direct testing. ElevenHack (2013) uses this same javax.sound.midi approach.

PORT AUTO-DETECT (case-insensitive):
  IN  = name contains "Eleven" AND "No detail"
  OUT = name contains "Eleven" AND "External"
Typical Windows enumeration: IN=port 7, OUT=port 5 (do not hardcode indices;
match by name).

BRIDGE PROTOCOL (JSON over WebSocket):
  CLIENT -> BRIDGE: {"cmd":"connect","inPort":7,"outPort":5}
                    {"cmd":"send","hex":"F0 13 0B 0F 01 01 F7"}
  BRIDGE -> CLIENT: {"type":"midi_in","hex":"F0 13...","bytes":[...]}
  First byte auto-detects SysEx (0xF0) vs short message (CC/PC).
  Shutdown: write "SHUTDOWN\n" to bridge stdin. A forceful kill
  (taskkill /F) skips JVM shutdown hooks on Windows and can leave orphan
  processes.

FRAMING — IMPORTANT: On this MIDI-layer path the app sees clean SysEx:
  F0 13 0B 0F [dir] [cmd] ... F7  — pure 7-bit, NO 0x04 framing.
  The 0x04 device-address byte and the "0x04 per 3 bytes" framing described
  in old raw-USB (node-usb / Wireshark) research apply ONLY to the raw
  Vendor Specific endpoint. javax.sound.midi handles that layer for us.
  Never insert or strip 0x04 framing in application code. (See Section 22
  conflict C1 for how this reconciles the two research eras.)

ENVIRONMENT:
  Electron ^25.0.0, build with electron-builder --win --x64.
  No node-midi, no electron-rebuild, no node-usb dependency.
  npm start has never worked in this environment — always build the EXE.
  Java: bridge source is Java 8 compatible (compile --release 8).
  Compiled under JDK 25; JDK 21 was used earlier and the --release 8 target
  makes the compiler version largely immaterial. Runtimes verified: 21, 25, 26.

PLATFORM MATRIX (consolidated 7/21/2026 — supersedes all earlier scattered
Windows notes). Avid USB driver v1.1.12 throughout.

  Platform            Eleven Edit   Avid Editor
  ─────────────────────────────────────────────────────────────────────
  Windows 10          WORKS         RUNS (VM and physical, several driver
   (VM + physical)                  versions)
  Windows 11 22H2     WORKS         INSTALLS BUT MUST NOT BE RUN — BSOD
   (VM, JDK 25)                     observed
  Windows 11 26H1     WORKS         UNTESTED — assume same as 22H2, do not
   (VM, JDK 26)                     run it

  Windows 11 26H1 was stood up 7/21/2026 specifically to check whether the
  revised Microsoft MIDI stack (MIDI 2.0 era) disturbed the bridge. It did
  not — javax.sound.midi still enumerates the Vendor Specific port and every

  PRACTICE: keep the rule. Alternate between them; never drive both at once.

  GRAPHICS ASSETS — WHERE THEY LIVE (7/21/2026). The pedal/amp/cab images the

        C:\Program Files\Avid\Eleven Rack Editor\System Plug-Ins

  (See Section 22 conflict C2.)

SLOT MATRIX: 26 letters x 4 = 104 user slots (A1–Z4, slot index 0–103).
  bank = Math.floor(slot/4), num = slot%4, label letter = BANKS[bank].
  (Note: one source uses slot/24 for a different bank grouping — see C7.)
  After Z4: factory presets (read-only).


===================================================================
2. SYSEX WIRE FORMAT
===================================================================

All messages:  F0 13 0B 0F [dir] [cmd] [data...] F7
  Manufacturer ID: 0x13 0x0B (Avid/Digidesign)
  Device ID:       0x0F  (0x0E occasionally noted in ElevenHack source)

DIRECTION BYTE:
  0x00 = SNDSET  — we write/command to hardware
  0x01 = REQU    — we request data from hardware
  0x02 = ASYNC   — hardware sends an unsolicited state update
  0x12 = RESPOND — hardware responds to one of our REQU queries

REQU LENGTH (confirmed 7/9, 18 commands in real Avid traffic):
  Every bare REQU is exactly 7 bytes: F0 13 0B 0F 01 [cmd] F7. No trailing
  bytes. (CMD 0x11 REQU is the exception: it carries paramLo — see Sec 3.)

RESP vs ASYNC PAYLOAD OFFSET (confirmed 7/9):
  RESP to our own REQU (dir=0x12) has NO slot byte; payload starts at
  byte 6. An ASYNC broadcast (dir=0x02, e.g. hardware save) has a slot byte
  at position 6; payload starts at position 7. This offset difference is
  handled by the SEND_PATCH decode path.

*** USB-MIDI FRAMING — READ BEFORE DERIVING ANY FORMAT FROM A CAPTURE ***
  (confirmed 7/18, after a full day lost to this)
  A raw USB capture of the Avid editor is NOT the message. USB-MIDI packs
  SysEx into 4-byte groups, each led by a Code Index Number (CIN) framing
  byte. Those framing bytes are transport, not data, and our Java bridge
  strips them. Regroup every capture in fours before reading it:

    f0 13 0b 04 0f 00 0d 06 00 f7
      -> [04] f0 13 0b | [04] 0f 00 0d | [06] 00 f7
      -> actual message: F0 13 0B 0F 00 0D 00 F7   (8 bytes, not 10)

  Common CINs: 0x04 = SysEx starts/continues (3 data bytes follow),
  0x05/0x06/0x07 = SysEx ends with 1/2/3 data bytes. The SAME framing byte
  appears at different offsets in different captures depending on payload
  length, which makes it look like a meaningful per-command value. It is not.

  SANITY CHECK: a send and its matching broadcast should be the same shape.
  If your derived send format is longer than the hardware's own broadcast of
  the same command, you have almost certainly kept a framing byte.


===================================================================
3. CMD 0x11 — LIVE PARAMETER READ/WRITE
===================================================================

The single most important command. Reads/writes any parameter on the amp
block in real time. TWO receive formats + one send format (resolved 7/16).

FORMAT A — ASYNC broadcast (hardware -> us, spontaneous):
  F0 13 0B 0F [dir] 11 [currentParamHi] [paramLo] [v0] 00 00 00 00 F7
    data[6]=currentParamHi, data[7]=paramLo, data[8]=v0
  Fires when: any parameter changes from any source (HW knob turned, or the
  hardware echoing a value we just sent). Used for tone knobs, gate, amp out,
  amp select, cab/mic/axis/breakup live updates, bypass changes.

FORMAT B — DELETED 7/23/2026; it never existed on this connection. Earlier
  revisions described a RESP shape with a fixed 0x04 at data[6] shifting
  handle/paramLo/v0 one byte right. Confirmed absent: across ~20 replies in
  session-2026-07-23-131306.log byte 6 is always the block handle (0x04-0x0D,
  0x12-0x1B), and every reply is 14 bytes, leaving no room for an extra marker.
  It was a USB-CIN-framing artifact of the same family as C1.
  RESP messages are FORMAT A shaped, with dir=0x12 instead of 0x02.
  The handler still accepts both shapes; harmless, not worth removing.
  See C11 (resolved).

  *** FORMAT A / FORMAT B DISAMBIGUATION — CONFIRMED BUG, FIXED 2026-07-20 ***
  data[6]===0x04 is NOT a reliable Format B marker. A block's runtime handle
  can itself BE 0x04 (observed on MOD in certain chain orders), and a Format A
  message from that block also has data[6]=0x04. The two are indistinguishable
  from that byte alone.
    DETECTION RULE: before treating data[6]===0x04 as a Format B marker, check
    whether 0x04 exists as a live handle in currentChain. If it does, data[6]
    IS the handle and the message is FORMAT A. Only if no block in the current
    chain holds handle 0x04 may it be read as Format B.
    SYMPTOM IF WRONG: bytes parse one position off, paramLo never matches, and
    any block whose handle lands on 0x04 reports "state unknown yet" forever.
    First hit MOD; would equally have hit WAH, DIST or any other block.
    Fix lives in the sysex-handler.js bypass routing block.
  This is a second instance of the same failure mode as C1: treating a byte
  whose VALUE is 0x04 as a structural marker, when 0x04 is also a legal datum.

SEND (our app -> hardware):
  F0 13 0B 0F 00 11 [currentParamHi] [paramLo] [v0] 00 00 00 00 F7
  Hardware accepts Format A (no 0x04) for ALL params including cab/mic, then
  echoes back as Format A ASYNC. v1–v4 = 0x00 confirmed for all writes.

REQU (query one parameter):
  F0 13 0B 0F 01 11 [handle] [paramLo] F7
  *** [handle] IS THE BLOCK HANDLE FROM THE CHAIN MAP, NOT A LITERAL 0x07. ***
  Earlier revisions of this doc showed 0x07 hardcoded — a stale artifact from
  early captures where the amp happened to be allocated handle 0x07. Querying
  with a fixed 0x07 silently fails on any patch where the amp sits elsewhere.
  This single wrong byte is what blocked amp/cab bypass from Phase 7 until
  7/18. Confirmed against Avid traffic: it queries every block this way.
  [DELETED 7/23] A sentence stood here claiming "the 0x07 is a broadcast/
  wildcard instance the firmware resolves to the current block, and hardware
  replies as Format B with the real currentParamHi filled in." That is the
  pre-7/18 belief, and it survived directly BENEATH the correction that
  withdrew it, saying the opposite. There is no wildcard: query with the real
  handle. The Format B half of that sentence is also unconfirmed — see C11.

UNIVERSAL paramLo VALUES (identical for all 33 amps, all sessions):
  0x03 = Amp Out Level
  0x04 = Gate Threshold
  0x05 = Gate Release
  0x01 = Block Bypass      (EVERY non-amp chain block, on its own handle;
                            v0: 0x40=active, 0x3F=bypassed. Confirmed 7/18.)
  0x06 = Amp Bypass        (v0: 0x40=active, 0x3F=bypassed. ONLY on the AMP
                            handle — see the handle-context warning below.)
  0x0E = Bright toggle     (live: v0=127=ON, v0=0=OFF)
  0x0F = Amp Select        (raw v0 — NOT run through the (v+64)%128 formula)
  0x12 = Sync              (tremolo amps only — 14 zones, Section 11)
  0x13 = Tremolo On/Off    (tremolo amps only — v0=127=ON, v0=0=OFF)
  0x14 = Cab Bypass        (v0: 0x40=active, 0x3F=bypassed. ONLY on the AMP
                            handle — amp+cab are one block, one handle.)
  0x15 = Cab Type          (non-standard v0 — lookup table, Section 8)
  0x16 = Mic Type          (non-standard v0 — lookup table, Section 8)
  0x17 = Mic Axis          (v0: 0x3F=On-Axis, 0x40=Off-Axis — see C4)
  0x18 = Speaker Breakup   (standard continuous 0–127)

*** paramLo 0x06 / 0x14 ARE AMP-HANDLE-ONLY (confirmed 7/22). *** These are
  amp/cab bypass ONLY when the message arrives on currentParamHi (the amp
  handle). paramLo is scoped per block: 0x06 on another block's handle is that
  block's own parameter — e.g. Eleven SR REVERB Pre-Delay is paramLo 0x06 on
  the reverb handle (Section 23). The bypass router MUST gate 0x06/0x14 on
  bInst===currentParamHi, or a Pre-Delay turn is misread as an amp-bypass
  event and its readback is swallowed. Same bug family as the 0x04-handle case
  (C11): a value that is a control code in one context is plain data in
  another — disambiguate by handle, never by the value alone. Block bypass
  (0x01) is correctly handled on every block's own handle.

Tone knob paramLo values are PER-AMP — see Section 11.

CRITICAL — paramLo is NOT derived from the Avid XML sldX key name above
0x09. sldF -> paramLo 0x10, sldG -> paramLo 0x11 (NOT 0x0F/0x10 as the
letter positions would imply). Wireshark is the source of truth for
paramLo; XML is the source of truth for knob labels and tfxKey names only.
(This corrects the June research; see C3.)

DO NOT send CMD 0x11 before currentParamHi is set (<=0): causes a HW assert.


===================================================================
4. currentParamHi — RUNTIME HANDLE
===================================================================

currentParamHi is a runtime handle the firmware assigns to the amp block on
each patch load. It IS the instance byte in every CMD 0x11 message for that
patch. It changes every firmware session and varies by slot position. It
CANNOT be predicted, hardcoded, or read from the TFX body.

SOURCE: data[i+2] — the third byte of the typeA=0x07 triplet in the CMD 0x21
chain map. Triplet structure at data[6+]: [typeA][mid][third]. typeA=0x07 =
amp block; its third byte = currentParamHi. DO NOT change the data[i+2]
offset — confirmed correct across many captures.

Confirmed via round-robin capture (single session):
  A2: typeA=0x07 third=0x10 -> CMD 0x11 instance=0x10
  A1: typeA=0x07 third=0x1E -> CMD 0x11 instance=0x1E
  J2: typeA=0x07 third=0x2C -> CMD 0x11 instance=0x2C
Same patch across different sessions: 0x03, 0x74, 0x21, 0x2B — varies each time.

IMPLEMENTATION:
  Read from CMD 0x21 on EVERY patch navigation; store as currentParamHi.
  Use as the instance byte in all CMD 0x11 sends.
  Filter incoming CMD 0x11 by instance === currentParamHi.
  Reset to -1 on disconnect.

*** CHAIN-REORDER HAZARD — RESOLVED 7/18-7/19, kept for context ***
  currentParamHi is POSITION-DEPENDENT: moving a block makes the firmware
  assign it a new handle on next load, and a send using a stale handle hits
  whatever block now sits at that position (this corrupted gate parameters
  when the amp was moved). That hazard is REAL but is no longer a limitation:
  the chain map was solved 7/18 and every block's handle is now read from it
  on each patch nav, so sends are correct at any chain position. Bypass
  shipped 7/19 on that basis and is verified at six different amp handles
  including the amp last in the chain.
  THE RULE THAT REMAINS: never cache a handle across a chain map. Re-read
  currentChain after every CMD 0x21, and after every CMD 0x0D (below).

*** STEREO/MONO ALSO REASSIGNS HANDLES *** (confirmed 7/18)
  Every accepted CMD 0x0D rebuilds the post-amp half of the chain and fires
  a fresh CMD 0x21 with NEW handles for those blocks. The amp handle and all
  pre-amp handles are unaffected.

    Same patch, consecutive toggles:
      Stereo: amp 0x30, post-amp blocks 0x31–0x36
      Mono:   amp 0x30, post-amp blocks 0x3A–0x3F
      Stereo: amp 0x30, post-amp blocks 0x43–0x48

  No consequence today — every wired control (amp, tone, gate, cab, mic) sits
  at or before the amp. But any future post-amp block control MUST re-read the
  chain map after a 0x0D send. The Avid editor does exactly this: after each
  toggle it re-queries every parameter it displays.

  [DONE 7/18-7/19] The former "future fix" described here — identify every
  block in the chain map and store each block's handle per patch nav — is
  implemented. Blocks are identified by SLOT ID (not by the field once called
  typeA, which is a back-link), and the full chain is stored in currentChain
  on every map. See the chain map structure below.

  *** FX LOOP PLACEMENT RULE (confirmed 7/18 by Charlie, definitive) ***
  The FX Loop block has only FOUR legal chain positions:
    1. First in chain
    2. Immediately left of AMP-CAB
    3. Immediately right of AMP-CAB
    4. Last in chain
  No other placement is possible. Every other block may go anywhere.
  NOTE: both sample patches captured 7/18 have LOOP immediately RIGHT of
  AMP-CAB — the same case twice. The other three positions are unsampled,
  so reorder captures must exercise all four deliberately.

  THE FOUR POSITIONS BEHAVE AS AN ORDERED LIST (observed 7/18, both UIs):
      START  <->  left-of-AMP  <->  right-of-AMP  <->  END
  On the hardware front panel, highlighting the loop and scrolling moves it
  one step along this list, skipping every illegal position in between. In
  the Avid editor, dragging the loop and releasing snaps it to the nearest
  legal position rather than refusing the drop. Neither UI ever presents an
  illegal placement to the protocol.
  IMPLICATIONS:
   - The rule is almost certainly enforced in firmware, not just in the
     editor. Mirror it; do not invent our own policy.
   - We cannot learn the hardware's tolerance for an illegal placement
     through either UI, and deliberately sending one to a working unit is
     not worth the risk. Assume it is rejected.
   - Our chain row must treat the loop differently from other blocks:
     four discrete stops, not free placement. Design this in from the start.
   - AVID DRAGS THE LOOP ALONG WITH THE AMP when the two are adjacent, which
     is why the amp cannot be pushed past position 9 in the Avid editor while
     the loop sits to its right — you must park the loop elsewhere first.
     OUR APP DELIBERATELY DOES NOT DO THIS (agreed 7/19): dragging the amp
     leaves the loop where it is and, if that strands it, snaps the loop to
     its nearest legal position. Charlie prefers the freer behaviour. This is
     an intentional divergence from the Avid editor, not a defect.
   - Because both UIs resolve legality before sending, the reorder command
     most likely carries a resolved destination rather than a raw drop
     position. Expect a clean capture.

  CHAIN MAP STRUCTURE — SOLVED 7/18 (8 patches + TFX cross-check)

  MESSAGE:  F0 13 0B 0F [dir] 21 [11 triplets] [trailing] F7   (41 bytes)
  Triplet = [backLink][mid][handle]

  IT IS A LINKED LIST. [backLink] is the SLOT ID OF THE PREVIOUS BLOCK, not
  a type and not an allocation index. The trailing byte is the LAST block's
  own slot ID. Triplet 1 (the input block) back-links to itself as the head
  marker. Read it as:

    slotID(triplet N) = backLink(triplet N+1)     for N = 1..10
    slotID(triplet 11) = trailing byte

  *** SLOT IDs ARE FIXED PER BLOCK TYPE, IN EVERY PATCH *** (8/8, and
  independently confirmed against TFX Wst keys — see below)

    0x00  AMP-CAB        0x05  REVERB
    0x01  FX LOOP        0x06  DELAY
    0x02  VOLUME         0x07  DIST
    0x03  WAH            0x08  FX 1
    0x04  MOD            0x09  FX 2
                         0x0B  INPUT  (triplet 1; 0x0A unused)

  This is the correct and only reliable way to identify a block. Do NOT
  identify blocks by mid ranges — mid is the effect MODEL (Sec 23), and the
  generic FX slots host models from other categories, so ranges overlap.
  Slot ID says WHICH BLOCK; mid says WHICH MODEL is loaded in it.
  In particular FX 1 and FX 2 are distinguishable ONLY by slot ID: they can
  hold the same model (B2 has Parametric EQ 0x12 in both) and their chain
  order is not fixed (A3 has FX1 first, A4 has FX2 first).

  MAP ORDER = CHAIN ORDER (left to right as shown in the Avid editor).
  Triplet 1 is the INPUT block (mid 0x37 "Guitar In"; other input models
  0x38-0x40). Skip it — that leaves 10 triplets for the 10 chain blocks.

  AMP-CAB IS ONE BLOCK in the protocol, with two independent bypass flags.

  *** HANDLES ARE SEQUENTIAL IN CHAIN ORDER *** (8/8 patches)
    handle(position N) = handle(position 1) + N - 1        [N = 1..10]
    input block handle = handle(position 1) + 10
  Examples: A1 blocks 0x0E-0x17, input 0x18.  B1 blocks 0x46-0x4F, input 0x50.
  The base shifts on every reload and after every stereo/mono toggle, so the
  map must still be re-read — but triplets need no individual parsing.

  TFX CROSS-CHECK (this is what settled the field-1 question):
    Keys WorB..WorL / WstB..WstL, 11 slots, 8 bytes each from offset 208.
    Wst[letter] = SLOT ID — matches the chain map exactly.
    Letters run B..L in CHAIN ORDER: B = input, C..L = the 10 blocks.
    Per-block parameters follow the bypa[letter] keys later in the body;
    the amp block uses sld* keys instead of a bypa* key.

  BYPASS MUST BE QUERIED — NOTHING PUSHES IT TO US.
  After every chain map, query all ten blocks:
      F0 13 0B 0F 01 11 [handle] 01 F7     the nine ordinary blocks
      F0 13 0B 0F 01 11 [ampHandle] 06 F7  amp
      F0 13 0B 0F 01 11 [ampHandle] 14 F7  cab
  11 queries in total, which is what the Avid editor itself does at each load.
  *** DO NOT TEST BYPASS READBACK WITH THE AVID EDITOR OPEN. *** Our app adopts
  broadcasts regardless of who asked for them, so with the editor running
  alongside, ITS queries make our state look populated when we never asked for
  anything. This produced a false pass on 7/19: only amp and cab were being
  queried, yet all ten slots appeared to work. Verified afterwards — that day's
  log contains zero paramLo 0x01 queries from us. Any readback feature must be
  tested with the editor CLOSED before it is called working.

  BYPASS IS NOT IN THE CHAIN MAP. Patches B2/B3/B4 (same rig, same order,
  different on/off states) produce byte-identical maps apart from handles.
  Bypass is CMD 0x11 on the block's handle — see Section 3.

  *** CHAIN REORDER — SOLVED 7/19 ***
  THERE IS NO SEPARATE REORDER COMMAND. To reorder, send a COMPLETE CHAIN MAP
  back with dir=0x00, in the same 41-byte format the hardware broadcasts:

      F0 13 0B 0F 00 21 [11 triplets] [trailing] F7

  Build it by taking the current map and re-linking it into the desired order:
  keep each block's existing [mid] and [handle], and rewrite the back-links so
  they describe the new sequence (backLink of triplet N+1 = slotID of triplet
  N; trailing byte = last block's slotID). Triplet 1 remains the input block.
  Confirmed over four consecutive moves in one capture, every one decoding to
  exactly the move performed.

  HARDWARE RESPONSE: a dir=0x02 broadcast of the resulting map, then a
  CMD 0x03 dirty flag (F0 13 0B 0F 02 03 [slot] 01 F7).
  *** THE BROADCAST IS AUTHORITATIVE — ADOPT IT, DO NOT ASSUME OUR SEND STUCK.
  The hardware may return different [mid] and [handle] values than we sent.

  *** FX LOOP MODE IS GLOBAL, NOT PER-PATCH *** (confirmed 7/19)
  CMD 0x3C (Sec 6) selects Mono (L) / Mono-Stereo / Stereo. It lives in the
  editor's USER OPTIONS panel, alongside other global settings.
   - The mode is NOT stored in the TFX. Saving the same rig under all three
     modes changes only the checksum and three model ids (the loop and the two
     blocks after it) — there is no mode field anywhere in the file.
   - THE GLOBAL SETTING OVERRIDES THE PATCH. Uploading a TFX that was saved
     under Mono (L) while the unit is set to Stereo yields a Stereo loop. All
     three uploads in the test produced the same loop model.
   - The loop's model id is therefore a CONSEQUENCE of the mode, not a store
     of it. Observed: Mono(L) -> 0x2D (key LMMM), Mono-Stereo -> 0x30 (LYMS),
     Stereo -> 0x32 (LSMS). The first key character tracks the mode (M/Y/S).
     Three of the seven loop variants sampled; the rest are unexplained.
   - PRACTICAL: our app can infer the current mode from the loop block's mid
     in any chain map. No REQU for CMD 0x3C was observed — the editor never
     queries it — so whether one exists is untested.

  *** CHANNEL CONFIGURATION — WHAT THE MODEL VARIANTS MEAN *** (7/19)
  The variant index within a model family selects a CHANNEL CONFIGURATION —
  but the set of configurations a model supports is PER MODEL and CANNOT be
  inferred from how many variants it has.

  THE RULE (7/19, holds across all 30 direct observations, no exceptions):
      the LOWEST variant in a model family outputs MONO;
      every other variant in that family outputs STEREO.
  It follows directly from there being no stereo-in/mono-out variant anywhere:
  once a block must produce mono it must also accept mono, so only the bottom
  variant of a family can be mono-out.

  *** RETRACTED — a "correction" recorded earlier the same day *** An earlier
  revision of this section claimed C1 Chorus/Vibrato broke the pattern by being
  stereo-out in BOTH variants, and concluded that capability cannot be inferred
  from variant position. That conclusion was itself the product of incomplete
  data: C1 Chorus/Vibrato has THREE variants (mid 0x01/0x02/0x03) and only the
  upper two had ever been seen. With 0x01 included it is an ordinary
  three-variant family and the rule above holds. The lesson repeats the one
  from the chain-map defect — a pattern inferred from a partial family looks
  exactly like a broken pattern.

  EXCEPTION — FX LOOP. Its send and return are independent, so variant order
  carries no information about its output (0x31 is mono-out despite not being
  the lowest). Loop variants must each be observed.

  *** THERE IS NO STEREO-IN / MONO-OUT VARIANT. *** This single fact drives
  the whole propagation behaviour: the moment a block must produce mono it
  must also accept mono, which forces the block feeding it to produce mono,
  and so on BACKWARDS to the stereo source.
  CONSEQUENCE: placing a mono-only block (wah, distortion, volume...) anywhere
  in the post-amp section collapses EVERYTHING UPSTREAM of it to mono.
  Verified: moving WAH to the very end of the chain took LOOP 0x11->0x0F,
  ParamEQ 0x4F->0x4E, MultiChorus 0x5A->0x58, DynDelay 0x52->0x50 and
  Eleven SR 0x35->0x33 — the entire post-amp chain, in one move.
  Downstream is unaffected, because mono-in/stereo-out DOES exist: inserting
  mono DIST between MOD and DELAY left REVERB stereo (DELAY simply became
  mono-in/stereo-out 0x22->0x21).

  Pre-amp blocks are always mono because the amp is a mono device; stereo can
  only originate at or after the amp/cab (or at a stereo FX Loop return).

  UI IMPLICATION: dragging a mono-only block into the post-amp section is an
  audible change the user did not explicitly request. Warn, or at minimum
  reflect the resulting mono state in the chain row immediately.

  CHAIN ROW RENDERING SPEC (from Avid editor reference screenshots, 7/19):
   - Block ORDER comes from the chain map, not a fixed layout. Our current row
     uses the default order with FX1/FX2 hardcoded, which is wrong for most
     patches — this is the visible symptom of the old "assume default chain"
     limitation.
   - STEREO IS SHOWN PER CONNECTION: Avid draws a DOUBLE connector line
     between blocks where the signal is stereo and a SINGLE line where it is
     mono. The connector after block N is stereo exactly when block N's OUTPUT
     is stereo.
     Use the OUTPUT CHANNEL TABLE in Section 23 — 30 models resolved. It
     cannot be derived from variant rank (two models with the same variant
     count can differ), so anything not in that table gets a single line plus
     a logged warning naming the mid, rather than a guess.
   - AMP and CAB render as ONE block with two stacked labels, matching the
     protocol (one handle, two independent bypass flags at paramLo 0x06/0x14).
   - Bypassed blocks are drawn dimmed; active blocks lit.
   - ACCEPTANCE TEST: load a patch with a stereo post-amp section, then drag a
     mono-only block (e.g. WAH) to the very end. Every connector in the row
     must collapse to single-line. If it does, the variant decoding is right.

  WHY IT MAY DIFFER — CHANNEL RECONFIGURATION:
  The firmware recomputes mono/stereo propagation through the chain on every
  reorder and RE-INSTANTIATES any block whose input/output configuration
  changed, giving it a different model variant and a new handle. Observed:
  moving mono-only DIST in between MOD and DELAY changed MOD 0x05->0x04 and
  DELAY 0x22->0x21, both with new handles. The other three moves in the same
  capture changed nothing at all.
  So handles are NOT reassigned wholesale on reorder (unlike a stereo/mono
  toggle, which reassigns the whole post-amp group) — only affected blocks
  move. Re-read the broadcast either way.

  LEGALITY IS RESOLVED BEFORE SENDING. The editor never transmits an illegal
  arrangement: dropping VOL between AMP-CAB and LOOP resulted in a map with
  VOL placed on the FAR SIDE of LOOP. Our UI must do the same resolution
  before building the map (see the FX Loop placement rule above).

  CAPTURES NO LONGER NEED MOVE NOTES: consecutive maps fully describe what
  moved, since slot IDs name the blocks. Verified by reconstructing four
  documented moves from the data alone.

  HANDLES ALSO CHANGE ON SAVE — confirmed 7/26/2026. A save commit makes the
  firmware re-instantiate the patch and reassign block handles, exactly like a
  reorder does. Observed the amp handle walk 7D -> 0C -> 1A and 1C -> ... -> 42
  across successive saves in one session. Consequence: after a save, our
  currentParamHi points at the OLD amp handle. SW knob writes then hit a dead
  handle (knobs "go dead"), and incoming broadcasts arrive from the NEW handle
  and get dropped as mismatches ("instId 0x1d does not match currentParamHi").
  FIX (shipped 7/26): the isSave branch re-reads the chain map immediately after
  a save confirms, so currentParamHi and the effect handles refresh at once.
  See Sec 15.

  SELF-HEAL FOR HANDLE DRIFT (shipped 7/26). Belt-and-suspenders for any path
  that leaves currentParamHi stale: if HANDLE_RESYNC_THRESHOLD (5) CMD 0x11
  broadcasts in a row arrive for a handle we do not recognise, sysex-handler
  re-reads the chain map once (debounced HANDLE_RESYNC_COOLDOWN = 2000 ms) to
  resync, instead of ignoring them forever. Logs "Self-heal: ... re-reading
  chain map to resync". This is why a physical knob turn could revive dead SW
  knobs before the post-save fix existed — the HW broadcast tripped the resync.

  KNOB-WRITE FLOOD IS WHAT FORCES A BAD RESYNC — mitigation shipped 7/26. An
  un-paced knob drag sent one CMD 0x11 write per mouse-move (~48/s measured).
  That flood swamps the rack, which reassigns the amp handle MID-DRAG and starts
  broadcasting from the new one while we still hold the old currentParamHi — the
  "dead in both directions" state. ui.js now throttles all knob/slider writes
  through queueKnobSend (trailing, KNOB_SEND_INTERVAL = 60 ms, per-control),
  mirroring the tempo throttle. On-screen motion stays instant; only the HW
  write is paced, and the final value always lands. Pre-existing bug, not from
  the 7/26 UI work; reproduced on the prior build.

6. FULL COMMAND REFERENCE (0x00–0x50)
===================================================================

Legend: [SEND]=we can send it, [RECV]=hardware broadcasts it,
[DEAD]=receive-only, no send path exists on any known interface.

CMD 0x00 — Bulk TFX (patch body). Hardware broadcasts full 7-bit-encoded
  patch body on hardware-initiated save. Auto-captured to disk. [RECV]
CMD 0x01 — SEND_PATCH / bulk write. Send = load body to HW memory
  (Section 16). REQU (dir=0x01) = pull current slot's body back. [SEND/RECV]
CMD 0x02 — Current Rig Number. Send selects a slot; broadcast/RESP reports
  current slot. Used in save + navigation. [SEND/RECV]
  CONFIRMED RECALL FORM (7/23/2026) — this is how Avid changes patches and
  now how we do:
      F0 13 0B 0F 00 02 00 [slot] F7      slot is 0-BASED, no translation
                                          (A1=0x00, A2=0x01, D4=0x0F)
  The hardware echoes the requested slot in both the 0x03 and 0x02
  announcements. Verified on sequential navigation and on non-adjacent jumps.
  *** DO NOT USE MIDI PROGRAM CHANGE (C0 nn) FOR NAVIGATION. *** It works,
  but it triggers the rack's own front-panel recall behaviour ON TOP OF the
  load. Avid never sends a Program Change. See Section 20.
CMD 0x03 — Save Rig (commit to slot). Part of save sequence (Section 15). [SEND]
CMD 0x04 — Rig Get/Set Name (address-based). Used in save; also a cheap
  names-only bank scan path. [SEND/RECV]
CMD 0x05 — Patch Name. Broadcast = null-terminated ASCII name; send = set
  current rig name (plain ASCII, no 7-bit encoding, no framing, max 16
  chars). [SEND/RECV]
CMD 0x07 — Rig Volume knob broadcast. F0 13 0B 0F 02 07 [v0] 00 00 00 00 F7.
  v0 decoded as CMD 0x11. Range val=0 -> -24.0 dB, val=127 -> 0.0 dB.
  REQU form reads current value. [SEND via CC17 / RECV via 0x07]
CMD 0x3C — FX Loop mode. GLOBAL setting, not per-patch.
  Send:      F0 13 0B 0F 00 3C [mode] F7
  Broadcast: F0 13 0B 0F 02 3C [mode] F7   (echo carries the real value,
             unlike CMD 0x0D — decode it normally)
  mode: 0x01 = Mono-Stereo, 0x02 = Stereo, 0x00 = Mono (L) (INFERRED — the
        capture only ever moved up from Mono, so 0x00 was never observed).
        The editor's label "Mono (L)" implies a "Mono (R)" exists; not seen.
  See Section 4 for what it does to the chain. [SEND/RECV]

CMD 0x0D — Stereo/Mono. Send: F0 13 0B 0F 00 0D [val] F7. Broadcast:
  F0 13 0B 0F 02 0D [val] F7. val 0x01=Mono, 0x00=Stereo (both directions).
  Echo after our own send is always 0x01 — acknowledgement only, do not
  decode. See Section 10. [SEND/RECV]
  READ FORM (confirmed 7/23/2026): F0 13 0B 0F 01 0D F7
    -> F0 13 0B 0F 12 0D [00=Stereo | 01=Mono] F7
  This read IS reliable, unlike the post-send echo, and does not change state.
  *** PER-PATCH, NOT GLOBAL. *** This entry previously said global; that was
  wrong and contradicted the RMno note in Section 10. Corrected 7/23/2026
  after a hardware test in which adjacent patches held different states and
  each followed its own patch. Must be re-read on EVERY patch change.
CMD 0x11 — Live parameter read/write. See Section 3. [SEND/RECV]
CMD 0x20 — Effect Description (per-effect query). Effect string ID at byte 7,
  name at byte 25. [SEND/RECV]
CMD 0x21 — Chain Map / Rig Description. F0 13 0B 0F 01 21 F7 -> 11 triplets
  + trailing byte (41 bytes). Triplet = [backLink][mid][handle], where
  backLink = the PREVIOUS block's SLOT ID (a linked list, NOT a type tag),
  mid = the effect MODEL, handle = that block's CMD 0x11 instance byte.
  Identify a block by its SLOT ID, never by mid range. Full structure,
  slot-ID table and handle arithmetic: Section 4.
  *** The old reading "[typeA][mid][third], typeA=0x07=amp" is WRONG and
  caused a live defect — 0x07 is DIST's slot ID, so it found the block
  AFTER dist. See Sec 24 (7/19). Do not reintroduce it. ***
  Send with dir=0x00 to REORDER the chain (Section 4). Fires on every patch
  load and on chain changes. [SEND/RECV]
CMD 0x22 — Effect Count. [SEND/RECV]
CMD 0x34 — True Z impedance broadcast. Global, front-panel only. Auto-
  broadcasts on amp/cab model change (val=0x7E=Auto in that context). [DEAD-send]
CMD 0x36 — Output Volume. F0 13 0B 0F [dir] 36 [outSel]... See Section 18.
  outSel 0x00=Main, 0x02=To Amp1, 0x03=To Amp2, 0x04=Unit Vol, 0x06=query.
  CONFIRMED READ (7/23/2026): F0 13 0B 0F 01 36 [outSel] F7
    -> F0 13 0B 0F 12 36 [outSel] [v0] 00 00 00 00 F7
  The outSel byte is REQUIRED; the bare form returns nothing. Decode v0 with
  the standard continuous-knob rule (Section 7). Values are PER-PATCH.
CMD 0x37 — To Amp Source. F0 13 0B 0F 00 37 07 [slot] [val] F7.
  *** MUST be preceded by a CMD 0x3A query for that slot — sending without it
  causes a firmware assert. *** The 7/14 factory-reset incident was this
  command sent unqueried. With the query first the sequence is safe, but SW
  sends still do not move the HW source (cause unknown). See Section 18.
CMD 0x3A — To Amp Source query. REQU: F0 13 0B 0F 01 3A [slot] F7.
  RESP: F0 13 0B 0F 12 3A 07 [slot] [currentVal] F7. Required before any
  CMD 0x37 write. See Section 18. [SEND/RECV]
CMD 0x38 — Global Cabinet Bypass. Global override. Front-panel only. [DEAD-send]
CMD 0x3B — Master Mute (Main/Phones). F0 13 0B 0F [dir] 3B [channel] [state]
  F7. channel 0x00=Main, 0x01=Phones; state 0x00/0x01. SW send CONFIRMED
  7/29/2026, retracting the old "Front-panel only [DEAD-send]" reading — see
  "MASTER MUTE — MAIN / PHONES" in Section 18/C13 for the full detail.
  [SEND/RECV, no query form]
CMD 0x3D — Input Selector broadcast. F0 13 0B 0F 02 3D [val] F7 (value at
  data[6], NOT data[7]=F7). Values: 0x00=Guitar, 0x02=Mic, 0x03=Line L,
  0x04=Line R, 0x05=Line L+R, 0x06=Dig L, 0x07=Dig R, 0x08=Dig L+R,
  0x12=Re-Amp. Broadcast on input change only (not startup/patch change).
  INPUT IS GLOBAL, NOT PER-PATCH — confirmed 7/27/2026 (Charlie): it never
  changes with the patch, only when the user changes input. So input CCs
  (65/66/67) must NOT mark the patch dirty (same category as To Amp source);
  sendCC only lights the SAVE latch for PER_PATCH_CCS = [17] (Rig Vol). Since the
  rack does not announce input on connect/recall and there is no REQU to poll it,
  the app cannot reflect the live global input on connect — it currently forces
  Guitar at startup (see Sec 21, "reflect input" deferred).
CMD 0x40 — Tuner. See Section 9. [SEND/RECV]
CMD 0x41 — Tuner companion broadcast. Safe to ignore.
CMD 0x50 — Rig tempo, in microseconds per beat, as four 6-bit digits.
  Full encoding, ranges and the throttling warning are in Section 18.
  [SEND/RECV/BROADCAST]
  (This entry formerly read "Version/capabilities query, response 04 03 14 29,
  likely firmware version". That was wrong and is deleted, not amended —
  7/24/2026.)

Startup commands seen only in Avid editor USB capture (purpose unknown,
not required by Eleven Edit): 0x08, 0x0A, 0x35, 0x39.
  (0x3A and 0x3C were formerly on this list; both are now identified —
  0x3A = To Amp Source query, 0x3C = FX Loop mode. See above.)


===================================================================
7. VALUE ENCODINGS
===================================================================

CONTINUOUS KNOBS (CMD 0x11, 0x07, 0x36) — single-byte offset binary:
  DECODE: if v0 >= 0x40 -> val = v0 - 0x40   (range 0–63)
          if v0 <  0x40 -> val = v0 + 64     (range 64–127)
  ENCODE: v0 = (targetV127 + 64) % 128
  val 0–127 maps to 0.0–10.0 on display.
  Sentinels: min = 0x40 00 00 00 (val 0); max = 0x3F 7F 7F 7F (val 127).
  CONFIRMED 2026-08-27: this sentinel rule applies to CMD 0x36 (To Amp 1/2
  volume) as much as 0x11/0x07 — it just hadn't been implemented there.
  sendToAmpVolume (transport.js) always sent a flat v0+00 00 00 00 tail,
  which for the true max landed ~0.19 dB short of +12.0 (asking for the
  BOTTOM of v0's step, not the top) — the same "9.9 bug" shape as the
  amp Tremolo Speed knob that started this rule on 7/23. Fixed and TESTED
  LIVE (Charlie, 2026-08-27): both To Amp knobs now hold exact min/max/
  0.0-centre. sendMasterVolume (same CMD 0x36 family, chain-strip MAIN
  VOL) is NOT a canvas knob — Charlie confirms it's the stepper/value-box
  control and is already exact at every value checked, so this gap does
  not apply there.

MULTI-BYTE CMD 0x11 VALUES (35-bit) — added 7/23/2026:
  *** SCOPE WARNING (added later the same day). The formula below does NOT
  drive the DISPLAY of continuous knobs. Speed's displayed value is the plain
  single-byte decode above, verified on nine messages against the rack's own
  readout (0x50 -> 1.3, 0x4A -> 0.8, 0x60 -> 2.5, 0x1F -> 7.5, exact to the
  tenth). This formula returns 6.28, 5.87, 7.52 and 2.56 for those same
  messages. Use the single-byte decode for display. ***
  A CMD 0x11 value is FIVE 7-bit bytes, not one. Most controls put everything
  in v0 and leave v1..v4 at the sentinel, which is why the single-byte rule
  above works for them. The full quantity is:
      N   = v0<<28 | v1<<21 | v2<<14 | v3<<7 | v4        (35 bits)
      raw = (N - 0x400000000) >> 3                       (signed)
      display = 64 + raw / 2147483647 * 63               (0-127)
  Verified against TFX-derived raws. 0x40 00 00 00 00 = 0 (centre);
  0x7F 7F 7F 7F 7F = full positive.
  *** WHEN CAPTURING WITH USBPcap, THE FINAL 4-BYTE GROUP OF EVERY MESSAGE IS
  LOST *** — proven by a name response reading "Bassguy 5" for "Bassguy 59".
  For a 0x11 reply that costs the 5th value byte. Our own app logs are not
  truncated; prefer them for byte-level work.

  TRAILING BYTES — RESOLVED 7/23/2026. They are the LOW-ORDER BITS of the same
  35-bit quantity: not a per-control signature, not padding. Two rules:
    1. THE 0x10 IN A BROADCAST IS ADDED BY THE RACK. The final byte of every
       hardware broadcast is 0x10 higher than the corresponding write. Proven
       against Avid's own traffic (Avid_Shark_Sync_Test.pcapng): Avid writes
         00 11 <handle> 12 40 00 00 00 00
       and the rack echoes
         02 11 <handle> 12 40 00 00 00 10
       Writes must NOT include it. Seen on Sync and Speed alike.
    2. CONTROLS DIFFER ONLY IN PRECISION. Depth and Sync are quantised to the
       byte, so their broadcasts always read v0 00 00 00 10. Speed carries real
       sub-step precision, so its low bytes vary — v0=0x00 was observed with
       both 00 00 00 10 and 7F 7F 7F 1F inside one sweep, either side of centre.

  ENDPOINT SENTINELS ON WRITES. Sending v0 with 00 00 00 00 asks for the BOTTOM
  of that step. Byte-quantised controls cannot tell; Speed can, and returned
  9.9 when asked for 10.0. sendParamWrite() therefore sends:
      v127 >= 127  ->  3F 7F 7F 7F 0F     (true maximum)
      v127 <= 0    ->  40 00 00 00 00     (true minimum)
      otherwise    ->  v0 00 00 00 00     (unchanged)
  Note 0F rather than 1F in the final byte, per rule 1.

  *** RETRACTED — an earlier revision of this block said Speed writes failed
  because the trailing bytes were malformed, and that the rack forced Speed to
  0 in response. BOTH WRONG, and the wrong diagnosis stood for a day. Speed
  writes failed because the rack IGNORES any Speed write while Sync is on a
  division (Section 11, TREMOLO). The trailing 00 00 00 00 was structurally
  correct all along — byte identical to Avid's own Sync write. ***

TOGGLES (Bright, live) — do NOT use the continuous decode:
  Live CMD 0x11: v0=127=ON, v0=0=OFF.
  In TFX body: raw 0=OFF, 1=ON (see Section 13 toggle note).

BYPASS (amp & cab, live) — check v0 DIRECTLY, do not decode:
  v0=0x40 = active,  v0=0x3F = bypassed.

MIC AXIS (live) — check v0 directly:
  v0=0x3F = On-Axis,  v0=0x40 = Off-Axis.   (Corrected 7/16 — see C4.)

AMP SELECT (paramLo 0x0F): raw v0 used directly (NOT the (v+64)%128 formula).
  Full v0->amp table is AMP_SELECT_LIST in protocol.js (Section 12 scheme B).

CAB TYPE / MIC TYPE: non-standard, require lookup tables. See Section 8.

32-BIT VALUES in TFX body (amp model, cab type raw): signed int32,
  little-endian in the body's 8-byte key/value pairs. Amp model also appears
  as a 32-bit selector in some CMD 0x11 contexts assembled big-endian
  (v0<<24|v1<<16|v2<<8|v3). Use the integer maps in Section 12.

10. STEREO / MONO
===================================================================

PER-PATCH, and FULLY BIDIRECTIONAL (bidirectional confirmed 7/18/2026;
per-patch confirmed 7/23/2026). An earlier revision called this global, which
never squared with the per-patch RMno key noted below. A hardware test settled
it: adjacent patches held different states and each followed its own patch.
Re-read it on every patch change — see REQU MONO in Section 5, which is a
reliable read, unlike the post-send echo described below.
Earlier docs called this receive-only; that was wrong — the send path exists,
it is just not exposed on the Eleven Rack front panel in an obvious way. The
Avid editor drives it from a small button on its chain graphic.

SOFTWARE SEND (confirmed 7/18 from Avid USB capture + working build):
  F0 13 0B 0F 00 0D [val] F7
  val: 0x01 = Mono,  0x00 = Stereo
  8 bytes. No query-first, no preamble, no length byte.

  *** Do NOT insert a 0x06 (or 0x04, or 0x07) before [val]. *** Those bytes
  appear in USB captures as CIN framing and are stripped by our bridge. A
  literal 0x06 in the payload is read by the hardware AS the value, so every
  send resolves to the same state (Mono) and Stereo becomes unreachable.
  See the USB-MIDI FRAMING block in Section 2.

HARDWARE BROADCAST (front-panel or Avid-editor change):
  F0 13 0B 0F 02 0D [val] F7
  val: 0x01 = Mono,  0x00 = Stereo   (same sense as send; message is the
  same shape as the send with only the direction byte differing)

ECHO AFTER OUR OWN SEND — UNRELIABLE, DO NOT DECODE:
  The hardware answers our send with F0 13 0B 0F 02 0D 01 F7 regardless of
  the value sent or the resulting state. It is an acknowledgement, not a
  state report. Decoding it drives the UI to the wrong state.
  Handling: transport.js sets suppressMonoEcho before each send;
  sysex-handler.js drops exactly one incoming CMD 0x0D and clears the flag.
  Unsolicited broadcasts (front panel) are never suppressed and decode
  normally. Our own display is set optimistically at click time.

TFX: key RMno (patch-wide section of the body — see the heading note in
  Section 14; this is PER-PATCH, not device-wide), body byte 124.
  0=Stereo, 1=Mono.
  Matches the wire value sense. Read on patch load.

CHAIN-MAP SIDE EFFECT: every accepted 0x0D reassigns the runtime handles of
  all post-amp chain blocks and fires a fresh CMD 0x21. See Section 4.

UI: clickable badge at the END OF THE CHAIN ROW, right after the last block.
  MONO = amber, STEREO = green (matching an active chain block) — recoloured
  7/24/2026 because the old dim-grey STEREO was near invisible. A connector
  line precedes the badge in the same stacked-line style as a between-block
  arrow: TWO lines when STEREO, ONE when MONO. That line tracks the BADGE
  state by deliberate choice (user, 7/24), NOT the last block's output channel
  count, so it can differ from the connector between the final two blocks.
  The badge is FIXED WIDTH (sized for STEREO) so it does not resize on the
  switch to MONO, and sits tight after the last block; the tempo field holds
  the far-right edge of the strip.
  300 ms click lockout to prevent accidental double-fires (the hardware
  itself has no minimum interval — it accepted machine-gun toggling from the
  Avid editor without complaint).

TREMOLO FEATURE SET — SOLVED 7/23/2026. Four controls, on the 15 amps that
have it: Lux Vib/Norm, Black Vib/SR/Mini/Duo, AC Hi Boost and all eight DC.
      0x10  Depth      plain knob
      0x11  Speed      plain knob, but see the interlock below
      0x12  Sync       14-zone selector
      0x13  On/Off     toggle, v0=127=ON / v0=0=OFF (same encoding as Bright)
A contiguous block. 0x13 exists ONLY on the hardware front panel — Avid's
editor has no such control and the per-amp XML does not describe it. On the
rack it shares a physical button with Bright, repurposed by screen; that is a
front-panel convenience, not a protocol fact, and they are separate params.

SYNC — 14 ZONES. On the wire Sync is a CONTINUOUS 0-127 value the firmware
quantises. Zone width 10, first and last truncated to 4, total exactly 128:
      0-3 OFF | 4-13 zone 1 | ... | 114-123 zone 12 | 124-127 zone 13
      index = (v < 4) ? 0 : min(13, 1 + floor((v - 4) / 10))
      write = zone centre: 0 for OFF, else min(125, 8 + 10*(index-1))
Divisions in order: whole note, then dotted / plain / triplet for half,
quarter, eighth and sixteenth. 1 + 1 + 12 = 14 entries.
DERIVED FROM two front-panel sweeps at different tempos that agree: at 120 BPM
the Speed broadcast changed at decoded 64, 74, 84, 94, 104, 114, 124 (zones
7-13); at 32.1 BPM only at 114 and 124 (zones 12-13). Slower divisions fall
below the Speed floor and read 0 — hardware behaviour, not a decode fault.
ORDER CONFIRMED INDEPENDENTLY: a dotted note is slower than the triplet before
it, so displayed Speed must dip at zones 8 and 11. It does — 1.3, 0.8, 2.5,
5.0, 4.2, 7.5 at 120 BPM.

*** THE SYNC/SPEED INTERLOCK IS A MODE, NOT A PROTOCOL DEFECT. ***
  Sync on a division: rate = rig tempo x division. Speed is an OUTPUT and the
    rack IGNORES every Speed write. Confirmed in Avid_Shark_Sync_Test.pcapng —
    Avid sent ~40 Speed writes with v0 ranging 0x16-0x2D and the hardware
    echoed the SAME unchanged value back every time.
  Sync OFF: Speed is an absolute rate and tempo is irrelevant. The only state
    in which Speed is writable.
  The rack's own Speed knob CLEARS SYNC TO OFF — that is how it hands control
    back. Avid never does this, so Avid's Speed knob is inert whenever Sync is
    engaged. An Avid limitation, not a rack one.
  OUR RULE (better than Avid): moving Speed sends Sync=OFF first, once per
    drag, then writes Speed normally. Mirrors the hardware and keeps the
    control live at all times.
  DO NOT reintroduce a write guard or grey the knob out. Both were tried on
    7/23 and both are worse than modelling the mode.

BRIGHT TOGGLE NAMING. paramLo 0x0E is called MOD on SL100 Drive and Bright on
every other amp that has it. AMP_TONE_PARAMS carries the per-amp label and the
button reads its text from there. Do NOT match on the string 'Bright' to decide
visibility, or that amp's button vanishes — match on paramLo 0x0E.


PARAMETER STORAGE IS PER CHAIN SLOT, NOT PER AMP MODEL (confirmed 7/24/2026,
hardware, cross-checked against the Avid editor).
  The amp block holds ONE set of parameter values, seeded from the TFX on
  patch load and persisted to that slot thereafter. An amp model does not own
  storage; it only determines WHICH paramLo values are exposed, in what order,
  and under what labels. The table above is a per-model VIEW over shared
  storage.

  CONSEQUENCES, all verified:
    - Changing amp model does NOT clear or reset any value. Every stored
      value survives, including paramLos the new model does not display.
    - Going from an 8-knob amp to a 3-knob amp hides five values; they are
      retained and reappear on returning to an 8-knob model.
    - A paramLo shared by two models under DIFFERENT NAMES is ONE value.
      Editing 59 Tweed's "Tone" and then selecting a 92 Treadplate shows
      that value on "Treble". Confirmed by direct test: Treadplate Treble
      7.4 -> switch to Tweed -> set Tone to 2.2 -> switch back -> Treble
      reads 2.2.
    - Sync (0x12) survives a model change across families for the same
      reason: 65 AC Boost -> any DC model keeps the selected division.

  This is hardware behaviour and Avid exhibits it identically. It is NOT a
  bug and must NOT be "corrected" in software. There is no mapping table to
  build and no knob-count reconciliation to do — whatever the rack reports
  for a paramLo is the truth.

  WHAT THIS MEANS FOR THE APP: after an amp model change, RE-READ the block.
  Do not carry values forward, and do not assume a same-layout change (e.g.
  Treadplate Vintage -> Modern) needs no refresh. See "AMP MODEL CHANGE —
  REFRESH SEQUENCE" below.


AMP MODEL CHANGE — REFRESH SEQUENCE (implemented 7/24/2026).
  Amp type is CMD 0x11 paramLo 0x0F — a PARAMETER INSIDE the amp block. It is
  NOT a chain map change. The block's slot ID and runtime handle are
  unchanged by it.
    DO NOT add a chain map request to this path. That distinguishes it from
    the DIST/REVERB model change (CMD 0x21), where the firmware assigns a
    NEW handle and a chain map re-read is mandatory. Confusing the two costs
    a wasted round trip and reintroduces a handle race that does not exist
    here.

  SEQUENCE, on the 0x0F echo (fires for our dropdown, the rack's front panel,
  and the Avid editor alike — all three arrive at the same handler):
    1. setCurrentAmp() relabels/reorders the tone stack from AMP_TONE_PARAMS
       and blanks every knob to 64 / "--".
    2. Wait AMP_CHANGE_SETTLE ms.
    3. Query the amp block's paramLo set against the EXISTING handle.
  Knobs read "--" for the settle period, then fill with the stored values.

  THE BUG THIS FIXED: step 3 did not exist. Step 1 blanked the knobs and
  nothing ever asked the hardware again, so every tone control read "--"
  after any amp change, even between two models with identical layouts.
  Avid appeared to "remember" values only because it re-reads.

  The paramLo set is built by ampBlockParamLos() in transport.js, shared with
  the post-nav pull (Section 3 / Primer code map) so the two paths cannot
  drift apart. Note that the nav pull's private paramQuery() helper also
  increments the Dev timings query counter and must NOT be reused from other
  paths; ampParamQuery() exists for that reason.

===================================================================
13. TFX BINARY FORMAT
===================================================================

A .tfx file = [56-byte header] + [body]. Body == decode7bit(SEND_PATCH
payload). A 968-byte body -> 1024-byte file. All sources (Avid Editor,
ElevenHack, Eleven Edit, HW save) produce SHA-256 identical files for the
same patch content.

56-BYTE HEADER:
  bytes 0–3   total file size, big-endian uint32 (e.g. 0x00000400 = 1024)
  bytes 4–7   zeros
  bytes 8–23  magic "DigiElvRELVhRig " (16 bytes, space-padded)
  bytes 24–55 zeros
  Load compatibility check: magic begins "DigiElv" at offset 8.

BODY LAYOUT:
  bytes 0–3   version quadlet
  bytes 4–7   signature/headerCode (changes when content changes)
  bytes 8–35  rig name, 7 quadlets (reversed byte order per quadlet)
  byte 36+    TOC / global params, then per-effect sections

KEY ENCODING ("quadToKey"): read 4 raw bytes, reverse to get the key name.
  e.g. raw 0x36 0x64 0x6C 0x73 reversed = "6dls" (amp model marker);
       raw 0x37 0x64 0x6C 0x73 reversed = "sld7".
  Every key is immediately followed by its 4-byte little-endian value
  (8-byte pairs). Key search scans the whole body, so it is position-
  independent and works regardless of chain order.

VALUE ENCODING (continuous knobs — gate, amp out, rig vol, tone, breakup):
  Signed 32-bit int, linear across the full int32 range.
  INT32_MIN (0x80000000) = 0% ; INT32_MAX (0x7FFFFFFF) = 100%.
  To 0–127: Math.round((signed - (-2147483648)) / 4294967295 * 127).
  Helper gateRawToV127(signed) does this.

TOGGLES in TFX body (e.g. Bright): raw 0=OFF, 1=ON. Do NOT run through
gateRawToV127 (which would map 0 to the midpoint 64). Use: signed !== 0 ? 127 : 0.

7-BIT DECODE (protocol.js — the trusted version):
  function decode7bit(enc){
    const res=[]; let begin=0,shift=1,i=0,len=enc.length;
    while(begin+i<len-1){
      let v=(((enc[begin+i]&0xFF)<<shift)&0xFF)+(((enc[begin+i+1]&0xFF)>>(7-shift))&0xFF);
      res.push(v&0xFF); shift++;
      if(shift===8){shift=1;begin++;} i++;
    }
    res.push(((enc[len-1]&0xFF)<<shift)&0xFF);
    return res;
  }
7-BIT ENCODE: use ONLY the encode7bit in protocol.js. encode7bit(968-byte
body) must produce exactly 1107 bytes. ElevenHack's encode7bit does NOT
correctly invert this decode — do not use it (causes "Bad Patch Data").

15. SAVE PROTOCOL (software-initiated commit to slot)
===================================================================

STATUS: implemented. Rename-on-save implemented (Phase 4a). CORRECTED
2026-08-11 (see WITHDRAWN note below for the full incident) — every step
but the first addresses the target by RAW SLOT NUMBER, no bank/num split
anywhere:
  Step  Cmd     Format                          Example (slot 0x67 = Z4)
  1     0x05    name (plain ASCII)              F0 13 0B 0F 00 05 [name] 00 F7
  2     0x03    [raw_slot] [0x00]               F0 13 0B 0F 00 03 67 00 F7
  3     0x04    [0x00] [raw_slot] [name] [00]   F0 13 0B 0F 00 04 00 67 [name] 00 F7
  4     0x02    [0x00] [raw_slot]               F0 13 0B 0F 00 02 00 67 F7
  raw_slot = 0–103. Name: plain ASCII, max 16 chars, null-terminated in
  Steps 1 and 3. Step 3's leading byte is a constant 0x00, NOT
  bank=floor(slot/4) — see WITHDRAWN note; confirmed by decoding a live
  Wireshark capture of Avid's own "Save Rig To…" saving to a different
  slot (AE_Save_to_Another_Slot_Capture.pcapng, 2026-08-11).
  HARDWARE RESPONSE, confirmed the same capture, in order: CMD 0x05 (name
  echo), CMD 0x03 dirty-flag-SET for the ORIGINAL/currently-loaded slot
  (the name edit alone dirties it — a side effect of Step 1, unrelated to
  the target slot). Then, once all four of OUR sends have gone out: a
  spontaneous CMD 0x00 bulk TFX broadcast for the TARGET slot — this is
  the exact same "hardware save" signal handleBulkTfxData's isSave branch
  (sysex-handler.js) already looks for, confirming that mechanism
  generalizes correctly to a different-slot commit with no change needed
  there — followed by echoes of Steps 3, 2 (now dirty-flag CLEARED for the
  target), and 4 (slot confirm) in that order.

*** HARDWARE SAFETY — raw_slot MUST STAY 0-103 (CONFIRMED, 2026-08-28). ***
Sending this save sequence with raw_slot outside 0-103 — e.g. the raw
unified slot index Eleven Edit uses internally for factory space
(104-207, see Sec on factory patch navigation) — does NOT fail cleanly.
Charlie confirmed live: while on a factory patch (post the 2026-08-28
CMD 0x02 decode fix, so currentSlot correctly read >103), Save to Rack
sent that raw value directly as Step 3/4's slot byte, BEFORE the
translate-to-user-slot guard (defaultRackSaveTarget, index.html) existed.
The name update PARTIALLY TOOK — briefly visible on the hardware in the
factory slot — but further interaction with the unit caused a BSOD.
A second attempt (name-only, no further interaction) appeared to "stick"
immediately after saving, but reading back the slot after a nav-away-and-
back showed the ORIGINAL factory name — the write did not actually
persist, it just looked like it had until the unit's next real read.
NEVER send this sequence with raw_slot > 0x67 (103). Eleven Edit now
guards this two ways: saveCurrentPatchToSlot (capture-scan.js) refuses
outright if ever called with a slot past MAX_SLOT, and Save to Rack's
default target is translated to the corresponding USER slot before this
sequence is ever built (defaultRackSaveTarget, Stage 4, 2026-08-28) — see
Session Log for the full incident. Same danger class as CMD 0x37 (Sec 18)
in that an out-of-range/invalid send corrupts state rather than failing
safely, though via a different mechanism and command.

RENAME: Step 1 (CMD 0x05) IS the rename. Passing any name string renames
the patch in hardware memory before committing. saveCurrentPatchToSlot()
in capture-scan.js accepts an optional nameOverride param; if supplied it
updates currentPatchName and the display element before sending. Rename
without a subsequent commit (Steps 2–4) changes the working name only —
not persisted to the slot until Step 4 fires.

SAVE TO RACK + AUTO TFX (Phase 4a, via SAVE ▾ → Save to Rack…):
saveToRackAndDisk(name) calls saveCurrentPatchToSlot(name) then waits
500 ms for the commit to settle before calling captureCurrentPatchNow().
The TFX file is written with the new name since currentPatchName is
updated before the capture request fires.

Hardware responds with dirty-flag clear, slot confirm, full bulk broadcast.
SAFETY NOTE: software save does NOT trigger the hardware-save auto-export
(the CMD 0x04 echo arrives AFTER the bulk broadcast in software save, but
auto-export detection needs it BEFORE).
*** WITHDRAWN THEN RE-CONFIRMED, 2026-08-11 — "protocol is identical to
current save, only the target slot number changes" (the line that used to
be here) turned out to be RIGHT about the overall shape (Steps 1-4, same
commands) but WRONG about one specific byte format: Step 3's
[bank][num] split. Full incident: a slot-picker UI was built on the old
(unverified) assumption, substituting the target slot into Steps 2-4 while
deliberately not recalling it first (so the live edit buffer stays
intact) — Charlie's live test showed the commit landing on the ORIGINAL
slot instead of the target. This exact assumption had never actually been
exercised with a target different from the currently-loaded slot before
that test; every real save prior to 2026-08-11 was always
slot === currentSlot, so a [bank][num] split had nowhere to diverge from
the correct [0x00][raw_slot] format — for anything in Bank A specifically,
bank=0 and num=rawSlot, so the two formats are byte-IDENTICAL by pure
coincidence, and Bank A is where most day-to-day saves land. ROOT CAUSE
CONFIRMED (not a guess) via Charlie's Wireshark capture of Avid's own
"Save Rig To…" saving to Z4 (AE_Save_to_Another_Slot_Capture.pcapng):
Step 3 is genuinely [0x00 constant][raw_slot], same addressing as Steps
2 and 4, both of which our code already had right. Bonus context: this
exact mistake (bank/num split where the real format is [space/0x00][raw
slot]) had already been found and fixed ONCE before, on CMD 0x04's sibling
READ form (sendPatchNameQuery, transport.js, 2026-08-03's "B1-B4 show
a1-a4" bug) — that fix was never generalized to this WRITE form, which is
how the same mistake survived here for months. Sec 15's step table above
is now corrected in place; code fix in saveCurrentPatchToSlot
(capture-scan.js). RE-TESTED LIVE, CONFIRMED WORKING (Charlie, 2026-08-11:
"Nailed it works good now"). See Session Log 2026-08-11 for the full
incident.

POST-SAVE HANDLE REFRESH (7/26/2026). A commit re-instantiates the patch and
REASSIGNS block handles (see Sec 4), so after the save-confirm bulk broadcast
our currentParamHi and effect handles are stale — SW knobs would write to a
dead handle until a HW broadcast tripped the self-heal. The isSave branch now
re-reads the chain map right after confirming a save (logs "Post-save:
re-reading chain map ..."), which refreshes currentParamHi, currentChain,
bypass, and any open effect panel. This is also where the knob-colour baseline
and FX-truth baselines are re-anchored to the just-saved values, and the SAVE
dirty latch is cleared (see Primer, 7/26 UI features).

SAVE/CAPTURE MUST NOT REPAINT LIVE KNOBS FROM THE BODY (7/27/2026). Both bulk
readback branches (isSave, and the manual/disk/nav-sync branch) decode the body
to identify the amp and set discrete controls. They must NOT re-decode the
continuous red-tracked knobs (gate, amp out, tone, To-Amp vols) and repaint them
over the values already shown, because:
  - The TFX body stores each knob as a high-res signed int32; the live CMD 0x11
    protocol carries it as a coarse 0-127. Converting body->0-127 (gateRawToV127)
    can round ONE unit off the live value. Values are not wrong (~0.08 on a 0-10
    scale, inaudible), but the pixel-perfect knob-colour comparator flags the
    variance as PHANTOM RED — persistent on Save-to-Disk, a red->amber flash on
    Save-to-Rack, and different knobs on different amps (all one cause).
  - setCurrentAmp() -> updateToneKnobs() BLANKS the tone row to "--"/midpoint on
    re-render, so on a same-amp save the row is wiped; the body repaint was the
    only thing refilling it (regression seen 7/27 when the repaint was first
    removed outright).
RULE (shipped 7/27): compute ampChanged = (decoded key !== currentAmpKey). Call
setCurrentAmp ONLY when ampChanged. Repaint the continuous knobs from the body
ONLY when (ampChanged || REQUEST_BULK_ON_NAV) — i.e. only when there is no live
truth to preserve (row was just re-rendered, or legacy bulk-on-nav populated
nothing live). On a normal same-amp save the live knobs are left untouched:
no blanking, no phantom red; captureKnobBaselines then snapshots the live values
so baseline == display. Discrete controls (cab/mic, mono) are always safe to
apply. Nav itself never enters these branches (targeted pull populates live).

NAME BEHAVIOUR (for reference — working as intended):
  - Save to Rack writes the name INTO the patch (CMD 0x05) before commit, then
    captures the TFX; the file's internal name and its filename both match.
  - Save to Disk only sets the filename (currentPatchName, with a "_manual"
    suffix via the manual-capture path); it does NOT write the name into the
    patch body, so the file's internal name stays whatever the buffer held.
    On reload the app reads the INTERNAL name, so a disk-saved file can load
    back showing a different name than its filename. Charlie confirmed 7/26
    this is intended; documented so it is not "fixed" by mistake.

16. LOAD TFX PROTOCOL (file -> hardware memory)
===================================================================

STATUS: implemented ("Load TFX"), round-trip verified.
  Step 1 — bulk write (memory only, does NOT commit to a slot):
    F0 13 0B 0F 00 01 [encode7bit(body)] F7
    body = TFX file minus the 56-byte header. encode7bit(968) -> 1107 bytes.
  Step 2 — name write:
    F0 13 0B 0F 00 05 [ASCII name] 00 F7
Hardware echoes bulk data back as ASYNC (dir=0x02, cmd=0x01); the SEND_PATCH
handler decodes it (payload at position 6). Load accepts any file with
"DigiElv" magic at offset 8. Round-trip: capture -> save -> load -> capture
-> SHA-256 matches.

17. BANK EXPORT / IMPORT ("Export All Rigs…" / "Import Rigs…")
===================================================================

STATUS: IMPLEMENTED, TESTED LIVE 2026-08-10 (Charlie: multiple clean full
exports, partial and zip-sourced imports, a deliberately-broken import
correctly listing every bad entry). Full byte-level evidence, the
abandoned-approach saga, and the race-condition bug hunt live in the
Session Log 2026-08-10 entries — this section states the settled result.

EXPORT ("Export All Rigs…") — RECALL-BASED, same core mechanism as the
existing (still-hidden) Scan Bank feature: CMD 0x03/0xC0 recall each slot
in turn, settle (SCAN_SETTLE_MS, state.js — 200ms, lowered from an
untuned 400ms guess 2026-08-10), then REQU SEND_PATCH. Reuses
capture-scan.js's scanSlot() directly rather than a separate
implementation (bank-transfer.js). Visibly walks all 104 slots on the
front panel, same as ElevenHack's method — the price of reliability, see
ABANDONED APPROACH below for why this wasn't the invisible method.
  OUTPUT (main.js, export-bank IPC): for each slot, a normal .tfx (56-byte
  header + body, Sec 13 format, identical to a single-patch capture) named
  from the patch's own embedded name. Filenames disambiguated on repeat
  in ENCOUNTER ORDER with a "-N" suffix — first occurrence bare, second
  "-1", third "-2", etc. — CONFIRMED to match Avid Editor's own
  disambiguation convention byte-for-byte (Session Log 2026-08-10: a real
  Avid export of 104 "-unused-" duplicates produced exactly
  "-unused-.tfx", "-unused-1.tfx", ... "-unused-102.tfx", same scheme).
  Writes a loose folder of these files PLUS an XML index PLUS a .zip of
  both (Charlie's call: keep all three, never delete the loose files
  after zipping). XML shape (matches Avid's own):
    <?xml version="1.0"?>
    <eleven>
      <hardware type_="string">"Eleven Rack"</hardware>
      <patch_list>
        <patch>
          <bank type_="string">"A1"</bank>
          <file type_="string">"PatchName.tfx"</file>
        </patch>
        ...
      </patch_list>
    </eleven>
  Always all 104 slots — export never asks the user which to include.
  There is no hardware signature for "this slot is empty"; an unused slot
  is exported and named exactly like any other patch (its stored name is
  literally "-unused-" on an untouched factory slot — not a sentinel we
  detect, just what's really stored there).
  ZIP CONTAINER: dependency-free, hand-written (src/js/zip-writer.js) —
  this project carries zero runtime npm dependencies by design. Standard
  local-file-header + central-directory + EOCD structure, DEFLATE via
  Node's built-in zlib when it helps, STORE otherwise. buildZip() writes,
  readZip() reads (scans backward for the EOCD record rather than
  assuming a fixed offset, so it isn't limited to zips this app wrote —
  Windows' built-in zip and 7-Zip's defaults both parse fine, same STORE/
  DEFLATE methods). Round-trip verified byte-exact.

IMPORT ("Import Rigs…") — DIRECT BY-SLOT WRITE, Avid's own real
mechanism (decoded from a live Wireshark capture of Avid Editor's actual
"Load All Rigs from Computer", Session Log 2026-08-10), NOT the
recall-based method export uses. Two writes per slot, no recall:
    F0 13 0B 0F 00 00 [slot] [encode7bit(968-byte-class body)] F7
      -> HW echoes it back (dir 0x02, same cmd)
    F0 13 0B 0F 00 04 00 [slot] [ASCII name] 00 F7
      -> HW echoes it back (dir 0x02, same cmd) — routes through the
         existing CMD 0x04 name-enum handler (handlePatchNameEnumReply,
         sysex-handler.js), which harmlessly also refreshes the Jump
         List's patchNameCache for that slot as a side effect.
  slot = raw 0-103 in both writes (NOT the SAVE protocol's bank/num
  split, Sec 15 — a THIRD distinct addressing scheme CMD 0x04 can take;
  see Sec 20 DO NOT RETRY for the other two, already-confirmed-different
  ones. Do not conflate any of the three.)
  Rationale for using the no-recall method here when export couldn't:
  export's bug was specifically about READING — a cold, un-recalled slot
  can hand back a stale signature/cab-table snapshot or even a stale
  internal name next to otherwise-current data. A WRITE has no such
  failure mode; you're setting data, not depending on hardware to hand
  back something fresh. Every live test of Avid's own Load All Rigs
  worked cleanly, including correctly refreshing the CMD 0x04 name-index
  a stale-read slot can otherwise disagree with (see Sec 20 note below).
  Existing pacing from the already-shipped single-patch Load TFX (Sec 16)
  reused as-is (300ms after the bulk write, 150ms after the name write) —
  not yet independently tuned for the multi-slot case, but not reported
  as a problem either.
  ONLY WRITES WHAT THE SOURCE LISTS — a 25-entry XML/zip writes exactly
  those 25 slots and leaves the other 79 untouched. Source can be a loose
  .xml (sibling .tfx files on disk, same folder) or a .zip (everything
  read directly from the archive, no manual unzip needed).
  VALIDATE-UP-FRONT, DECIDE-ONCE (Charlie's explicit design call,
  2026-08-10 — see Session Log for the reasoning): every entry the XML
  lists is checked (file exists, has a real TFX header) BEFORE any
  hardware write happens. This is NEITHER of the two obvious options:
  not Avid's own behaviour (writes progressively, stops silently on the
  first bad file, leaves a partially-imported bank with no record of what
  landed) and not naive all-or-nothing (one bad file blocking 103 good
  ones). One prompt shows the complete picture — what will import, what's
  being skipped and why — Charlie picks skip-and-continue or cancel once,
  with full information, before anything touches the rack.

ABANDONED APPROACH (kept in code, unused, for the record — protocol.js's
reqSendPatchBySlot) — Avid's OWN direct by-slot SEND_PATCH QUERY (i.e.
the read-side mirror of the import write above), no recall:
    F0 13 0B 0F 01 00 [slot] F7
    -> F0 13 0B 0F 12 00 [slot] [encode7bit(body)] F7
  Decoded from the same Wireshark capture as the import mechanism above,
  and initially used for export — half the round trips of the recall
  method, nothing visible on the front panel. Live-tested and found
  unreliable: files decoded as structurally perfect (right size, right
  name, well-formed) but Avid Editor's own loader intermittently
  rejected them, both singly and in a full bank. Byte-diffed against a
  known-good single-patch manual capture (recall-based) of the same
  patch and found the ONLY differences were the "signature/headerCode"
  field (body[4:8]) and, on a separate occasion, the internal name field
  itself truncated by one character — both consistent with reading a
  slot's memory before some hardware-side refresh (triggered only by an
  actual recall) had completed. A 60ms settle delay was tried as the
  first, cheap fix and failed on the very next live test — two failed
  fixes on the same theory (this Primer's own rule) meant switching
  method, not tuning the delay further. Charlie's own read, plausible and
  unconfirmed: ElevenHack's author likely tried this same invisible
  method and hit the same wall, landing on the slower recall-per-slot
  walk for exactly this reason.

RACE CONDITION FOUND AND FIXED IN scanSlot() ITSELF (sysex-handler.js,
handleBulkTfxData) — predates this session, just never exercised at real
104-slot scale before (Scan Bank, which has always used this exact path,
was a hidden feature with no UI entry point). scanSlot()'s REQU_SEND_PATCH
reply (CMD 0x01) carries no slot number on the wire, so the handler
guessed the slot from the app's own `currentSlot` — which only updates
once a SEPARATE CMD 0x02 "slot confirmed" broadcast has landed. No
ordering guarantee between those two messages; a late confirm meant the
guess was wrong, the reply went unclaimed, and that slot's promise just
timed out. Symptom: full exports coming back with roughly half the
expected 104 files. FIX: for CMD 0x01 replies specifically, trust
pendingScanResolve unconditionally (nothing else sends a bare
REQU_SEND_PATCH while a scan/export has one in flight) instead of gating
on the currentSlot guess, and resolve with the slot actually requested.
CMD 0x00 broadcasts (which DO carry a real slot byte) are unaffected.
CONFIRMED via two consecutive clean 104-file exports after the fix.

RELATED, SEPARATE FINDING — Avid Editor's own exporter silently drops the
LAST character of a patch name whenever that name is exactly one
character longer than the immediately-preceding slot's name and shares
its full prefix (e.g. a slot named "Dumble Drive" followed by one named
"Dumble Drive1" -> Avid's own file for the second slot loses the "1"; a
16-char name at the true documented limit, "Glaswerks SODII1", showed
the identical pattern). Eleven Edit's own captures (both the old
single-patch capture feature AND the new by-slot/recall methods)
correctly preserve the full name every time — cross-confirmed by two
independent, unrelated code paths agreeing with each other and
disagreeing with Avid. Not an Eleven Edit defect; worth remembering that
Avid's own reference exports cannot always be trusted as ground truth for
a name field specifically. Separately, the CMD 0x04 name-index (read by
the Jump List feature, Sec 24 2026-08-03 entry) is now confirmed to be a
DIFFERENT stored value from the patch body's own embedded name and the
two can genuinely disagree on real hardware (observed live: an old
front-panel rename apparently updated one without the other) — Avid's
own Load All Rigs explicitly rewrites both per slot (see the import wire
sequence above), which is why a full Avid reload always shows them back
in sync; nothing else in this app writes to that index.

orchestration, both button+modal wiring), src/js/zip-writer.js

RIG TEMPO — CMD 0x50. FULLY DECODED 7/24/2026 (Tempo_Settings.pcapng).
  PER-PATCH — corrected 7/26/2026. The live value is broadcast rig-wide (front
  panel, Avid, our echo), which earlier read as "rig level, not per patch," but
  Charlie confirmed by test that the value is STORED IN THE PATCH: save a patch,
  navigate away and back, and the tempo persists and differs between patches;
  editing it flags the patch dirty on the hardware and in the Avid editor, same
  as Rig Volume and the To Amp volumes (see Sec 18). Treat tempo, Rig Vol and
  To Amp 1/2 alike: per-patch values that happen to sit outside a panel in the
  GUI. (The stale transport.js comment near the nav pull still calls tempo "not
  per patch — strictly a refresh"; harmless, but correct it when next in there.)

  THE PAYLOAD IS MICROSECONDS PER BEAT — the standard MIDI tempo quantity —
  carried as a 24-bit number split into four SIX-BIT digits, most
  significant first:
      us  = (d1 << 18) | (d2 << 12) | (d3 << 6) | d4
      BPM = 60000000 / us          (displayed to one decimal)
      d1..d4 back out of BPM by the reverse: us = round(60000000 / BPM)

  *** THE BYTES ARE 6-BIT DIGITS, NOT THE 7-BIT BYTES USED BY CMD 0x11. ***
  Every payload byte is below 0x40. Reading them as base 128, by analogy with
  every other multi-byte value in this protocol, is exactly what made this
  look like an undecodable inverse relationship with a ~98:1 span. If a
  multi-byte value refuses to decode, check the observed byte ceiling before
  assuming the field width — the ceiling is data.

  EXACT against all six calibration points, no rounding slack, and the
  encoder reproduces every captured message byte for byte:
      500.0 BPM   00 1D 13 00      120000 us
       60.0 BPM   03 34 09 00     1000000 us
      120.0 BPM   01 3A 04 20      500000 us
      240.0 BPM   00 3D 02 10      250000 us
       32.1 BPM   07 08 15 27     1869159 us
       10.0 BPM   16 38 36 00     6000000 us

  READ:      F0 13 0B 0F 01 50 F7
  RESP:      F0 13 0B 0F 12 50 d1 d2 d3 d4 F7
  BROADCAST: F0 13 0B 0F 02 50 d1 d2 d3 d4 F7   (front panel, Avid, or our
             own write echoed straight back — the echo agrees with what was
             sent, so unlike CMD 0x0D it needs no suppression)
  WRITE:     F0 13 0B 0F 00 50 d1 d2 d3 d4 F7

  RANGE: 10.0-500.0 BPM per the hardware and the Avid editor. 24 bits reaches
  far past both ends, so the limits are the rack's, not the encoding's.

  RETRACTED BY THIS ENTRY (was in Sec 21 as an open question):
    - "INVERSELY related to BPM but not a simple reciprocal, value range spans
      a ratio of about 98 where 10-500 BPM spans 50." It IS a simple
      reciprocal. The 98:1 was an artifact of the wrong field width.
    - "The startup reply F0 13 0B 0F 12 50 01 3A 04 20 F7 is byte identical
      across sessions at different tempos, so it is NOT the tempo value."
      01 3A 04 20 decodes to exactly 500000 us = 120.0 BPM, the default. It
      IS the tempo value; the probe evidently ran at 120 BPM each time.
    - Sec 6's "CMD 0x50 — Version/capabilities query, response 04 03 14 29
      (likely firmware version)" — wrong command, deleted there.

  COST WARNING — A TEMPO CHANGE IS AN EXPENSIVE EVENT. The rack rebroadcasts
  the parameters of every tempo-synced block afterwards: three CMD 0x11
  messages in the calibration capture, but 753 in an earlier front-panel
  sweep (paramLo 0x02 on handle 0x17, paramLo 0x04 on handle 0x1A). Anything

===================================================================
20A. KNOB / CONTROL CONTRACT (every knob and slider must obey ALL of these)
===================================================================

WHY THIS EXISTS. Knob mechanics are IDENTICAL everywhere — there is no knob
anywhere that behaves differently because it needs to. Every "difference" found
so far has been a rule that was FORGOTTEN when a panel was built, because the
rules lived scattered in whatever bug-context first produced them (the 9.9 fix
in the amp Speed context, the Sync interlock in the amp panel, etc.). With 50+
new knobs coming across FX1/FX2/MOD/DELAY, a single checklist is what stops each
new panel from re-inheriting an old gap. When you build or copy a knob panel,
satisfy EVERY item below. Each item points to its origin detail; this section is
the authoritative list, not a replacement for those.

R1 — ENDPOINT SENTINELS ON WRITES. A knob write must send the endpoint-sentinel
  tail, NOT 00 00 00 00, or the control cannot reach its true top/bottom (caps
  at 9.9 instead of 10.0; Pre-Delay ~198 not 200). Origin: Sec 3/4 ENDPOINT
  SENTINELS; the "9.9 bug" (Sec 23) was this rule missing from fx-transport.js.
  Applies to EVERY per-panel send function, not just the amp path.

R2 — ZERO-VALUE SAFE. Value 0 is a legal knob value. Never initialise or read a
  knob value with a falsy guard (parseInt(x) || default, x ? x : default) — 0 is
  falsy and gets silently replaced, making a knob at 0 jump to the default on
  grab. Use an explicit undefined/null check. Origin: the zero-value drag fix.

R3 — RED-ON-CHANGE (dirty indication). A knob turns RED when its live value
  differs from the value in the loaded patch, and returns to normal when it
  matches again (or the patch is saved). Origin: Primer knob-colour-state.

R4 — SCROLL-WHEEL. Every knob accepts mouse-wheel adjustment on hover, in
  addition to drag. No knob is drag-only. Origin: Primer scroll-wheel item.

R5 — dB / UNIT SCALE ANCHORING. A display scale (dB, ms, ratio, etc.) is
  anchored at a REAL measured point and derived from the confirmed curve shape —
  never stretched to fit assumed endpoints. Confirm the curve against hardware
  before trusting a formula. Origin: Sec 18 (Amp Out), Sec 23 (Dyn3 formulas).

R6 — DRAG-QUEUE SAFETY. A queued hardware write must NEVER fire after mouseup
  has reset the drag's paramLo to -1: that sends byte 0xFF, an illegal 7-bit
  MIDI data byte, mid-SysEx, and can hang the rack (not an assert — a hard
  wedge). Guard every panel's drag handler. Origin: the DRAG-QUEUE RACE, Primer
  HARDWARE SAFETY.

R7 — SYNC INTERLOCK (any knob a Sync selector can drive). When a Sync selector
  is engaged it takes control of one or more knobs and sets them to a
  division-derived value; in that mode the rack treats those knobs as OUTPUTS
  and IGNORES writes to them. The rule, mirroring the physical hardware and
  BETTER than Avid (whose knob goes inert): GRABBING such a knob sends Sync=OFF
  first, once per drag, then writes the knob normally — handing control back to
  the user exactly as the rack's own front-panel knob does. Do NOT write-guard
  or grey the knob out (both tried 7/23, both worse). Origin: Sec 11 amp
  Sync/Speed interlock.
  *** THIS APPLIES TO EVERY SYNCED CONTROL, PRESENT AND FUTURE — not just the
  amp Speed knob. *** The FX1 Chorus panel was found missing the grab-clears-
  Sync half and RETROFITTED 7/31/2026 (and Sync turned out to drive BOTH Chorus
  and Rate on that panel, confirmed live). Any panel with a Sync selector
  (MOD/DELAY families to come) must implement R7 from the start.

R8 — DOUBLE-CLICK RESTORES THE KNOB TO ITS LOAD VALUE. Double-clicking a knob
  jumps THAT ONE knob (not all knobs) to the value it had when the patch loaded
  — the same baseline R3 uses for the red ring. It behaves exactly as if the
  user had manually turned the knob back to that value: the rack reacts in real
  time (you hear the parameter return to its original amount), and the ring
  clears back to normal because the knob now matches the baseline again. It is a
  position shortcut, nothing more — no save, no commit, no effect on other
  knobs. The baseline is the load/save baseline (refreshed on save, per R3), so
  after a save double-click returns to the saved value; there is no reach-back
  past a save (that is what a disk patch backup is for). Because the rack must
  hear the jump like any knob change, the same send rules apply — R1 endpoint
  sentinels (a baseline at max restores to 10.0, not 9.9) and R6 drag-queue
  safety. Applies to every knob on every panel.

R9 — SYNC OFF KNOB JUMP (aka the SYNC-CLEAR REPAINT RACE). A DIFFERENT bug
  from R7, easy to conflate with it because it looks identical to the user —
  R7 is about the WRITE (the knob must send Sync=OFF so the rack accepts the
  write at all); R9 is about the READ side once R7 is implemented. The moment
  R7's Sync=OFF write goes out, the rack replies almost immediately with a
  broadcast for the knob it just freed. If that broadcast is painted onto the
  knob UNCONDITIONALLY, it can land WHILE the user's own drag is still moving
  the mouse — visually the knob jumps to whatever transitional value the rack
  reported, then snaps back to wherever the drag left it. Same visible shape
  as the OLD R2 falsy-zero jump-to-default bug, DIFFERENT cause (a genuine
  broadcast race, not a bad guard) — check R2 is actually fine before
  assuming a recurrence; they can coexist as two candidate explanations for
  the same symptom and only one may be present.
  FIX: a per-control "currently being dragged" flag that the CMD 0x11
  readback handler checks and skips repainting while true, clearing it on
  mouseup/blur — i.e. R6's drag-queue guard, but for the READ direction
  instead of the write queue. THIS PATTERN ALREADY EXISTED before R9 was
  named: To Amp 1/2 (ui.js, toAmp1Dragging/toAmp2Dragging) — "readback
  handler checks these and skips display update while the user is actively
  dragging, preventing HW broadcasts from fighting the drag in progress."
  R9 formalizes that existing pattern as a MANDATORY rule for any control
  where R7 applies (a write-triggering interlock), since R7 is exactly the
  situation that provokes the race — a plain knob with no side-effect write
  on grab is much less exposed to it. Origin: DELAY Rate/Sync interlock,
  found live 2026-08-02 (Session Log) — R7 was implemented first, R9's gap
  surfaced on the very next live test as "grab the knob, it jumps to
  midpoint then back," which Charlie recognised from the OLD R2 bug's
  symptom and asked whether it had recurred; it had not — this was new.
  DEPLOY CHECKLIST for any future R7 control: implement R7 (clear-write) and
  R9 (drag-guard on the SAME paramLo) together, not just R7 alone — an R7-
  only implementation LOOKS correct in every way except a live drag, which

*** KEEP THESE IN NUMERIC ORDER. *** They drifted out of order between 7/20

C1 — 0x04 FRAMING (RESOLVED). Old raw-USB research (node-usb / Wireshark)
  shows a 0x04 device byte in the header (F0 13 0B 04 0F) and a 0x04 marker
  before every 3 payload bytes. The Java-bridge MIDI path does NOT: the app
  sees clean F0 13 0B 0F with no framing. Both are correct for their own
  layer. Application code must never add/strip 0x04. Separately, the 0x04 at
  data[6] of CMD 0x11 FORMAT B is real SysEx, unrelated to USB framing.

C2 — REQUIRED DRIVER VERSION (RESOLVED). v1.1.12 is confirmed as the working
  driver for the Java-bridge build. The v1.0.11 requirement came from the 
  abandoned node-usb path, which claimed the raw USB interface; the Java-bridge
  path goes through the OS MIDI layer and works on the newer, fully featured

C3 — paramLo VALUES ABOVE 0x0F (RESOLVED, newer wins). The June research
  derived paramIds from Avid XML sldX letters (sldF=0x0F, sldG=0x10), which is

C5 — AMP BYPASS paramLo (RESOLVED). June research: 0x01 (from the wrong XML
  derivation). Confirmed: amp bypass = 0x06, cab bypass = 0x14, and paramLo

TFX BLOCK PARAMETER SETS  (from 9 patch files, 7/18)
-------------------------------------------------------------------
A TFX carries all 10 blocks, so each saved patch yields up to 10 model
parameter sets for free. No capture needed.

TFX LAYOUT: 4-byte key stored REVERSED, followed by its 4-byte value.
  Slot table at offset 208: 11 x 16 bytes = Wor[letter]+value, Wst[letter]+value.
    Wst value = SLOT ID (see Sec 4).   Wor value = MODEL ID (TFX numbering).
  Block parameters follow the bypa[letter] marker for that slot. The bypa key
  is 5 chars, which breaks the 8-byte stride — re-anchor after it.
  The AMP block has NO bypa marker; it uses sld* keys and sits in chain order.

*** TFX MODEL ID IS A DIFFERENT NUMBERING FROM THE CMD 0x20 MODEL INDEX. ***
  They are not offset by a constant. Do not convert between them by arithmetic;
  correlate by parameter set / block type. (MultiChorus: CMD 0x20 0x04-0x06,
  TFX 0x58-0x5A. Parametric EQ: CMD 0x20 0x12-0x13, TFX 0x4E-0x4F.)

*** MODEL ID ENCODES MONO vs STEREO INSTANTIATION *** (confirmed 7/18)
  The same patch saved in mono and again in stereo keeps identical model IDs
  for every PRE-amp block and changes the ID of every POST-amp block:
    800 EchoScream  post-amp  0F 26 4E 50 33  ->  11 48 4F 52 35
    Big Blue        post-amp  0F 58 1B 55 4E 33 -> 11 5A 30 56 4F 35
  Pre-amp blocks unchanged in both. Confirmed on two independent file pairs.
  Known mono/stereo pairs: 0F/11 (FX Loop), 26/48 (Volume), 4E/4F (Param EQ),
  50/52 (Dyn Delay), 33/35 (Eleven SR), 58/5A (MultiChorus), 1B/30 (BBD Delay).
  THIS EXPLAINS two earlier observations: the duplicate display names in the
  CMD 0x20 table (Sec 23) are mono/stereo variants, and a stereo/mono toggle
  reassigns exactly the post-amp handles (Sec 4) because those blocks are
  genuinely re-instantiated as different models.

OUTPUT CHANNEL TABLE — mid -> mono or stereo out  (7/19)
-------------------------------------------------------------------
Needed for the chain row's double-arrow connectors: the connector AFTER a
block is stereo exactly when that block's OUTPUT is stereo.

*** EXTEND THIS TABLE ONLY BY THE LOWEST-VARIANT RULE, NEVER BY GUESSWORK. ***
The rule (Sec 4): within a model family the LOWEST variant is mono-out and
every other variant is stereo-out. It follows from there being no
stereo-in/mono-out variant anywhere.
  NOTE — an earlier revision of this header claimed the rule was broken by
  C1 Chorus/Vibrato being stereo-out in both variants, and concluded the table
  could not be extended by inference at all. That was itself a partial-data
  error: C1 has THREE variants (mid 0x01/0x02/0x03) and only the upper two had
  been seen. The claim is RETRACTED and the rule holds. See Sec 4.
  EXCEPTION: FX Loop — send and return are independent, so variant order says
  nothing about its output. Loop variants must each be observed.

HOW IT WAS DERIVED (repeat this to fill gaps):
  Within any chain, out(block N) == in(block N+1). Anchor with: the first
  block's input is mono (guitar in), the amp's input is mono, and any chain
  the user has explicitly identified as stereo from a given point on.
  Solve as a union-find over (modelId,'in') / (modelId,'out') nodes.
  Do this in TFX-model-id space, then translate to mid via the bridge — the
  same solve run directly in mid space collapsed, because the "everything
  pre-amp is mono" anchor is unsafe there (a stereo FX Loop can sit pre-amp).
  Run over 35 TFX files + 109 logged chain maps: NO CONTRADICTIONS, which is
  also the evidence that in/out are FIXED per model id rather than contextual.

  NAME SOURCE — CMD 0x04, confirmed live this session (previously only a
  Tech Ref "ALSO CAPTURED, not yet used" note, ambiguously transcribed):
      Query:  F0 13 0B 0F 01 04 [space] [slot] F7
      Reply:  F0 13 0B 0F 12 04 [space] [slot] [name] 00 F7
    space = 0x00 user patches, 0x01 factory patches (only two valid values
    — NOT a bank number). slot = the FULL raw slot 0-103 within that space
    (NOT slot%4). This is a DIFFERENT addressing scheme from the SAVE
    protocol's CMD 0x04 write form (bank=floor(slot/4), num=slot%4, Sec
    15) — the first version of this feature wrongly reused that scheme,
    which happened to look correct for A1-A4 only (both schemes agree for
    slot 0-3) then broke immediately after: slot 4 (B1) under the wrong
    scheme sent bytes (1,0), read by the hardware as [space=1 FACTORY,
    slot=0] = factory a1, and bank 2+ isn't a valid space value at all
    (no reply, matching the blank C1-onward Charlie originally saw). The
    name DECODE itself (offset 8 to the null terminator) was correct from
    the start. Factory patches (a1-z4) are deliberately never shown —
    Charlie's call, this app only tracks user A1-Z4.

2026-07-19 (later still) — Channel configuration decoded. The variant index
  within a model family encodes mono/stereo in and out, and there is no
  stereo-in/mono-out variant — which is why a single mono-only block placed
  post-amp collapses the entire chain upstream of it to mono. Proven by a
  purpose-built patch pair (all-mono-left/all-stereo-right, then the same
  patch with WAH dragged to the end) and independently consistent with the
  drag-test capture. Section 4.

2026-07-19 (later) — CHAIN REORDER SOLVED, the last unknown in the chain

7/23 (afternoon) — TREMOLO FEATURE SET COMPLETE, and four wrong diagnoses

  • Tremolo On/Off found at paramLo 0x13 — a control that exists only on the
