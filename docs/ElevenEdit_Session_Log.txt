ELEVEN EDIT — SESSION LOG (append-only scratchpad)
===================================================================
Purpose: the ONE place provisional, unconfirmed, or in-progress findings
live during a work session. Newest entry on top. Safe to be messy and even
contradictory — nothing here is treated as truth until it is promoted.

TRUTH LIVES ELSEWHERE:
  ElevenEdit_Technical_Reference.txt — confirmed protocol/hardware facts
  ElevenEdit_Primer.txt              — project orientation & app state
Confirmed facts are EDITED IN PLACE in those two docs. This log is never a
substitute for them and is never superseded by a dated copy.

HOW AN ENTRY GRADUATES:
  1. Add findings here as you work (any state: idea, tried-X-got-Y, confirmed).
  2. When a finding is CONFIRMED, promote it: edit the value directly into the
     Technical Reference (or Primer), then mark the log entry [FOLDED IN].
  3. [FOLDED IN] entries can be deleted once the merge is verified. The log
     should trend back toward empty.

A FACT IS EITHER:
  - confirmed  -> lives in a main doc, edited in place, not here; or
  - provisional -> lives here.
Never both. Never a third dated file.

ENTRY FORMAT (copy this block):
-------------------------------------------------------------------
DATE:        YYYY-MM-DD
STATUS:      provisional | confirmed | [FOLDED IN: <doc + section>]
AREA:        (e.g. Sync selector / CMD 0x11 / TFX keys / UI)
FINDING:     what was observed, in plain terms
EVIDENCE:    capture file, byte sequence, test result, or "inferred — unverified"
CONFLICTS:   any main-doc value this would change (cite section), or "none"
NEXT:        what would confirm it, or what to do with it

DATE:        2026-07-31
STATUS:      CODE FIX APPLIED, NOT TESTED LIVE — needs Charlie's build/HW test
AREA:        FX1 Chorus panel missing the Sync interlock (R7) the amp has
FINDING:     The amp Sync/Speed interlock (Tech Ref Sec 11 / now R7 in the
             Sec 20A Knob Contract) says: grabbing a Sync-driven knob sends
             Sync=OFF first, once per drag, then writes the knob — mirroring the
             rack's own knob, which clears Sync when grabbed. The FX1 Chorus
             panel (built 7/30) implements the Sync-SETS-the-knob half but NOT
             the grab-CLEARS-Sync half: grabbing Rate while Sync is engaged does
             not turn Sync off, unlike the amp panel and unlike the physical HW.
             Noticed by Charlie 7/31. This is the exact scatter failure the new
             contract exists to prevent — the rule lived only in the amp context
             and was not carried to the effect panel.
FIX APPLIED (2026-07-31, Claude Code): Rate (paramLo 0x04) marked
             syncDriven:true in FX1_MODELS (protocol.js). fx-panels.js FX1 drag
             handler now clears Sync (paramLo 0x06 -> 0) once per drag on grab
             of any syncDriven cell before writing the knob, matching the amp
             pattern exactly (mousedown latch, mousemove check, no write-guard/
             grey-out). Same interlock applied to the FX1 dblclick (R8) handler,
             since a baseline-restore is a knob move too. Built generically
             (fx1SyncCellLo / fx1CellIsSyncDriven / fx1ClearSyncIfDriving read
             the model's row data, not a hardcoded paramLo) so MOD/DELAY's
             future Sync-driven controls only need the syncDriven flag on their
             model row, not new interlock code.
EVIDENCE:    Code only — node --check passed on fx-panels.js/protocol.js/ui.js.
             NOT hardware-tested (no bridge in this session per usual).
CORRECTION (2026-07-31, same day, Charlie's first live test): Rate cleared
             Sync correctly, but Chorus did NOT — Charlie confirmed grabbing
             Chorus while Sync was engaged left Sync on. Matches the earlier
             capture note ("engaging Sync overwrites the live Chorus AND Rate
             values") — Sync drives BOTH knobs on this model, not just Rate.
             FIXED: Chorus (paramLo 0x02) also marked syncDriven:true in
             FX1_MODELS (protocol.js). No handler code changed — the R7
             interlock in fx-panels.js was already written generically against
             "any syncDriven cell in the model", so adding the flag was the
             entire fix. Noted as possibly the only FX1 model where Sync
             drives two knobs at once (per Charlie) — worth checking on every
             future Sync-bearing FX1/FX2/MOD/DELAY model rather than assuming
             single-knob like the amp.
