ELEVEN EDIT — SESSION LOG (append-only scratchpad)
===================================================================
Purpose: the ONE place provisional, unconfirmed, or in-progress findings
live during a work session. Newest entry on top. Safe to be messy and even
contradictory — nothing here is treated as truth until it is promoted.

TRUTH LIVES ELSEWHERE:
  ElevenEdit_Technical_Reference.txt — confirmed protocol/hardware facts
  ElevenEdit_Primer.txt              — project orientation & app state
Confirmed facts are EDITED IN PLACE in those two docs. This log is never a
substitute for them and is never superseded by a dated copy.

HOW AN ENTRY GRADUATES:
  1. Add findings here as you work (any state: idea, tried-X-got-Y, confirmed).
  2. When a finding is CONFIRMED, promote it: edit the value directly into the
     Technical Reference (or Primer), then mark the log entry [FOLDED IN].
  3. [FOLDED IN] entries can be deleted once the merge is verified. The log
     should trend back toward empty.

A FACT IS EITHER:
  - confirmed  -> lives in a main doc, edited in place, not here; or
  - provisional -> lives here.
Never both. Never a third dated file.

DATE:        2026-07-30
STATUS:      confirmed root cause, fixed in DIST/REVERB/WAH/VOL/FX1, NOT
             TESTED LIVE yet — Charlie's rack was hung/deadlocked when this
             was found, not asserted (no factory reset needed; per Tech Ref
             this class of firmware confusion has recovered before with a

AREA:        DRAG-QUEUE RACE — malformed paramLo=-1 send wedged the hardware
FINDING:     Charlie sent the app's own session log after a hang working the
             Dyn3 Ratio knob (rapid dragging/wheeling). Rack stopped
             responding to everything, including the Avid editor (which
             could still probe/connect but got no data back either) — so
             this is hardware-side confusion, not an app-side hang. Found
             the exact trigger by grepping the log for anything with a
             negative or out-of-range paramLo byte:
               [12:11:51] RX: {"cmd":"send","hex":"F0 13 0B 0F 00 11 0F -1 63 00 00 00 00 F7"}
               MIDI OUT: F0 13 0B 0F 00 11 0F FF 63 00 00 00 00 F7
             paramLo arrived as the JS number -1, which (-1).toString(16) do
             encode as the literal text "-1" (not a hex pair) — the bridge
             sent it as raw byte 0xFF. 0xFF is not a legal 7-bit MIDI data
             byte (bit 7 set) — it is literally the MIDI System Reset
             status byte, landing mid-SysEx. The very next hardware reply
             came back one byte short (13b instead of the expected 14b,
             missing byte), so the rack's OWN parser visibly got confused by
             it too — strong corroboration this exact byte is the trigger,
             not a coincidence. Traffic continued for several more seconds
             after that one bad send, then went silent for good ~12 seconds
             before Charlie force-quit — consistent with a single bad byte
             putting the SysEx parser in a bad state that didn't fully
             surface until more traffic followed.
             ROOT CAUSE — a closure-timing race, present in EVERY effect
             panel's knob-drag handler (DIST, REVERB, WAH, VOL, and the FX1
             just built off the same template), NOT present in the ORIGINAL
             amp tone-knob drag (ui.js), which is why this took this long to
             surface: queueKnobSend throttles a knob's hardware write by up
             to 60ms (KNOB_SEND_INTERVAL) via setTimeout. The DIST-pattern
             drag handlers passed a closure like
               function(v) { sendDistParamWrite(activeParamLo, v); }
             where activeParamLo is the panel's SHARED mutable drag-state
             variable — read at SEND TIME (when the 60ms timer fires), not
             at the moment the closure was created. mouseup resets that same
             variable to -1 immediately on release. So: drag a knob, release
             the mouse within 60ms of the last drag tick, and the queued
             send fires AFTER mouseup already zeroed activeParamLo to -1 —
             sending garbage. The ORIGINAL amp tone-knob handler never had
             this bug because it captures a fresh `const lo = knobs[idx].lo`
             INSIDE the mousemove call before building the closure, so each
             queued send owns its own copy, immune to a later mouseup.
             FIX — same shape in all five: snapshot the shared var into a
             local (`var lo = activeParamLo;`) immediately before the
             queueKnobSend call, and close over that local, not the shared
             one. One line per handler, fx-panels.js: DIST (line ~172),
             REVERB (~397), WAH (~534), VOL (~712), FX1 (~943).
EVIDENCE:    Charlie's app log, session20260730120800.log, line ~5589 (the
             malformed send) and the short/garbled reply immediately after.
CONFLICTS:   none — this bug predates today's FX1 work (DIST/REVERB/WAH/VOL
             have had it since they were built) but was never triggered
             visibly before; it just happened to surface during fast Ratio
             knob dragging today.
NEXT:        Charlie power-cycle the rack (per Tech Ref: after a firmware
             assert/confusion, power-cycle recovers it — this is NOT the
             CMD 0x37 brick class, no factory reset needed) and rebuild with
             this fix before resuming any FX1 work. If a hang recurs after
             this fix, the closure race is NOT the whole story and needs
             more digging — but this is a clean, reproducible, well-
             corroborated root cause, not a guess.

AREA:        THE "9.9 BUG" — endpoint sentinels missing from fx-transport.js
FINDING:     Charlie's live FX1 test: Chorus and Rate knobs visibly reach 10
             on screen but immediately settle back to 9.9 on hardware
             readback; Depth stays at 10 on screen but hardware never passes
             9.9. Named "the 9.9 bug" per Charlie's request — this is a
             RECURRENCE, not a new bug: it's the exact defect already fixed
             once for the amp Tremolo Speed knob (Tech Ref, "ENDPOINT
             SENTINELS ON WRITES", 7/23/2026) — a CMD 0x11 value is five
             7-bit bytes, not one, and sending v0 with a 00 00 00 00 tail
             asks for the literal BOTTOM of that value's step. Byte-
             quantised controls can't tell the difference; anything with
             real sub-step precision reports back one tick low. The 7/23 fix
             (special-case true endpoints with sentinel tail bytes: max ->
             3F 7F 7F 7F 0F, min -> 40 00 00 00 00, else v0 00 00 00 00) only
             ever went into transport.js's amp-knob sendParamWrite. It was
             NEVER ported to the per-effect-panel send functions in
             fx-transport.js — so sendDistParamWrite, sendReverbParamWrite,
             sendWahParamWrite, and sendVolParamWrite (and, until this
             entry, sendFx1ParamWrite, copied from that same unfixed
             pattern) all still send a flat zero tail and are exposed to the
             same bug on any of their knobs that have real precision.
             FIXED for sendFx1ParamWrite only (fx-transport.js) — same
             endpoint-sentinel logic as transport.js, inline comment names
             it "THE 9.9 BUG" so it's grep-able next time. DIST/REVERB/WAH/
             VOL's send functions are UNCHANGED — same latent bug, left
             alone per this session's FX1-only scope; worth a dedicated pass
             later since it's the same three-line fix copied four more
             times.
EVIDENCE:    Charlie's live hardware test, 2026-07-30 — Chorus/Rate/Depth
             knobs on the FX1 C1 Chorus/Vibrato panel.
